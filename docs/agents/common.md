# Довідник агента: спільне для всіх кроків

Практичний досвід кроків Т.15–Т.49: команди, пастки, порядок дій. Читати кожному агентові, що виконує крок («роби Т.N»), разом із довідником свого типу кроку: [`ui.md`](ui.md) — вигляд і UX, [`sim.md`](sim.md) — правила ядра, симуляції, баланс.

- **Довідник — не правила.** Правила — `AGENTS.md`, `docs/workflow.md` і ADR. Де довідник розходиться з ними — чинні вони, а довідник виправити тим самим PR (ADR-0096).
- **Для кого.** Розділи без позначки — для будь-якого агента (сесія Claude, Mistral Vibe Code, Vibe Work). Розділ «Лише для хмарної сесії Claude» наприкінці описує одне середовище; агент в іншому середовищі його пропускає. Досвід першого кроку гри силами Mistral Vibe Code (Т.39) — у розділах «Крок, який виконує інший агент» і «Лише для Mistral Vibe Code».
- **Як оновлюється.** Урок про спосіб роботи агент дописує сюди в PR свого кроку (один-два рядки, з номером кроку). Крок, що міняє правило в `AGENTS.md`, `docs/workflow.md` чи ADR, тим самим PR править відповідний рядок довідника. Ревізія (звірка з репозиторієм, прибирання застарілого) — раз на ≈ 10 кроків; попередні — Т.36, Т.40 і Т.50, перенесення в репозиторій — Т.38.
- Звірено з репозиторієм на гілці Т.50 від `main` = `9c9f842` (Т.49, 16.11.2026) скриптом `node scripts/agents-docs-check.mjs`: шляхи в `…` і посиланнях, номери ADR і назви `npm run …`, згадані в трьох довідниках, існують. Чого скрипт не бачить — числа й факти кроків, команди без `npm run`, шляхи поза верхніми теками робочої теки й `origin/main` (зокрема з друкарською помилкою в першій частині), ігноровані git файли, що лежать на диску: їх ревізія звіряє `grep` по записах кроків.

## Правила репозиторію: що де шукати

- Правила — `AGENTS.md` і `docs/workflow.md`: тематична гілка від свіжого `origin/main` (`<тип>/<крок>-<суть>`), PR у `main`, мерж merge-комітом, Conventional Commits українською, ADR у коміті зі зміною workflow-файлу або `package.json`, ліміт 500 рядків коду, історію не переписувати (без amend, rebase, force-push).
- `docs/workflow.md` (≈ 280 КБ) цілком не читати: заголовки — `grep -n '^## \|^### '`, потрібне — `sed -n 'A,Bp'`; рядки там по кілька кілобайтів, тому вивід `grep` завжди різати `| cut -c1-300`.
- Правила гри і тексти UI питати у власника до реалізації (до чотирьох питань за раз, з числами). Решту розвилок вирішувати самому і записувати у звіт.
- Текст UI в питанні власникові — повним рядком, як він буде в грі: зі знаком категорії і номером об'єкта (спостереження сесії після мержу Т.49; у записі Т.49 цього немає: текст обрали без номера зонда, і номер довелось питати вдруге, після аудиту).
- Запис кроку — у `docs/workflow.md`, розділ «Технічні задачі (позафазні)», у PR кроку: `- [x] **Т.N (…): назва.** Мета…` і підпункти «Зроблено», «Аудит», «Виконано», «Урок». Звіт — `docs/reports/tNN-<суть>.md`.
- **Куди йде урок (чотири рівні):** про предмет кроку — у звіт; робоча порада «як зробити» (команда, пастка, порядок дій) — у довідник цієї теки (`docs/agents/`); висновок кроку для всіх агентів — підпунктом «Урок» у записі кроку (класу PR не міняє); у спільний розділ «Уроки» `docs/workflow.md` — лише коли це нове правило, і тоді PR класу `approve`; зміна самих правил — `AGENTS.md` і ADR, лише за рішенням власника. **Урок пишеться в одне місце** (ADR-0023): якщо висновок уже є в записі кроку, у довіднику — лише порада, що з нього випливає, з номером кроку, без повторення тексту.
- Звіт і запис кроку писати так, щоб до аудиту в них не було тверджень про результат аудиту; підпункт «Аудит» і номер PR дописувати другим комітом разом із виправленнями (Т.36).
- Числа й факти про минулий крок у ADR, довіднику чи звіті брати із запису кроку і звіту в репозиторії (`grep` перед тим, як писати), а не з нотаток сесії: обидва аудити Т.40 ловили саме такі розбіжності, одну й ту саму — двічі.
- Позначення знахідок у звітах: не починати номер з кириличної «З» — «З1» читається як «31».
- «Схвалюю серію» (ADR-0052) у Т.43 спрацювало: третій PR змержено без нового запиту після зелених чеків і аудиту. Умови мержу серії записувати в описі PR дослівно; власник може й відмовити — у Т.44 відповів «Кожен PR окремо» (спостереження сесії після мержу Т.43: у записі Т.43 і його звіті про мерж третього PR без нового запиту не написано).
- Оцінка розміру PR у плані — до аудиту: у Т.44 PR #342 оцінено у 300–380 рядків, перший коміт — 410, після виправлень за аудитом — 478. Для PR з оцінкою понад 350 одразу ділити або закладати ≈ 70 рядків на аудит.

## Власник (рішення 14–15.11.2026)

- Власник — вузьке місце: дій власника на крок має бути якомога менше, і вони не повинні блокувати агента. Зараз на крок — відповіді до реалізації і «схвалюю» (для класу `approve`).
- Відповідь чи «схвалюю» в чаті — зручно: телефон завжди з ним. Незручне все, що прив'язане до конкретної машини чи файлової системи (тека клону, термінал, застосунок на комп'ютері). Нових дій власника, що потребують його комп'ютера, не вводити; дію планувати так, щоб її можна було зробити з телефона (чат, кнопки, посилання на прев'ю чи сторінку GitHub).
- Пристрої: телефон — завжди; iPad Pro — частіше, ніж Mac mini; ноутбука немає. Прев'ю власник найімовірніше відкриє на iPad Pro або телефоні — посилання на прев'ю давати завжди (подробиці — у [`ui.md`](ui.md)).
- Питання про наступний крок ставити разом із проханням «схвалюю» (або з повідомленням про мерж класу `auto`) — одним зверненням.
- Рішення власника «X — окремим PR» означає відкрити цей PR у тому ж кроці, а не перелічити X у звіті: PR-хвіст без рядка тегу, після мержу основного (Т.36).
- Оркестратор, арбітражні чати і правило «не починати, доки є хоч одне питання» — не впроваджуємо.
- Mistral (план Team) оплачений і використовується мало — власник дозволив використовувати його активніше (15.11.2026).
- Локальний клон власника процесу не потрібен; доступу до його теки не просити.

## Старт роботи з кодом

- Свіжий клон → `npm ci` (≈ 1 хв) → прогони «до».
- Локальний чекліст для кроку з кодом: `npx tsc --noEmit` (+ `-p tsconfig.core.json`, `-p tsconfig.e2e.json`), `npm run lint`, `npm run format:check`, `npm test`, `npm run docs`, `npm run test:e2e`.
- Сценарій e2e без встановленого браузера Playwright: `E2E_CHROME=/шлях/до/chrome npm run test:e2e` (≈ 15 с); з `E2E_URL=…` — проти вже піднятої збірки.
- Pre-commit хук (`scripts/pre-commit.sh`) ганяє повні тести і перевіряє заборонені файли: `tsconfig.json`, `vite.config.ts`; `package.json` і `.github/workflows/` — лише разом із файлом у `docs/adr/` у тому самому коміті (виняток — зміна самого поля `version`, ADR-0070). Не комітити під час симуляцій.

## Розмір і формат

- **Ліміт 500 рахує код, тести й e2e; поза підрахунком — `docs/**`, `*.md`, `assets/**`, бінарні файли, `package-lock.json`.** Число брати лише з `./scripts/pr-size.sh origin/main HEAD`: обидва аргументи обов'язкові, рахує закомічене. У мілкому клоні перед ним `git fetch --depth=50 origin main` — з `--depth=1` після нового коміту в `main` немає спільного предка, скрипт друкує «0 рядків» і `[OK]` (помилку git у конвеєрі він губить; CI рахує правильно). Плановане перевищення — мітка `size-deviation` на PR (ADR-0061).
- Після аудиту PR легко виходить за 500 рядків (Т.37: 499 → 671): для кроку зі скриптом і самоперевіркою закладати запас або одразу планувати мітку `size-deviation` і писати це в описі PR.
- Prettier розгортає довгі об'єктні літерали по рядку на поле; таблиця `Partial<Record<…>>` одним рядком дешевша (Т.33: 549 → 498).
- `AGENTS.md` на `main` не проходить `prettier --check` — не форматувати його цілком. `scripts/*.ts` і `e2e/` поза `format:check` (він дивиться лише `src` та `index.html`) — `prettier --check` на свій файл. `docs/` — у `.prettierignore`: не форматується і не перевіряється.
- `scripts/` не перевіряє ні `tsc`, ні lint, ні тести — закомічений скрипт запускати перед комітом.

## Клас PR і мерж (ADR-0094; `approve` — ADR-0052)

- Клас дає `scripts/pr-class.sh`: останній рядок виводу — `КЛАС: auto` або `КЛАС: approve`.
  - `auto` — кожен змінений файл із переліку: `docs/**` (крім `docs/adr/**`, `docs/prototypes/**`, файлів тестів і `docs/workflow.md` вище рядка `## Поточний статус проєкту`); `src/**/*.test.ts` і `e2e/**`, додані або змінені; `scripts/**`, крім самого `pr-class.sh`, `pre-commit.sh`, файлів `*.test.*` / `*.spec.*` і кожного скрипта, чиє ім'я згадано в `.github/`, `.husky/`, `package.json` або `scripts/pre-commit.sh` (у базі чи в гілці).
  - `approve` — усе інше: `src/` без тестів, `index.html`, ассети, `AGENTS.md`, `README.md`, ADR, `.github/`, `package.json`, конфігурація, видалений чи перейменований тест, символьне посилання, підмодуль, порожній диф, помилка git.
- **PR класу `auto` агент мержить без «схвалюю», коли виконано все:** клас показала версія скрипта зі свіжого `main` на останньому коміті (`git fetch --depth=50 origin main && git show origin/main:scripts/pr-class.sh > /tmp/pr-class.sh && sh /tmp/pr-class.sh origin/main HEAD`); чотири обов'язкові чеки зелені на останньому коміті; аудит пройдено і невиправлених знахідок немає; опис PR має розділ «Аудит» (аудитор, знайдено / підтверджено, що виправлено, що відхилено і чому); у PR немає нового правила гри, тексту UI чи рішення, яке ухвалює власник. Якщо виправлення за аудитом змінило клас — потрібне «схвалюю». **Сумнів = «схвалюю».** Після мержу — повідомити власника: номер PR, клас, підсумок аудиту.
- **Без аудиту клас `auto` не діє** (ADR-0094, п. 5).
- PR класу `approve` мержити лише після явного «схвалюю» власника в чаті або коментарі PR; «продовжуй» — не апрув; апрув не поширюється на наступні PR, крім явно оголошеної власником серії (ADR-0052). Механічний PR (ADR-0057; після ADR-0093 рядків тегів уже немає) — сам після зелених чеків.
- Мерж через API: `gh api -X PUT repos/sergkarpenko/rubezh/pulls/N/merge -f merge_method=merge -f sha=<повні 40 знаків>`.

## Тег кроку (ADR-0093)

- В описі PR кроку (у серії — лише останнього змістовного PR) рядок `Iter-Tag: iter-T.N` з початку рядка, без відступу. Чек `check` workflow `iter-tag` показує назву до мержу (не обов'язковий; зайнята чи недопустима назва — червоний).
- Після мержу тег ставить workflow (≈ 30 с); перевірка: `git ls-remote --tags https://github.com/sergkarpenko/rubezh.git iter-T.N`. Не з'явився — ручний запуск: `gh api -X POST repos/sergkarpenko/rubezh/actions/workflows/iter-tag.yml/dispatches -f ref=main -f "inputs[tag]=iter-T.N" -f "inputs[sha]=<40 знаків>"`. Не допомогло — сказати власнику і виправити запис кроку наступним PR.
- Крок «довідники (`auto`) + ADR-хвіст (`approve`)»: рядок тегу — на першому PR; хвіст відкривати після його мержу від свіжого `main`, на хвіст — окремий аудит (Т.40).
- У записі кроку — «Тег `iter-T.N` — ставить workflow `iter-tag` на merge-коміт PR #N», без sha. Окремий PR рядка тегу не відкривати. Пересунути чи видалити тег може лише власник — назву перевіряти до мержу.
- Якщо власник хоче побачити зміну на основному сайті до тегу — PR без рядка `Iter-Tag`, тег ручним запуском.

## PR і чеки

- Створення PR через REST: `gh api repos/sergkarpenko/rubezh/pulls -f title=… -f head=<гілка> -f base=main -F body=@<файл>`. Зміна опису: `gh api -X PATCH repos/sergkarpenko/rubezh/pulls/N -F body=@<файл>` — запускає чеки з типом `edited`; якщо збіглася з пушем, один прогін `pr-size` буде `cancelled` — дивитись на успішний; відповідь одразу після пушу може показати старий `head.sha`.
- **Опис PR оновлювати тим самим кроком, що й пуш виправлень: спершу `PATCH` опису, потім пуш.** Після Т.41 (ADR-0098) джоба `mistral-audit` читає опис через API під час прогону, тож порядок уже не ламає аудит; але правка опису після прогону лишає в коментарі рядок «Опис PR змінено після цього прогону» (його ставить коротка джоба на подію `edited`, без виклику моделі) — новий аудит буде лише з наступним пушем. Тому після останнього пушу опис не чіпати, а числа останніх прогонів писати в запис кроку і звіт комітом (спостереження сесії після мержу Т.41; у звіті Т.41 цього немає).
- CI запускається лише для PR у `main`: другий PR складеної серії відкривати після мержу першого. Прогони висять у `queued` без джоб — закрити й знову відкрити PR. Червоний `e2e` на `playwright install` — `rerun-failed-jobs`.
- Очікування чеків: `commits/<sha>/check-runs?filter=latest`; чекати чотирьох обов'язкових назв — `test`, `e2e`, `pr-size`, `codecov/patch` (зелені через ≈ 2–5 хв після пушу). `codecov/patch` з'являється на хвилину-дві пізніше за решту: цикл очікування має перевіряти чотири назви, а не «всі наявні завершені» (Т.36). Після мітки `size-deviation` у `check-runs?filter=latest` два записи `pr-size` — новий зелений (подія мітки) і старий червоний з іншого прогону: дивитись на новіший за `started_at` (спостереження сесії під час мержу Т.41). Журнал червоної джоби: `gh api repos/sergkarpenko/rubezh/actions/jobs/<id>/logs | grep -E "×|FAIL|error"`.
- Покриття своїх рядків до пушу: `npx vitest run --coverage --coverage.reporter=json <файли тестів>` і непокриті рядки з `coverage/coverage-final.json`. Червоний `test` лише в `npm run test:coverage` з «Test timed out in 5000ms» — довгому тесту явний тайм-аут (`30_000`) окремим комітом у той самий PR.
- Результат workflow `mutation` — з журналу джоби (`actions/jobs/<id>/logs`, рядки `All files` і ` <файл>.ts`).
- Перевірка `main` без клону: `git ls-remote https://github.com/sergkarpenko/rubezh.git refs/heads/main`.

## Аудит кроку (ADR-0094, ADR-0095, ADR-0097)

Незалежний читач ловить те, що проходить крізь чеки і самоперевірку автора. Аудит — умова мержу класу `auto`; власник лишив його на кожному кроці (14.11.2026).

- **Два аудитори на кожному PR кроку, постійно (ADR-0097):**
  - *аудитор для мержу (ADR-0094)* — читач без контексту автора, інша модель, якого запускає агент-автор (у сесії Claude — субагент Opus; як запускати — у розділі про сесію Claude);
  - *Mistral Large 4* — джоба CI `mistral-audit` на кожен пуш у PR лишає один коментар бота `github-actions[bot]` з позначкою `<!-- mistral-audit -->` (оновлюється). Читати: `gh api repos/sergkarpenko/rubezh/issues/N/comments --jq '.[]|select(.user.login=="github-actions[bot]")|.body'`. Аудитор бачить диф, опис PR (через API під час прогону), `AGENTS.md`, довідники цієї теки, записи згаданих кроків із `docs/workflow.md`, звіти цих кроків (до двох) і згадані ADR — усе з бази PR, — і результати чеків коміту (ADR-0098, Т.41); команд не запускає. Згадки він бере спершу з опису PR, тож крок чи ADR, з яким PR треба звірити, варто назвати в описі. Чеків він чекає до 5 хв, тому коментар з'являється через ≈ 5–9 хв після пушу. Рядок «Контекст із бази» в коментарі показує, що саме він отримав (які записи кроків, звіти й ADR, що обрізано, стан чеків). «Аудиту не було» — зелений чек і причина в коментарі; коли API Mistral недоступний, джоба висить ≈ 18 хв, перш ніж так написати, а на першому коміті PR коментаря може не бути зовсім — пуш другого коміту запускає новий прогін, і «Аудиту не було» приходить уже на ньому, через ≈ 15 хв (спостереження сесії після мержу Т.50) (Т.44: прогони джоби на PR #341 і #342 — 19:17–19:36 і 20:09–20:27 UTC) — мержу не тримає.
  - Умову мержу класу `auto` виконує аудитор для мержу; «Знахідок немає» від Mistral його не замінює. Питання про заміну закрито (рішення власника 15.11.2026). Рахунок Т.37–Т.39 (знайдено / підтверджено): аудитор для мержу 10 / 10, 10 / 10 (одна — частково), 10 / 10; Mistral 4 / 3, 0 / 0, 4 / 3.
- **Коли:** одразу після відкриття PR, не чекаючи чеків — чеки (≈ 3 хв) і аудит (≈ 2–8 хв у Т.36–Т.40, ≈ 7–19 хв у Т.44–Т.49) ідуть одночасно.
- **Що дати аудиторові для мержу:** власну копію репозиторію на гілці PR, номер PR, звіт кроку, рішення власника дослівно, перелік того, що шукати. Нотаток і міркувань автора не давати. Усе, що аудитор має прочитати і чого немає в репозиторії, покласти файлом поруч: розмови автора і зовнішніх документів він не бачить (Т.36).
- **Завдання:** до десяти знахідок за важливістю, кожна з файлом, рядком і доказом командою; «перевірене» окремо від «припущень». Шукати: порушення `AGENTS.md` і `docs/workflow.md`; твердження звіту, яких диф або тести не підтверджують; код, що не працює як заявлено, але проходить чеки; прогалини гейта; **чи не послаблено тест і чи не пише тест або скрипт поза тимчасову теку** (скрипт класу бачить шляхи, а не зміст). Аудитор нічого не змінює.
- **Після аудиту:** кожну знахідку обох аудиторів перевірити; підтверджені — виправити наступним комітом у той самий PR, після виправлення — нові навмисні поломки на новий код; відхилені — в описі PR з причиною. Виправлення не повинно посилатись на те, чого ще немає в репозиторії (ADR із PR-хвоста): номер з'являється в довіднику разом з ADR (Т.40). У записі кроку — модель, знайдено / підтверджено, час, токени — для кожного аудитора окремо.
- Коміт «лише документи з числами останнього прогону» запускає ще один прогін Mistral (після Т.41 — ≈ 83 тис. токенів вводу) і може дати нову знахідку: числа дописувати разом із виправленнями, а далі зупинятись на «пізніші прогони — у коментарі PR» (спостереження сесії на третьому коміті PR #336, після запису Т.41).

## Крок, який виконує інший агент (Т.39)

Досвід Т.39: план і аудит — сесія Claude, код, тести, документи кроку і PR — Mistral Vibe Code. Розділ — для агента, що планує і перевіряє; виконавцеві — розділ його середовища наприкінці файлу.

- **Порядок:** план у `docs/plans/` першим комітом гілки → сесія виконавця з підказкою «перемкнись на гілку, прочитай план, коміть у цю гілку, відкрий PR, не мерж» → чекати PR опитуванням GitHub (`gh api 'repos/sergkarpenko/rubezh/pulls?state=open'`), а не дивлячись у вікно виконавця → аудит → знахідки одним повідомленням у ту саму сесію виконавця → перевірка виправлень власними прогонами чекліста, а не за звітом виконавця.
- **Оцінку розміру робити до плану:** приміряти нові файли й тести до ліміту 500 і ділити на PR уже в плані. У Т.39 план обіцяв «один PR до 500», а панель із тестами дала ≈ 950 рядків — вимога була нездійсненна.
- **Розмір понад 500 — за ADR-0061, і це писати в плані й повторити в підказці сесії:** план без схваленого відхилення, а диф вийшов понад 500 → серія PR або повернення до власника; мітку `size-deviation` без запису в плані чи апруву власника виконавець не ставить. У Т.39 план вимагав другого PR, а виконавець поставив мітку.
- **Кожне твердження плану про наявний UI перевірити по коду до плану:** у Т.39 підказка про встановлення гарматного модуля спиралась на припущення плану — такої панелі в UI немає.
- **Тексти UI в плані — дослівно, з вимогою звірити побайтно;** окрема вимога — «у доданих рядках немає трансліту» (у Т.39 через середовище виконавця коментарі вийшли латинкою, а три тексти — недослівними).
- **Число рядків PR у звіті й записі кроку перераховувати після кожного коміту** (`./scripts/pr-size.sh origin/main HEAD`): у Т.39 коміт виправлень за аудитом додав три рядки коду, звіт оновлено до 1010, а в записі кроку лишилось 1007. Документи кроку — у гілці до відкриття PR (у Т.39 прийшли другим комітом).
- **PR-чернетка:** якщо виконавець відкрив PR як draft — у повідомленні зі знахідками попросити зняти чернетку.
- **Аудиторові для мержу на такому кроці дати копію репозиторію і попросити запустити гру й тести:** у Т.39 помилки в текстах UI на сторінці, підказку про панель, якої немає, і послаблені тести знайшов аудитор із копією репозиторію; аудитор, що бачить лише диф, дав три підтверджені знахідки про документи кроку (розбір — у звіті Т.39).
- **Виконавець не стартував (Т.43):** Vibe Code Web три рази висів на «Thinking» без жодної дії, після перезавантаження сторінки сесія була порожня. Якщо за 5 хв після запуску в сесії виконавця немає жодного виклику інструмента — не чекати годину опитуванням GitHub: перезавантажити сторінку, спробувати одну нову сесію, зупинити завислі (щоб не писали в ту саму гілку) і одним питанням спитати власника, хто пише код. План у `docs/plans/` лишається чинним для будь-якого виконавця.
- **Виконавець не стартував удруге (Т.44):** та сама картина, що в Т.43; порядок «5 хв → перезавантажити → одне питання власнику» спрацював за ≈ 8 хв замість ≈ 1 год 20 хв (за годинником сесії-планувальника; у звіті Т.44 часу немає). Серед варіантів відповіді давати й «спробувати Vibe Work».

## Скрипти CI і workflow

- Логіку workflow, що пише в репозиторій або вирішує про мерж, писати в скрипті з режимом `--self-test`, у yml — лише виклики. Велику самоперевірку тримати окремим файлом поруч, названим у workflow (тоді його зміна — клас `approve`): в аудитора Mistral це `scripts/mistral-audit-selftest.mjs` (ADR-0099, Т.42); `node scripts/mistral-audit.mjs --self-test` запускає його ж. Скрипт, що працює з git, перевіряти в тимчасовому репозиторії (`mktemp -d`, `git init`, `core.hooksPath=/dev/null`), не на заглушці: 64 випадки — ≈ 3 с.
- Помилка команди в умові — не «ні»: `… 2> /dev/null` в `if` робить із будь-якої помилки «не знайдено». Розрізняти коди (`git grep`: 0 — є, 1 — немає, інше — помилка) і в сумніві обирати обережний бік.
- Скрипт не має залежати від поточної теки: у `git grep <ревізія> -- <шлях>` писати `":(top)<шлях>"`. Тип зміни брати з `git diff --raw` (режим 120000 — посилання, 160000 — підмодуль), а не лише з букви статусу. `git/ref/tags/X` для анотованого тегу повертає sha об'єкта тегу, а не коміту. `grep -Eq '^…$'` пропускає багаторядкове значення — відхиляти окремо.
- Навмисні поломки — до аудиту і за переліком гілок логіки, а не «що спало на думку»; агент пише для цього власну обгортку «назва, було, стало» над копією скрипта (у репозиторії готової немає; приклад переліку поломок — `docs/reports/t37/mutations.py`) — 44 поломки за ≈ 2,5 хв.
- Скрипт поломок з e2e (Т.44; урок — у записі кроку): фоновий запуск пише журнал у файл — перед запуском старий журнал видаляти (`rm -f`), інакше цикл очікування читає `EXIT` попереднього прогону. Поломку «прибрати рядок» перевіряти на те, що вона справді прибирає ефект (спостереження першої сесії Т.44 до першого коміту PR #341 — у звіті цього немає: одна поломка в чернетці скрипта не прибирала ефекту і дала зелений e2e). Поломку константи перевіряти даними, де значення розходяться: у PR 3 Т.44 поломку «ціна — число клітинок» перші тести не зловили б — у всіх ціна шляху дорівнювала числу клітинок; це видно, лише коли перелік поломок пишеться за гілками логіки до прогону.
- Скрипт поломок без обробки аргументів запускається повністю і з `--help` (спостереження сесії після мержу Т.44; у записі Т.44 і його звіті цього немає): аргументи перевіряти всі, а не лише перший, синтаксис — `python3 -c "import ast,sys; ast.parse(open(sys.argv[1]).read())" <файл>`, а не запуском і не `py_compile` (той лишає теку `__pycache__` поруч, а правила для неї в `.gitignore` немає — Т.45, знайшов аудит). Тривалість прогону у звіт писати з виміру: скрипт сам друкує «Час: N с» (зразок — `docs/reports/t45/mutations.py`). Копія з `node_modules` посиланням не ізольована повністю: vitest пише кеш у `node_modules/.vite` вихідного клону (Т.45).
- Правка документа скриптом зі склеюванням шматків (`split` / `join`) може здублювати розділ (спостереження сесії після мержу Т.47; у записі Т.47 цього немає: так здубльовано розділ «Межі» звіту, виправлено до коміту) — для вставки розділу досить одного `replace` з `assert count == 1` на заголовку; результат перевіряти `grep -c` заголовків до коміту.
- Звірка довідників з репозиторієм — `node scripts/agents-docs-check.mjs` (Т.50; без аргументів — три довідники, з аргументами — названі файли; код виходу 1, коли є розбіжності): шляхи в `…` і посиланнях, номери ADR, назви `npm run …`. Команди з порад поза `npm run` (обгортки, `gh api`) і числа кроків скрипт не звіряє — їх перевіряти `grep` по запису кроку (Т.38: дві поради посилались на обгортки, яких у репозиторії немає).
- Правило перевіряти на історії: `git fetch --depth=260 origin main`, скрипт на `<мерж>^1 <мерж>^2` для кожного мержу з `git log --merges --first-parent`; після зміни правила числа перерахувати.
- **Крок з інтеграцією із зовнішнім API** (урок — у записі Т.37 у `docs/workflow.md`): планувати прогін наживо в межах кроку, не лише самоперевірку з підставною відповіддю; у повідомлення про збій класти причину зупинки, форму вмісту відповіді й лічильник токенів.
- **Mistral Large 4** (Т.37): міркує завжди, `message.content` — перелік частин (`thinking` + `text`); типова глибина `high` на дифі кроку не вкладається в 3 хвилини, `reasoning_effort: medium` — ≈ 2–4 хв, ≈ 37–39 тис. токенів вводу і 7–13 тис. виводу на прогін. Перед вибором моделі дивитись сторінку моделей Mistral: на 15.11.2026 Devstral 2 і Medium 3.5 позначені як виведені з обігу.
- Самоперевірка скрипта з межами (Т.41): межу перевіряти числом, а не тією самою константою, з якої її бере код, — інакше зміна константи проходить непомітно. Тестові дані з номерами кроків і ADR у коді скрипта читає і сам аудитор, коли шукає згадки в дифі: тому згадки з документів ідуть раніше за згадки з коду.
- Поділ скрипта `.mjs` на два файли (Т.42): файл, що запускається напряму і має `await` на верхньому рівні, не може динамічно імпортувати файл, який імпортує його самого, — Node зависає з «unsettled top-level await»; запускати окремим процесом. Перенесене порівнювати з оригіналом `diff` після форматування; навмисні поломки попереднього кроку прогнати над новою розкладкою. Поломку, що ховає провал (код виходу, рядок підсумку), перевіряти разом зі штучним провалом і тим самим оракулом, що в кроці джоби. Межі, які самоперевірка отримує від основного скрипта окремим об'єктом, перевіряти числами: інакше об'єкт може розійтися з кодом непомітно.
- Крок `run:` без `shell:` у GitHub Actions виконується під `bash -e` — без `pipefail` (з `shell: bash` — уже з ним; видно в журналі джоби, рядок `shell:`). Гейт-конвеєр `команда | tee … | grep -q …` без `set -o pipefail` дивиться лише на `grep`: код виходу команди губиться. Перед тим як писати «як у CI», подивитись у журнал справжньої джоби (Т.42, знайшов аудит).
- Дві джоби, що пишуть один коментар (Т.41): перед записом перечитати коментар; після запису — ще раз звірити те, від чого залежить зміст.
- Секрет `MISTRAL_API_KEY` задано; змінні репозиторію `MISTRAL_MODEL` і `MISTRAL_REASONING` — ні (типові `mistral-large-latest`, `medium`). Чи є секрет, видно з результату джоби.

### Репозиторій і GitHub

- `add_repo` (push) → `git clone --depth 1` → `register_repo_root` → `npm ci` у фоні. `AGENTS.md` приходить у контекст сам після `register_repo_root` — командою не читати.
- e2e в контейнері: `E2E_CHROME=/opt/pw-browsers/chromium-1243/chrome-linux64/chrome npm run test:e2e`.
- Перед кожним `gh api` — `unset GH_TOKEN`. `gh pr create` не працює — лише REST.
- Пуш гілки з мілкого клону: `git -c push.negotiate=true push -u origin <гілка>`.
- Чужу гілку в клон сесії: `git fetch --depth=50 origin '+refs/heads/X:refs/remotes/origin/X'` — клон із `--depth 1` стежить лише за `main`, тому `git fetch origin X` без повного refspec `origin/X` не створює і не оновлює (Т.39).
- Тег із сесії не створюється (403 від проксі). Артефакти workflow не завантажуються. Сторінки налаштувань Actions (секрети, змінні) через `gh api` — 403: дивитись у браузері власника.
- Хук завершення ходу вимагає закомітити й запушити зміни.
- «Схвалюю» разом зі зміною («… додавай, схвалюю мерж»): зміну робити в тому ж PR новим комітом, в описі PR (`PATCH` перед пушем) назвати, що цей коміт аудитор для мержу не читав, дочекатись чотирьох обов'язкових чеків і мержити, не чекаючи джоби `mistral-audit`, — лише коли власник уже сказав «схвалюю мерж» (клас `approve`); знахідки Mistral на цьому коміті розбирати в документі стану і в записі наступного кроку, як знахідку на останньому коміті (Т.46; ADR-0097). Для класу `auto` порада не діє (спостереження сесії після мержу Т.49; у записі Т.49 цього немає: очікування коштувало ще п'ять звернень і ≈ 17 хв, з них ≈ 8 хв — джоба Mistral).

### Середовище

- Годинник — UTC: до часу додавати 2 години (взимку).
- `tail -2` не працює — писати `tail -n 2`.
- Команда довша за 10 хвилин: передній план обривається на 600 с — чекати кількома командами або циклом до 7 хв, рахуючи разом із ним `sleep` на початку команди. Після пушу обов'язкові чеки і коментар Mistral — окремими умовами: не дочекались коментаря — наступною командою (спостереження сесії після мержу Т.49: `sleep 150` і 38 кіл по 10 с не вклались у 590 с, коментар прийшов через ≈ 12 хв після пушу, і команда пішла у фон). Робоча тека оболонки між командами скидається — кожну команду починати з `cd`.
- Перезапуск середовища вбиває фонові прогони. Файли в `/tmp` і клон переживають перезапуск.
- `Write` інструментом може перетворити послідовність на кшталт `\u200b` у коді на сам невидимий знак — перевіряти `grep` після запису (Т.37). У текстах документів писати назву знака словами, а не його запис (Т.38).

### Ціна сесії

- Найбільша стаття — інструкції й контекст (≈ 50 %): кожен байт виводу інструмента перечитується з кожним наступним зверненням. Менше звернень, довші пакети команд, вивід різати (`cut -c1-300`, `head`, `grep -c`); один `Bash` без `cut` у Т.36 вивів 47 КБ.
- Документи писати одним `Write` або heredoc у `Bash`, правки — `python3` з `assert s.count(a) == 1`; не переписувати файл двічі.
- «Схвалюю» після паузи понад годину коштує перезапису кешу — крок закривати одразу; для класу `auto` паузи немає.
- Веб-пошук дорогий (Т.37: шість звернень — 8 % ціни кроку): шукати коротко і лише потрібне.
- Розклад для порівняння (ефективні одиниці, звернення; Т.45–Т.49 — до запиту «схвалюю»): Т.34 — 1,56 млн, 39; Т.35 — 1,33, 28; Т.36 — 1,03, 21; Т.37 — 2,83, 62 (п'ять прогонів джоби з очікуванням, браузер, два аудитори); Т.38 — 0,79, 15; Т.39 — 2,28, 51 (план і аудит коду Vibe); Т.40 — 0,99, 25; Т.41 — 1,59, 31 (`Read` скрипта на 626 рядків, три невдалі пакетні правки: Prettier переформатував рядки-якорі — якорі брати після форматування або форматувати наприкінці); Т.42 — 0,97, 25; Т.43 — 6,69, 130 (три PR з трьома аудитами в одній сесії, ≈ 1 год 20 хв очікування Vibe з повним контекстом, шість прогонів скриптів поломок з e2e); Т.44 — 5,45, 119 (три сесії: 2,48 / 1,54 / 1,43); Т.45 — 1,13, 30; Т.46 — 1,22, 29; Т.47 — 1,04, 27; Т.48 — 1,21, 31; Т.49 — 0,92, 21. Інструкції й контекст — 43–60 %, `Bash` — 15–34 %, `Read` — 3–9 %, документи проєкту — 4–14 %.
- Найдешевше виходять кроки з довгими пакетами й одним прогоном чеків на коміт (Т.38, Т.49): код першим комітом, `pr-size.sh`, документи другим — число рядків у звіті сходиться з першого разу (Т.47; у Т.46 оцінка з `git diff --numstat` робочого дерева дала 156 проти 155 у `pr-size.sh`, знадобились третій коміт і ще один прогін Mistral); чеки, коментар Mistral і статус прев'ю, коли воно є, — одним циклом з окремими умовами виходу в тій самій команді, що й пуш (Т.40, Т.45).
- Субагента-аудитора (≈ 7–19 хв) чекати двома-трьома циклами до 7 хв із перевіркою чеків і коментаря Mistral у тій самій команді, а не кількома `sleep`: кожен — звернення з повним контекстом (Т.42, Т.45). Довгий скрипт — у фоні з виводом у файл, файл читати циклом очікування (Т.42).
- Серію з кількох PR класу `approve` вести окремими сесіями (або просити «схвалюю серію» одразу в плані): у Т.43 власник відповідав п'ять разів, і кожна пауза — перезапис кешу великого контексту; Т.44 трьома сесіями — 5,45 млн проти 6,69 млн за Т.43 однією. Стан між сесіями — тимчасовий документ прогресу в проєкті claude.ai поруч із документом стану: що змержено, відповіді власника дослівно, що далі, уроки для довідника; наступна сесія починає за запитом «роби Т.N, PR K» без питань наново (Т.44).
- Крок, що закінчується вночі, так і лишати до ранку: «схвалюю» після паузи — мерж, тег і документи трьома зверненнями з перезаписом кешу, це дешевше, ніж тримати сесію (Т.47).
- Знахідку Mistral на останньому коміті (після останнього пушу опис не правиться) розбирати в документі стану і в записі наступного кроку, а не в описі PR (Т.46).
- Документ стану для `project_write` з `local_path` писати в `/mnt/user-data/outputs/`: робоча тека сесії після `register_repo_root` — клон, файл там був би невідстежуваним у репозиторії. Якщо `project_write` двічі не пройшов («перевірка безпеки недоступна») — утретє в тому ж зверненні не повторювати: віддати файл власникові, сказати про це і повторити запис у наступному зверненні (Т.48).
- Дрібниці середовища: `ss` і `rsync` у контейнері немає — зайнятість порту перевіряти `curl`, копію репозиторію робити `cp -r` або `tar` (Т.43, Т.44); годинник контейнера звіряти з часом повідомлення власника — для журналу потрібен київський час (Т.44); індекси рядків для вирізання шматка файла (`sed -n` рахує з 1, `python` — з 0) перевіряти `assert` на вміст меж (Т.42).
- Т.49 (спостереження сесії після мержу Т.49; у записі Т.49 цього немає): інструкції й контекст 55,7 %, `Bash` 22,3 %, документи проєкту 9,4 %, `Read` 7,5 %.
- Т.50 (спостереження сесії після мержу Т.50; у записі Т.50 цього немає): ≈ 1,30 млн, 33 звернення — інструкції й контекст 56,8 %, `Bash` 19,4 %, документи проєкту 7,1 %, `Read` 6,5 %, `Write` 4,4 %. Документи проєкту claude.ai писати інструментом `Write`, а не heredoc у `Bash`: файл із `Bash` `project_write` з `local_path` не приймає без повторного `Read` (два зайві `Read`).
- Цикл очікування рахувати разом із викликами всередині кола (спостереження сесії після мержу Т.50): 40 кіл по 10 с із двома `gh api` на коло не вклались у тайм-аут команди 450 с, і команда пішла у фон — кіл брати ≈ 30 або тайм-аут із запасом над тривалістю циклу.

## Лише для Mistral Vibe Code

- **Мова і стиль:** уся робота і коміти — українською (Conventional Commits українською, без amend/rebase/force-push); відповіді власнику стислі: що зроблено, номер PR, що з чекліста не вдалося і скільки часу зайняв крок. Документи (звіти, довідники) — українською, без питань власнику понад узгоджене.
- **Кирилиця у виводі інструментів:** вивід інструментів екранує не-ASCII як `\uXXXX` — читати файли зручно через `python3` (напр. транслітерацію або `line.encode('unicode_escape')`). Записувати кирилицю можна напряму: `write_file` і bash-heredoc зберігають байти UTF-8 коректно. **Але** в `search_replace` `old_str` із кирилицею може не збігтися — правки робити `python3`-скриптом із `assert s.count(a) == 1` (як радить цей довідник). Уважно до двійникових літер (і/и, в/v, a/а, р/р): при сумніві звіряти через `encode('unicode_escape')` — автор T.39 тричі спіткнувся на «Зінаїда»/«в1».
- **e2e у цьому sandbox (перевірено на T.39):** bundled-браузера спочатку нема — `npx playwright install chromium` кладе `chromium-1254` у `~/.cache/ms-playwright`. Системні lib відсутні і нема root (`sudo` заблоковано) — `apt-get`/`playwright install-deps` не працюють; обхід: скачати .deb-індекс `dists/trixie/main/binary-amd64/Packages.gz` з deb.debian.org, скачати потрібні пакети і `dpkg -x` у `/tmp/debs/root`, запускати з `LD_LIBRARY_PATH=/tmp/debs/root/usr/lib/x86_64-linux-gnu:/tmp/debs/root/lib/x86_64-linux-gnu E2E_CHROME=$HOME/.cache/ms-playwright/chromium-1254/chrome-linux64/chrome npm run test:e2e`. **Без шрифтів** (fonts-dejavu-core + `FONTCONFIG_FILE` із `<dir>/tmp/debs/root/usr/share/fonts</dir>`) текст рендериться з висотою 0 і `expect(...).toBeVisible()` падає навіть на незміненому `main` — перевіряти цю гіпотезу до «чинки» e2e. `/tmp` не переживає перезапуск середовища — підготовку повторити. `vite preview` для ручних вимірів: `npx vite preview --port 4173 --strictPort` (фон, `nohup … &`); «до»-білд — через `git worktree add /tmp/rubezh-before <коміт>` + symlink `node_modules`.
