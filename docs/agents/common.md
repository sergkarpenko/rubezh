# Довідник агента: спільне для всіх кроків

Практичний досвід кроків Т.15–Т.202: команди, пастки, порядок дій. Читати кожному агентові, що виконує крок («роби Т.N»), разом із довідником свого типу кроку: [`ui.md`](ui.md) — вигляд і UX, [`sim.md`](sim.md) — правила ядра, симуляції, баланс.

- **Довідник — не правила.** Правила — `AGENTS.md`, `docs/workflow.md` і ADR. Де довідник розходиться з ними — чинні вони, а довідник виправити тим самим PR (ADR-0096).
- **Для кого.** Розділи без позначки — для будь-якого агента (з Т.87 — сесія Claude, що веде крок, і аудитор `vibe-audit`, ADR-0104). Розділ «Лише для хмарної сесії Claude» наприкінці описує одне середовище; агент в іншому середовищі його пропускає. Досвід кроків Vibe за планом (Т.39–Т.73) — `git fetch --depth=1 origin tag iter-T.73 && git show iter-T.73:docs/agents/common.md` (схему згорнуто, ADR-0100); режим Issues закрито (ADR-0101).
- **Як оновлюється.** Урок про спосіб роботи агент дописує сюди в PR свого кроку (один-два рядки, з номером кроку). Крок, що міняє правило в `AGENTS.md`, `docs/workflow.md` чи ADR, тим самим PR править відповідний рядок довідника. Ревізія (звірка з репозиторієм, прибирання застарілого) — раз на ≈ 10 кроків або коли документ стану сесії Claude перевищує 25 КБ; ревізії — Т.36, Т.40, Т.50, Т.59, Т.68, Т.74, Т.85, Т.95, Т.105, Т.115, Т.127 (без PR), Т.138, Т.148, Т.158, Т.168, Т.177 і Т.203 (технічний блок між фазами), перенесення в репозиторій — Т.38; уроки Т.177–Т.188 перенесено технічним блоком між фазами Т.189, уроки Т.189–Т.202 — технічним блоком Т.203 (ADR-0146 п. 6).
- Звірено з репозиторієм на гілці Т.203 від `main` = `bba5e57` (п18.7 / Т.202, 26.11.2026) скриптом `node scripts/agents-docs-check.mjs` (перед запуском `rm -rf dist`: зібрана тека `dist/` дає дві хибні розбіжності в `sim.md`): шляхи в `…` і посиланнях, номери ADR і назви `npm run …`, згадані в трьох довідниках, існують. Чого скрипт не бачить — числа й факти кроків, команди без `npm run`, шляхи поза верхніми теками робочої теки й `origin/main` (зокрема з друкарською помилкою в першій частині), ігноровані git файли, що лежать на диску: їх ревізія звіряє `grep` по записах кроків.

## Правила репозиторію: що де шукати

- Правила — `AGENTS.md` і `docs/workflow.md`: тематична гілка від свіжого `origin/main` (`<тип>/<крок>-<суть>`), PR у `main`, мерж merge-комітом, Conventional Commits українською, ADR у коміті зі зміною workflow-файлу або `package.json`, ліміт 500 рядків коду, історію не переписувати (без amend, rebase, force-push).
- `docs/workflow.md` (за ADR-0137 п. 6 — ≈ 200–245 КБ між ревізіями, після ревізії Т.177 — ≈ 187 КБ, після Т.203 (записи Т.168–Т.176 і блоки фаз 17 і 18 — в архіві, `faza-17.md`, `faza-18.md`) — ≈ 190 КБ; записи кроків до попередньої ревізії — у `docs/workflow-archive/tehnichni-zadachi-t*.md`; пошук — `git grep -n -E '^- \[x\] \*\*(T|Т)\.N ' docs/workflow-archive/`, Т.39 — з латинською `T`, Т.77 — у `faza-15.md`; форма `[TТ]` з ADR-0137 п. 5 залежить від локалі: за `LC_ALL=POSIX` `git grep` не знаходить запис з кириличною `Т` (Т.120 — 0 збігів), а альтернатива `(T|Т)` знаходить за `POSIX` і `C.UTF-8` (Т.180, аудит; кандидат процесу 165, Т.189) цілком не читати: заголовки — `grep -n '^## \|^### '`, потрібне — `sed -n 'A,Bp'`; рядки там по кілька кілобайтів, тому вивід `grep` завжди різати `| cut -c1-300`.
- Правила гри і тексти UI питати у власника до реалізації (до чотирьох питань за раз, з числами). Решту розвилок вирішувати самому і записувати у звіт.
- Текст UI в питанні власникові — повним рядком, як він буде в грі: зі знаком категорії і номером об'єкта (спостереження сесії після мержу Т.49; у записі Т.49 цього немає: текст обрали без номера зонда, і номер довелось питати вдруге, після аудиту).
- Запис кроку — у `docs/workflow.md`, розділ «Технічні задачі (позафазні)», у PR кроку: `- [x] **Т.N (…): назва.** Мета…` і підпункти «Зроблено», «Аудит», «Виконано», «Урок». Звіт — `docs/reports/tNN-<суть>.md`. PR ревізії переносить старі записи в архів (ADR-0137): спосіб і звірка — пункт «Ревізія» розділу для сесії Claude.
- **Куди йде урок (чотири рівні):** про предмет кроку — у звіт; робоча порада «як зробити» (команда, пастка, порядок дій) — у довідник цієї теки (`docs/agents/`); висновок кроку для всіх агентів — підпунктом «Урок» у записі кроку (класу PR не міняє); у спільний розділ «Уроки» `docs/workflow.md` — лише коли це нове правило, і тоді PR класу `approve`; зміна самих правил — `AGENTS.md` і ADR, лише за рішенням власника. **Урок пишеться в одне місце** (ADR-0023): якщо висновок уже є в записі кроку, у довіднику — лише порада, що з нього випливає, з номером кроку, без повторення тексту.
- Звіт і запис кроку писати так, щоб до аудиту в них не було тверджень про результат аудиту; підпункт «Аудит» і номер PR дописувати другим комітом разом із виправленнями (Т.36).
- Числа й факти про минулий крок у ADR, довіднику чи звіті брати із запису кроку і звіту в репозиторії (`grep` перед тим, як писати), а не з нотаток сесії: обидва аудити Т.40 ловили саме такі розбіжності, одну й ту саму — двічі.
- **Твердження про властивість правила** («витоку немає», симетрія, «байт-у-байт») у плані чи ADR — коротким скриптом до запису, а не міркуванням; споживачів зміненої функції — `grep` усіх викликів, і для необов'язкового параметра теж: `tsc` їх не перелічить (спостереження сесій Т.190 — контрприклад «витоку» знайшов аудитор PR #506 копією `hasLineOfSight`; Т.197 — виклики `advanceTime` у скриптах і дзеркалі e2e).
- **Нове поле, що йде через кілька шарів** (ядро → бій → сторінка → журнал), — тест на кожен шар і навмисна поломка кожного місця до PR (Т.194: тести передачі типу ворога додано лише за аудитом PR #510, факти — у записі п17.5 у `docs/workflow-archive/faza-17.md`).
- **Новий пункт довідника перевіряти тим самим правилом, яке він вводить** (Т.158: факт «Passkey не знадобився» у пункті про sudo mode був узятий із документа стану сесії, а не з запису Т.156 — знайшов аудит PR #471); джерело факту — пункт вище. Історичне твердження «щоразу», «N з N» — звіряти кожен випадок із записом кроку в архіві фази (`docs/workflow-archive/`), а не з уроком-підсумком (Т.166, аудит PR #480: на П11.9 дрейф `README.md` знайшов власник питанням, урок з'явився лише тоді). У довідник для будь-якого агента не писати інструментів, доступних лише сесії Claude (як `add_repo`), і чисел-знімків, що застаріють (кількість обов'язкових чеків — команда, а не число; Т.166).
- **Цитата правила в лапках** (ADR, опис PR, довідник) — лише дослівно; перевірка — `grep -F '<цитата>' <джерело>` (спостереження сесії після мержу Т.176: у «Контексті» ADR-0143 цитата з `common.md` скорочена — знахідка Vibe на останньому коміті PR #490; ADR не оновлюємо).
- **Оновлення документа «за кодом»** (`README.md`, довідка): звіряти з кодом кожне речення, а не лише відомі зміни кроку — у Т.157 аудитор знайшов у `README.md` застарілий опис карти і неповний перелік множника, яких сесія не шукала.
- **Реліз-крок — звірка `README.md` і «Як грати»** (ADR-0135, Т.166): кожне речення обох текстів — проти коду гілки реліз-PR: числа економіки, цін і рахунку — з констант `src/core/` (`economy.ts` та ін.), гарячі клавіші — з `src/ui/input.ts` (`ev.code`) і рядка клавіш у `src/ui/help.ts`, обов'язкові чеки — `gh api repos/sergkarpenko/rubezh/branches/main/protection/required_status_checks --jq '[.contexts[]]'` (потрібен `gh` з правом читання налаштувань гілки), механіки — записи кроків фази в `docs/workflow.md`. Розділ «Звірка README і «Як грати»» в описі реліз-PR — знахідки або «розбіжностей не знайдено» з переліком джерел; без нього аудит — знахідка. Звіряти всі речення, а не диф фази: у п16.6 (Т.188) аудит PR #503 знайшов у `README.md` ще п'ять застарілих тверджень (умова вікна ролі, картка смуги загону, міграція сейву, тег кроку, «0.25 за кожен кредит»). Слово, яке фаза зробила назвою правила, шукати в чинних текстах, де воно мало інший зміст: «Ветеран» — звання з фази 16, а рахунок «50 за живого ветерана» рахував усіх живих (Т.188, рішення власника — «за живого оперативника»). Тим самим проходом — інші тексти для гравця про ту саму механіку: підказки `title` кнопок в `index.html` і ті, що ставить код UI (`grep -n "title" index.html src/ui/*.ts`; спостереження сесії Т.202: підказку «+1 доба» без штурму знайшов аудит PR #518). На старті реліз-кроку — повідомлення власникові «можна перевіряти Pages» (`main` уже на Pages), а питання валідації — разом із питаннями звірки, коли PR готовий: власник перевіряє, поки йде звірка (Т.202).
- **Зміна статусу чека чи правила** — перед комітом `grep` за назвою по `AGENTS.md`, `docs/agents/*.md` і `docs/workflow.md` вище «Поточного статусу проєкту»: застарілі формулювання правити тим самим PR (Т.156; у Т.157 — 0 застарілих).
- Позначення знахідок у звітах: не починати номер з кириличної «З» — «З1» читається як «31».
- «Схвалюю серію» (ADR-0052) у Т.43 спрацювало: третій PR змержено без нового запиту після зелених чеків і аудиту. Умови мержу серії записувати в описі PR дослівно; власник може й відмовити — у Т.44 відповів «Кожен PR окремо» (спостереження сесії після мержу Т.43: у записі Т.43 і його звіті про мерж третього PR без нового запиту не написано).
- Оцінка розміру PR у плані — до аудиту: у Т.44 PR #342 оцінено у 300–380 рядків, перший коміт — 410, після виправлень за аудитом — 478. Для PR з оцінкою понад 350 одразу ділити або закладати ≈ 70 рядків на аудит.

## Легка зміна (ADR-0146, Т.181)

- **Що це:** PR, де `sh scripts/ci-scope.sh --light origin/main HEAD` (скрипти — зі свіжого `main`, як і для класу; `vibe-audit` бере їх із бази PR) друкує `light=true` — рівень не `full` (лише `docs/**`, `scripts/**`, без файлів тестів) і клас `auto` за `pr-class.sh` (без ADR, правил `docs/workflow.md`, скриптів CI і хуків, `AGENTS.md`, `README.md`).
- **Як вести:** без номера кроку, запису в `docs/workflow.md`, рядка `Iter-Tag`, ADR і аудиту (субагента не запускати; `vibe-audit` пропускає аудит сам). Мерж — після зелених обов'язкових чеків тією самою командою API; власникові — один рядок. Окремої сесії не відкривати: покласти в PR найближчого кроку гри або зібрати кілька в один PR на фазу.
- **Усе інше — звичайний крок** за розділами нижче: рішення цього розділу аудит і «схвалюю» для класу `approve` не скасовують.
- **CI за рівнем:** `docs` — `ci` ≈ 20 с (самоперевірка скрипта рівня, крок рівня, перевірка оболонки workflow і порожнє завантаження Codecov для `codecov/patch`); `tools` — ще `tsc` скриптів, лінт, формат; `full` — усе. У джобі `test` окремого `npm test` немає — тести ганяє `test:coverage`. Pre-commit без тестів для рівнів `docs` і `tools`.
- **Рівень — після коміту** (спостереження сесії Т.182): `ci-scope.sh --light origin/main HEAD` рахує закомічене — до коміту він показує рівень без нових файлів. `codecov/patch` на легкому PR (порожнє завантаження) з'являється в check-runs із затримкою — чекати його там. План фази з ADR — завжди `light=false`, клас `approve` (Т.183).
- **Кандидати процесу — заморожено на час фази гри** (ADR-0146 п. 6): записати в перелік, кроком не робити; виняток — поломка, що блокує мерж.

## Власник (рішення 14–15.11.2026)

- Власник — вузьке місце: дій власника на крок має бути якомога менше, і вони не повинні блокувати агента. Зараз на крок — відповіді до реалізації і «схвалюю» (для класу `approve`).
- Відповідь чи «схвалюю» в чаті — зручно: телефон завжди з ним. Незручне все, що прив'язане до конкретної машини чи файлової системи (тека клону, термінал, застосунок на комп'ютері). Нових дій власника, що потребують його комп'ютера, не вводити; дію планувати так, щоб її можна було зробити з телефона (чат, кнопки, посилання на прев'ю чи сторінку GitHub).
- Пристрої: телефон — завжди; iPad Pro — частіше, ніж Mac mini; ноутбука немає. Прев'ю власник найімовірніше відкриє на iPad Pro або телефоні — посилання на прев'ю давати завжди (подробиці — у [`ui.md`](ui.md)).
- Питання про наступний крок ставити разом із проханням «схвалюю» (або з повідомленням про мерж класу `auto`) — одним зверненням.
- Рішення власника «X — окремим PR» означає відкрити цей PR у тому ж кроці, а не перелічити X у звіті: PR-хвіст без рядка тегу, після мержу основного (Т.36).
- Оркестратор, арбітражні чати і правило «не починати, доки є хоч одне питання» — не впроваджуємо.
- Mistral (план Team) оплачений і використовується мало — власник дозволив використовувати його активніше (15.11.2026).
- Локальний клон власника процесу не потрібен; доступу до його теки не просити.

## Старт роботи з кодом

- Свіжий клон → `npm ci` (≈ 1 хв) → прогони «до».
- Локальний чекліст для кроку з кодом: `npx tsc --noEmit` (+ `-p tsconfig.core.json`, `-p tsconfig.e2e.json`, `-p tsconfig.scripts.json`), `npm run lint`, `npm run format:check`, `npm test`, `npm run docs`, `npm run test:e2e`. Після коміту виправлень за аудитом `npx tsc --noEmit` — знову перед пушем, навіть коли змінено лише тест: vitest і pre-commit типів не перевіряють (спостереження сесії після мержу Т.99; факт — у записі Т.100).
- Сценарій e2e без встановленого браузера Playwright: `E2E_CHROME=/шлях/до/chrome npm run test:e2e` (≈ 15 с); з `E2E_URL=…` — проти вже піднятої збірки; `E2E_PORT=<порт>` — власне прев'ю сценарію на іншому порту, типово 4173 (ADR-0144, Т.178).
- Pre-commit хук (`scripts/pre-commit.sh`) ганяє повні тести і перевіряє заборонені файли: `tsconfig.json`, `vite.config.ts`; `package.json` і `.github/workflows/` — лише разом із файлом у `docs/adr/` у тому самому коміті (виняток — зміна самого поля `version`, ADR-0070). Не комітити під час симуляцій. Заборонений файл, який хук блокує механічно (`tsconfig.json`, `vite.config.ts`), — лише з явною згодою власника; коміт із ним — окремий, з `--no-verify`, перевірки хука прогнати вручну (Т.104, прецедент П10.2).

## Розмір і формат

- **Ліміт 500 рахує код, тести й e2e; поза підрахунком — `docs/**`, `*.md`, `assets/**`, бінарні файли, `package-lock.json`.** Число брати лише з `./scripts/pr-size.sh origin/main HEAD`: обидва аргументи обов'язкові, рахує закомічене. У мілкому клоні перед ним `git fetch --depth=50 origin main` — з `--depth=1` після нового коміту в `main` немає спільного предка, з Т.113 скрипт тоді друкує `[FAIL] … немає спільного предка` і виходить з кодом 2; якщо мілка сама гілка (склонована з `--depth=1`, з комітами понад `main`), ще `git fetch --deepen=50` (до Т.113 — тихі «0 рядків» і `[OK]`, ADR-0112). Плановане перевищення — мітка `size-deviation` на PR (ADR-0061).
- **Прогноз розміру PR до коду — з вилученим** (Т.123): `pr-size.sh` рахує додане + вилучене; заміна модуля з таблицями даних (матриці 12 × 12) — сотні вилучених рядків (Т.123: прогноз «до 500», факт 686, після аудиту 773 — мітка `size-deviation` і окремий апрув власника). Рахувати `wc -l` того, що вилучається.

## Клас PR і мерж (ADR-0094; `approve` — ADR-0052)

- Клас дає `scripts/pr-class.sh`: останній рядок виводу — `КЛАС: auto` або `КЛАС: approve`.
  - `auto` — кожен змінений файл із переліку: `docs/**` (крім `docs/adr/**`, `docs/prototypes/**`, файлів тестів і `docs/workflow.md` вище рядка `## Поточний статус проєкту`); `src/**/*.test.ts` і `e2e/**`, додані або змінені; `scripts/**`, крім самого `pr-class.sh`, `pre-commit.sh`, файлів `*.test.*` / `*.spec.*` і кожного скрипта, чиє ім'я згадано в `.github/`, `.husky/`, `package.json` або `scripts/pre-commit.sh` (у базі чи в гілці).
  - `approve` — усе інше: `src/` без тестів, `index.html`, ассети, `AGENTS.md`, `README.md`, ADR, `.github/`, `package.json`, конфігурація, видалений чи перейменований тест, символьне посилання, підмодуль, порожній диф, помилка git.
- **PR класу `auto` агент мержить без «схвалюю», коли виконано все:** клас показала версія скрипта зі свіжого `main` на останньому коміті (`git fetch --depth=50 origin main && git show origin/main:scripts/pr-class.sh > /tmp/pr-class.sh && sh /tmp/pr-class.sh origin/main HEAD`); усі обов'язкові чеки зелені на останньому коміті (перелік — пункт про очікування чеків у розділі «PR і чеки»); аудит пройдено і невиправлених знахідок немає; опис PR має розділ «Аудит» (аудитор, знайдено / підтверджено, що виправлено, що відхилено і чому); у PR немає нового правила гри, тексту UI чи рішення, яке ухвалює власник. Якщо виправлення за аудитом змінило клас — потрібне «схвалюю». **Сумнів = «схвалюю».** Після мержу — повідомити власника: номер PR, клас, підсумок аудиту.
- **Порядок: клас → запис → коміт** (Т.155–Т.157: заглушка причин класу в записі кроку тричі поспіль коштувала зайвого коміту): `git status --short` → `git add <файли кроку>` (не `-A`, якщо в клоні є стенд `proto/` чи тимчасові блоки e2e — їх не комітять) → клас на індексі без коміту — `C=$(git commit-tree "$(git write-tree)" -p HEAD -m tmp) && sh scripts/pr-class.sh origin/main "$C"` (гілка і `HEAD` не рухаються; перевірено в Т.158) → причини класу повним переліком файлів `approve` з виводу скрипта — у запис кроку й опис PR → `git add` запису → коміт. Новий файл у гілці після цього — клас тією самою командою ще раз. Перед мержем `auto` — як і раніше, версія скрипта з `main` на останньому коміті. Причини класу в записі кроку — повний вивід `pr-class.sh` (Т.172). Після коміту — ще раз `sh scripts/pr-class.sh origin/main HEAD`; `git stash` у робочих командах не вживати: у Т.169 він у ланцюгу після `git add -A` сховав усі зміни, відновлено `git stash pop` (спостереження сесії Т.169).
- **Правило процесу в `docs/workflow.md` нижче межі** («Поточний статус проєкту»; його зміна — `auto`) шукати й за приписами без слова «правило»: `m=$(grep -n '^## Поточний статус проєкту' docs/workflow.md | cut -d: -f1); awk -v m="$m" 'NR>m && /перед рядком|переносить|має|слід/ {print NR": "$0}' docs/workflow.md | cut -c1-300` (номери — рядки файла) (Т.174, аудит PR #488: пропущено покажчик «Технічних задач» з приписом про місце нового запису). Наслідок для класу PR доводити пробним комітом у `git worktree` — на гілці і на `main` (`sh scripts/pr-class.sh HEAD~1 HEAD`), а не міркуванням (спостереження сесії Т.174).
- **Без аудиту клас `auto` не діє** (ADR-0094, п. 5) — крім легкої зміни (ADR-0146; розділ «Легка зміна»).
- PR класу `approve` мержити лише після явного «схвалюю» власника в чаті або коментарі PR; «продовжуй» — не апрув; апрув не поширюється на наступні PR, крім явно оголошеної власником серії (ADR-0052). Механічний PR (ADR-0057; після ADR-0093 рядків тегів уже немає) — сам після зелених чеків.
- Мерж через API: `gh api -X PUT repos/sergkarpenko/rubezh/pulls/N/merge -f merge_method=merge -f sha=<повні 40 знаків>`.
- Шлях мержу — саме `…/pulls/N/merge`: `gh api -X PUT …/pulls/N` без `/merge` не мерж, у Т.81 цикл мержу на ньому висів 2 хв (спостереження сесії після мержу Т.81).

## Тег кроку (ADR-0093)

- В описі PR кроку (у серії — лише останнього змістовного PR) рядок `Iter-Tag: iter-T.N` з початку рядка, без відступу. Чек `check` workflow `iter-tag` показує назву до мержу (обов'язковий з Т.156, ADR-0132; зайнята чи недопустима назва або кілька рядків з різними назвами — червоний і блокує мерж: виправити опис `PATCH` і чекати нового прогону `edited` — старий не перезапускати, «Re-run» бере старий опис; помилка запиту про тег — «Re-run»).
- Після мержу тег ставить workflow (≈ 30 с); перевірка: `git ls-remote --tags https://github.com/sergkarpenko/rubezh.git iter-T.N`. Не з'явився — ручний запуск: `gh api -X POST repos/sergkarpenko/rubezh/actions/workflows/iter-tag.yml/dispatches -f ref=main -f "inputs[tag]=iter-T.N" -f "inputs[sha]=<40 знаків>"`. Не допомогло — сказати власнику і виправити запис кроку наступним PR.
- Крок «довідники (`auto`) + ADR-хвіст (`approve`)»: рядок тегу — на першому PR; хвіст відкривати після його мержу від свіжого `main`, на хвіст — окремий аудит (Т.40).
- У записі кроку — «Тег `iter-T.N` — ставить workflow `iter-tag` на merge-коміт PR #N», без sha. Окремий PR рядка тегу не відкривати. Пересунути чи видалити тег може лише власник — назву перевіряти до мержу.
- Якщо власник хоче побачити зміну на основному сайті до тегу — PR без рядка `Iter-Tag`, тег ручним запуском.
- PR з «пX.Y» у назві без рядка `Iter-Tag:` — попередження чека `check` (анотація й підсумок прогону, ADR-0148): дивитись на першому пуші разом із чеками; на перших PR серії і допоміжних PR кроку («docs(workflow): п16.5 — аудит…») воно очікуване.
- Рядок `Iter-Tag: iter-T.N` — у перший опис PR, а не дописом після відкриття (Т.142; повторилось на п16.5 / Т.187 — з п16.6 рядок у чеклісті першого опису, і тег поставився сам).

## PR і чеки

- Створення PR через REST: `gh api repos/sergkarpenko/rubezh/pulls -f title=… -f head=<гілка> -f base=main -F body=@<файл>`. Зміна опису: `gh api -X PATCH repos/sergkarpenko/rubezh/pulls/N -F body=@<файл>` — запускає чеки з типом `edited`; з ADR-0148 `pr-size` і `iter-tag` ідуть чергою без скасування, і `cancelled` буває лише тоді, коли три події (пуш, `PATCH`, мітка) прийшли поспіль: скасовану копію перезапустити — вона блокує мерж (пункт про `add_repo` з push, Т.146; до ADR-0148 — на кожному кроці Т.183–Т.188) (у Т.84 — після кількох правок опису без пушу; спостереження сесії після мержу Т.84); відповідь одразу після пушу може показати старий `head.sha` — голову PR брати з `git ls-remote origin <гілка>` через ≈ 10 с (спостереження сесії після мержу Т.89).
- **Скрипт правки файла опису PR — окремою командою від `PATCH` і пушу** (Т.128): помилка скрипта в ланцюжку `&&` лишала старий опис, а пуш — уже з новим кодом. Відхилення розміру PR (ADR-0061) — і в описі PR, і в записі кроку `docs/workflow.md` (Т.128: `vibe-audit` знайшов, що в записі його немає).
- **Опис PR оновлювати тим самим кроком, що й пуш виправлень: спершу `PATCH` опису, потім пуш.** Джоба `vibe-audit` читає опис через API під час прогону (як `mistral-audit` після Т.41, ADR-0098), тож порядок не ламає аудит; але подію `edited` вона не обробляє — правка опису після прогону в коментарі ніяк не позначається, новий аудит буде лише з наступним пушем (рядок «Опис PR змінено після цього прогону» ставила лише вимкнена `mistral-audit`). Тому після останнього пушу опис не чіпати, а числа останніх прогонів писати в запис кроку і звіт комітом (спостереження сесії після мержу Т.41; у звіті Т.41 цього немає).
- Заголовок коміту набирати однією розкладкою: у Т.89 «поодinці» з латиницею, а `amend` без схвалення заборонено — заголовок лишився. Мерж-коміт бере назву PR у тіло повідомлення, тож назву PR перевіряти окремо (суміш у слові: `grep -P '[а-яіїєґ][a-z]|[a-z][а-яіїєґ]'`) (спостереження сесії після мержу Т.89).
- CI запускається лише для PR у `main`: другий PR складеної серії відкривати після мержу першого. Прогони висять у `queued` без джоб — закрити й знову відкрити PR. Червоний `e2e` на `playwright install` — `rerun-failed-jobs`.
- Очікування чеків: `commits/<sha>/check-runs?filter=latest`; чекати всіх обов'язкових назв — перелік із захисту `main`: `gh api repos/sergkarpenko/rubezh/branches/main/protection/required_status_checks --jq '[.contexts[]]'` (з Т.155 у ньому `shuffle`, ADR-0131, з Т.156 — `check`, ADR-0132; зелені через ≈ 2–5 хв після пушу). `codecov/patch` з'являється на хвилину-дві пізніше за решту: цикл очікування має перевіряти всі назви переліку, а не «всі наявні завершені» (Т.36); на другому коміті PR — і на кілька хвилин пізніше, мерж до нього — 405 (спостереження сесії Т.172; у записі кроку цього немає). `codecov/patch` приходить то check-run'ом, то статусом коміту (`commits/<sha>/statuses`) — цикл шукає назву в обох каналах (спостереження сесій Т.159 і Т.160: у Т.160 цикл з обома каналами — без зайвого очікування). Після мітки `size-deviation` у `check-runs?filter=latest` два записи `pr-size` — новий зелений (подія мітки) і старий червоний з іншого прогону: дивитись на новіший за `started_at` (спостереження сесії під час мержу Т.41). Журнал червоної джоби: `gh api repos/sergkarpenko/rubezh/actions/jobs/<id>/logs | grep -E "×|FAIL|error"`.
- Умова циклу очікування — «серед назв переліку немає `in_progress` / `queued` і є всі»; умова «є рядок без `completed success`» виходить одразу, поки чеки ще не створені (Т.157: три зайві звернення).
- Нова умова в коді без тесту — покрити тестом або прибрати; перед кроком тесту перевірити, що гілка досяжна на чинній сторінці тесту (Т.152: гілку «Граната» сторінка тесту не досягає — на ній немає гранати). Число файлів прогону vitest — з рядка `Test Files` виводу, не з `ls` (Т.150).
- Покриття своїх рядків до пушу: `npx vitest run --coverage --coverage.reporter=json <файли тестів>` і непокриті рядки з `coverage/coverage-final.json`. Червоний `test` лише в `npm run test:coverage` з «Test timed out in 5000ms» — довгому тесту явний тайм-аут (`30_000`) окремим комітом у той самий PR.
- Результат workflow `mutation` — з журналу джоби (`actions/jobs/<id>/logs`, рядки `All files` і ` <файл>.ts`). Колонки таблиці: score загальний, score від покритих, убито, тайм-аут, вижило, без покриття, помилки; перевірка читання — сума п'яти колонок кількостей рядка `All files` дорівнює числу з рядка «Instrumented … with N mutant(s)». ## Скрипти CI і workflow

- Логіку workflow, що пише в репозиторій або вирішує про мерж, писати в скрипті з режимом `--self-test`, у yml — лише виклики. Велику самоперевірку тримати окремим файлом поруч, названим у workflow (тоді його зміна — клас `approve`): так було у вимкненого аудитора `mistral-audit` — `scripts/mistral-audit-selftest.mjs` (ADR-0099, Т.42; заморожено ADR-0104); у чинного `vibe-audit` самоперевірка невелика і лежить у тому самому файлі (`node scripts/audit-vibe-cli.mjs --self-test`). Скрипт, що працює з git, перевіряти в тимчасовому репозиторії (`mktemp -d`, `git init`, `core.hooksPath=/dev/null`), не на заглушці: 64 випадки — ≈ 3 с.
- Самоперевірки чинних `.sh`-скриптів CI — у тих самих файлах: `sh scripts/pr-class.sh --self-test`, `sh scripts/iter-tag.sh --self-test`, з Т.176 — `sh scripts/pr-size.sh --self-test` (ADR-0143; перший крок джоби `pr-size`: випадки в тимчасовому репозиторії, коди 0 / 1 / 2 і рядки виводу). Правка `pr-size.sh` — разом із випадком самоперевірки; змінне оточення джоби (`GITHUB_ACTIONS`, `PR_SIZE_*`) самоперевірка скидає. Збій `git diff` після перевірок ревізій відтворено видаленим об'єктом blob гілки (Т.176). Самоперевірка фільтра — випадок на кожну маску окремо, де інші маски не перекривають результат, і поломка «зняти якір `^`»; у кожному випадку забороняти рядок, якого не має бути у виводі за цим кодом (Т.176, аудит PR #490, коміт `358625e`: пропуск `docs/` перевірявся лише файлами `.md`, а випадок «перевищення в CI» забороняв `[FAIL]` замість `[OK]`). Самоперевірка запускає `$0`, тож поломки до PR — обгорткою `sed` над копією скрипта в /tmp, яку запускає сама копія (спостереження сесії Т.176: так знайдено непокритий шлях — збій `git diff`).
- Помилка команди в умові — не «ні»: `… 2> /dev/null` в `if` робить із будь-якої помилки «не знайдено». Розрізняти коди (`git grep`: 0 — є, 1 — немає, інше — помилка) і в сумніві обирати обережний бік.
- Скрипт не має залежати від поточної теки: у `git grep <ревізія> -- <шлях>` писати `":(top)<шлях>"`. Тип зміни брати з `git diff --raw` (режим 120000 — посилання, 160000 — підмодуль), а не лише з букви статусу. `git/ref/tags/X` для анотованого тегу повертає sha об'єкта тегу, а не коміту. `grep -Eq '^…$'` пропускає багаторядкове значення — відхиляти окремо.
- Навмисні поломки — до аудиту і за переліком гілок логіки, а не «що спало на думку»; агент пише для цього власну обгортку «назва, було, стало» над копією скрипта (у репозиторії готової немає; приклад переліку поломок — `docs/reports/t37/mutations.py`) — 44 поломки за ≈ 2,5 хв.
- Скрипт поломок з e2e (Т.44; урок — у записі кроку): фоновий запуск пише журнал у файл — перед запуском старий журнал видаляти (`rm -f`), інакше цикл очікування читає `EXIT` попереднього прогону. Поломку «прибрати рядок» перевіряти на те, що вона справді прибирає ефект (спостереження першої сесії Т.44 до першого коміту PR #341 — у звіті цього немає: одна поломка в чернетці скрипта не прибирала ефекту і дала зелений e2e). Поломку константи перевіряти даними, де значення розходяться: у PR 3 Т.44 поломку «ціна — число клітинок» перші тести не зловили б — у всіх ціна шляху дорівнювала числу клітинок; це видно, лише коли перелік поломок пишеться за гілками логіки до прогону.

## Залежності, Dependabot і `npm audit` (ADR-0012, ADR-0020, ADR-0134, ADR-0136, ADR-0138)

- **Інша версія Node локально** (Т.170): Node у контейнері сесії — 22, у CI — 26 (ADR-0138). Двійковий файл — з реєстру npm: `npm i --no-save node@26` у тимчасовій теці, далі `PATH=<тека>/node_modules/node/bin:$PATH`; повний набір — у копії клону (`git clone -q <клон> /tmp/rzNN`, `npm ci` під тим самим Node). Реліз-лінії й статус LTS — з nodejs.org (`WebFetch` сторінки «Previous Releases»), дати початку LTS і EOL — з таблиці розкладу github.com/nodejs/release (на «Previous Releases» їх немає; аудит PR #484), а не з пам'яті: у Т.170 кандидат «Node 24» виявився вже Maintenance LTS.
- **Розбір Dependabot-PR** (Т.165; команди — спостереження сесії Т.165): гілки — `git fetch --depth=50 origin '+refs/heads/dependabot/*:refs/remotes/origin/dependabot/*'`, зміни — `git diff origin/main...<гілка> -- package.json`; перевірка — злиттям із поточним `main` у тимчасовій гілці (`git merge`, `npm ci`, повний набір перевірок). Мажор `@types/node` звіряти з `node-version` у workflow (ADR-0134). Оновлення з Dependabot-PR переносити точними версіями (`npm install -D <пакет>@x.y.z`): без точної версії `npm install` бере найновішу в діапазоні, а не версію PR (у Т.165 — fast-check, lint-staged, typescript-eslint новіші за PR; спостереження сесії); lockfile звіряти з головою PR (`git diff <гілка> -- package-lock.json`).
- **`npm audit` для `main`** — у тимчасовій теці з `package.json` і lockfile з `git show origin/main:…` і `npm audit --package-lock-only --json` (Т.165, Т.167). Для кожного пакета (команди — спостереження сесії Т.167) — хто тягне і з яким діапазоном (`packages` у lockfile), `npm view <пакет> dist-tags` і `dependencies.<залежність>` новіших версій. Варіант з `overrides` — `npm install --package-lock-only --ignore-scripts` у тимчасовій теці, потім `npm ci`, `npm run docs` і `npm test` у копії клону (Т.167: так знайдено, що `minimatch` 11 ламає `typedoc`). Назви вразливостей — дослівно з виводу `npm audit` (аудит PR #481).
- «Пакет не вживається» — перевіряти ланцюг статичних імпортів, а не лише виклики: `grep` за назвою знаходить виклик, а модуль може завантажуватись разом із ядром інструмента (Т.167, аудит). Умову перегляду «коли вийде реліз X» звіряти з `npm view X` до запису — вона може бути вже виконана (Т.167, аудит).
- **ADR з варіантами, обраними кнопкою:** відхилений власником варіант — «відхилено власником (кнопкою)», а причина — окремо як аргумент агента: кнопка мотивів не містить (Т.167, аудит PR #481).
- **Факт коду під рішенням ADR — звірити до PR**, а правило ADR, на яке спирається крок (як-от версія сейву чи релізу), читати всіма пунктами, а не першим (спостереження сесії Т.183). Буквальне слово рішення власника, що розходиться з кандидатним пунктом ADR, — питання кнопкою разом зі «схвалюю», а не тихий вибір сесії (Т.185: «лікує й себе»).

- `gh pr view` і `gh pr diff` теж ідуть через GraphQL — у хмарній сесії заборонені; лише `gh api repos/sergkarpenko/rubezh/…` (REST) (спостереження пачки 2 PR Vibe, перенесено в Т.80).
- `gh pr edit` теж падає (403: GraphQL недоступний) — опис PR міняти REST-запитом `PATCH` (пункт «PR і чеки»; з файла JSON — `gh api -X PATCH repos/sergkarpenko/rubezh/pulls/N --input body.json`, де `{"body": …}`). Правка опису перезапускає обов'язкові чеки `pr-size` і `check` (подія `edited`; `check` обов'язковий з Т.156): мерж одразу після неї — 405 «Required status check "pr-size" is queued»; чекати ≈ 1 хв (спостереження сесії Т.64 після останнього пушу; у записі Т.64 цього немає).
- Пуш гілки з мілкого клону: `git -c push.negotiate=true push -u origin <гілка>`.
- **Скрипт правок кількох файлів: спершу всі `assert` і заміни в пам'яті, потім запис усіх файлів** (факти — у записі Т.116): у Т.115 скрипт записав перший файл і впав на `assert` другого — коміт пішов з одним файлом, а повтор з `open(p, 'w')` до перевірки обнулив `docs/workflow.md` (відновлено `git checkout`); у Т.116 помічник заміни, що щоразу перечитував файл з диска, губив попередні заміни того самого файла — помітно лише з `tsc` чи `git diff --stat`. Заміну робити над рядком у пам'яті (`s = rep(s, old, new)`), файл читати один раз.
- Скрипт правки через `str.replace` з `assert`: спершу `grep -n` точного рядка — у Т.110 двічі мимо (у рядку не було зворотних лапок; вирівнювальні пробіли в `README.md`), один зайвий коміт (спостереження сесії після мержу Т.111; факти — у записі Т.112).
- Чужу гілку в клон сесії: `git fetch --depth=50 origin '+refs/heads/X:refs/remotes/origin/X'` — клон із `--depth 1` стежить лише за `main`, тому `git fetch origin X` без повного refspec `origin/X` не створює і не оновлює (Т.39). Так само `git fetch origin <гілка> main` — посилання `origin/<гілка>` лишається старим, і звірка з прототипом іде зі старою ревізією (спостереження сесії після мержу Т.69: зайвий вивід ≈ 12 КБ).
- Гілку на `origin` із сесії не видалити: ні `gh api -X DELETE …/git/refs/heads/…`, ні `git push --delete` проксі не пропускає (403); вбудований браузер у GitHub не увійшов. Спрацювала сторінка `…/branches/all` у Chrome власника: кнопка «Delete branch» видаляє без діалогу і лишає кнопку «Restore» (спостереження сесії після мержу Т.60). Для дій на GitHub, яких не пропускає проксі, — одразу Chrome, без другого браузера і його навички.
- Захист гілки `main` (обов'язкові чеки) із сесії не змінити: `PATCH …/branches/main/protection/required_status_checks` відхиляє класифікатор дій («Destructive or Unwanted Actions», Т.155) — одразу Chrome власника: `Settings → Branches` → правило `main` → «…» → Edit → «Search for status checks» → назва чека (джерело GitHub Actions) → «Save changes»; далі «Confirm access» (sudo mode, Passkey) — підтверджує лише власник, тож питання про Passkey ставити разом із «схвалюю». Після підтвердження GitHub зберігає правило сам — чек додавати вдруге не треба (Т.155). Sudo mode тримається ≈ 1–2 год; якщо GitHub попросить Passkey — питання власникові кнопкою (Т.156). Перевірка — `gh api …/protection/required_status_checks` (`GET` проходить).
- Тег із сесії не створюється (403 від проксі). Артефакти workflow не завантажуються. Сторінки налаштувань Actions (секрети, змінні) через `gh api` — 403: дивитись у браузері власника.
- Мітку репозиторію видалити можна: `gh api -X DELETE repos/sergkarpenko/rubezh/labels/<назва>` проходить (на відміну від гілок і тегів), перевірка — `GET` дає 404 (спостереження сесії після мержу Т.81).
- Хук завершення ходу вимагає закомітити й запушити зміни.
- Тимчасовий локальний коміт для стенда йде в PR, бо історію не переписуємо: у Т.67 коміт з назвою «wip» (не Conventional Commits) лишився в PR #369. Стенд, якому потрібне чисте дерево, робити в окремому `git worktree` або одразу називати коміт за Conventional Commits (спостереження сесії після мержу Т.67).
- «Схвалюю» разом зі зміною («… додавай, схвалюю мерж»): зміну робити в тому ж PR новим комітом, в описі PR (`PATCH` перед пушем) назвати, що цей коміт аудитор для мержу не читав, дочекатись усіх обов'язкових чеків і мержити, не чекаючи джоби `vibe-audit` (до Т.87 — `mistral-audit`), — лише коли власник уже сказав «схвалюю мерж» (клас `approve`); знахідки Mistral на цьому коміті розбирати в документі стану і в записі наступного кроку, як знахідку на останньому коміті (Т.46; ADR-0097). Для класу `auto` порада не діє (спостереження сесії після мержу Т.49; у записі Т.49 цього немає: очікування коштувало ще п'ять звернень і ≈ 17 хв, з них ≈ 8 хв — джоба Mistral).
- Після `add_repo` з push другий коміт у PR запускає `pr-size` двічі — дивитися на успішний; скасована копія блокує мерж (405 «Required status check "pr-size" is cancelled») — перезапустити її: `gh api "repos/sergkarpenko/rubezh/actions/runs?branch=<гілка>"` → id скасованого → `gh api -X POST repos/sergkarpenko/rubezh/actions/runs/<id>/rerun` (≈ 1 хв) (Т.146).

### Середовище

- Годинник — UTC: до часу додавати 2 години (взимку).
- `tail -2` не працює — писати `tail -n 2`.
- Команда довша за 10 хвилин: передній план обривається на 600 с — чекати кількома командами або циклом до 7 хв, рахуючи разом із ним `sleep` на початку команди (спостереження сесії після мержу Т.91: цикл на 20 хв пішов у фон і обірвався перериванням сесії). Після пушу обов'язкові чеки і коментар Mistral — окремими умовами: не дочекались коментаря — наступною командою (спостереження сесії після мержу Т.49: `sleep 150` і 38 кіл по 10 с не вклались у 590 с, коментар прийшов через ≈ 12 хв після пушу, і команда пішла у фон). Робоча тека оболонки між командами скидається — кожну команду починати з `cd`.
- Коли на першому коміті PR коментар Mistral — «Аудиту не було» (API недоступний), на останньому коміті чекати не довше одного циклу і мержити: у Т.62 API був недоступний на обох комітах, три цикли очікування (≈ 25 хв) нічого не дали, а умова мержу класу `auto` від Mistral не залежить (спостереження сесії після мержу Т.62).
- Пуш виправлень за аудитом не тримати заради коментаря Mistral на першому коміті: у Т.59 цикл з умовою «чотири чеки зелені **і** коментар Mistral» коментаря на першому коміті не дочекався (джоба `in_progress` ≥ 9 хв), а на останньому коміті коментар прийшов ≈ 5 хв після пушу (спостереження сесії після мержу Т.59).
- Перезапуск середовища вбиває фонові прогони. Файли в `/tmp` і клон переживають перезапуск. Після перезапуску — `git status --short` у клоні: у Т.58 перезапуск обірвав скрипт поломок і лишив зіпсований `src/main.ts` (`git checkout`; спостереження сесії після мержу Т.58).
- Свої навмисні поломки з e2e не ганяти, поки аудитор працює на тій самій машині: у Т.58 це дало шум — хибно зелений e2e і хибно червоні тести (спостереження сесії після мержу Т.58).
- `Write` інструментом може перетворити послідовність на кшталт `\u200b` у коді на сам невидимий знак — перевіряти `grep` після запису (Т.37). У текстах документів писати назву знака словами, а не його запис (Т.38).
- **`npm test` — у фоні одразу після `npm ci` на кожному кроці, і на кроці лише з документів (спостереження сесії після мержу Т.68; з Т.181 легка зміна — без тестів: хук їх пропускає, ADR-0146):** `AGENTS.md` (принцип 3) винятку для документів не має; у Т.68 звіт казав «`npm test` локально не запускався» — знайшов Mistral на останньому коміті PR #370, тести запущено вже перед мержем (47 файлів, 1189 тестів), а рядок звіту лишився старим. Результат писати у звіт кроку.

- **Фоновий процес — лише `run_in_background` (спостереження сесії після мержу Т.78):** `&` у звичайному виклику `Bash` гине разом з оболонкою (повторилось у Т.114: `npm ci && npm test` через `&` не залишив журналу — повтор з `run_in_background`). Якорі для правок скриптом брати після `prettier --write` — він розгортає довгі рядки (у Т.88 — знову 1 зайвий виклик).
- **Тег і GitHub Release з хмарної сесії (спостереження сесії після мержу Т.77):** тег не пушиться, Release через API заборонено — створювати сторінкою `releases/new?tag=…&target=<sha>&title=…` у Chrome власника (тіло — `javascript_tool` у `textarea[name="release[body]"]`, без `navigate` у `browser_batch`). Лише тег без релізу (`phase15-complete`): пре-реліз тією ж сторінкою з `&prerelease=1`, потім «Delete» на `releases/tag/<тег>` — тег лишається. Бамп версії комітиться з хуком (ADR-0070): «`--no-verify`» у записах П15.6 і v0.6.0 застаріле (Т.188).
- **Пропущений фініш попереднього кроку (спостереження сесії після мержу Т.77):** рішення власника про наступний крок є у файлі пам'яті проєкту claude.ai.
- Вивід прицільного `npx vitest run <файл>` дивитися через `grep -E "Tests |FAIL"` (Т.144).
- Назву тесту з апострофом (`з'являється`) брати в подвійні лапки; `sed` у рядку з одинарними лапками ламає розбір (Т.145). Заміна `sed` типографського апострофа ’ на ' так само ламає рядки коду в одинарних лапках — правити `python3` з `assert` (Т.184).
- `console.log` у тимчасовому тесті vitest видно лише з `--silent=false` (Т.184).

Стан між сесіями — тимчасовий документ прогресу в проєкті claude.ai поруч із документом стану: що змержено, відповіді власника дослівно, що далі, уроки для довідника; наступна сесія починає за запитом «роби Т.N, PR K» без питань наново (Т.44).
- Крок, що закінчується вночі, так і лишати до ранку: «схвалюю» після паузи — мерж, тег і документи трьома зверненнями з перезаписом кешу, це дешевше, ніж тримати сесію (Т.47).
- Знахідку Mistral на останньому коміті (після останнього пушу опис не правиться) розбирати в документі стану і в записі наступного кроку, а не в описі PR (Т.46).
- Документ стану для `project_write` з `local_path` писати в `/mnt/user-data/outputs/`: робоча тека сесії після `register_repo_root` — клон, файл там був би невідстежуваним у репозиторії. Якщо `project_write` двічі не пройшов («перевірка безпеки недоступна») — утретє в тому ж зверненні не повторювати: віддати файл власникові, сказати про це і повторити запис у наступному зверненні (Т.48).
- Дрібниці середовища: `ss` і `rsync` у контейнері немає — зайнятість порту перевіряти `curl`, копію репозиторію робити `cp -r` або `tar` (Т.43, Т.44); годинник контейнера звіряти з часом повідомлення власника — для журналу потрібен київський час (Т.44); індекси рядків для вирізання шматка файла (`sed -n` рахує з 1, `python` — з 0) перевіряти `assert` на вміст меж (Т.42).
- Документи проєкту claude.ai писати інструментом `Write`, а не heredoc у `Bash`: файл із `Bash` `project_write` з `local_path` не приймає без повторного `Read` (Т.50: два зайві `Read`).
- **Очікування виконавця коштувало кроку з Vibe найбільше** (Т.51, Т.58: контекст перечитується кожним зверненням циклу опитування) — тому в режимі Issues сесія запускає Vibe і не чекає (ADR-0100).
- Коментар Mistral на попередньому PR, якого не дочекались до мержу, читати на старті наступного кроку одним `gh api` разом з іншими командами (спостереження сесії після мержу Т.53).
- Цикл очікування рахувати разом із викликами всередині кола (спостереження сесії після мержу Т.50): 40 кіл по 10 с із двома `gh api` на коло не вклались у тайм-аут команди 450 с, і команда пішла у фон — кіл брати ≈ 30 або тайм-аут із запасом над тривалістю циклу.
- `git commit` без обрізання виводу друкує ≈ 100 рядків хука pre-commit — комітити з `> /tmp/commit.log 2>&1 && git log --oneline -1 || tail -n 20 /tmp/commit.log` (Т.56; з `;` замість `&&` падіння хука не видно — `git log` покаже попередній коміт); прапорець `-q` вивід хука не глушить (спостереження сесії після мержу Т.67); у клоні з хуком він може йти понад 2 хв — тайм-аут команди із запасом (спостереження сесії після мержу залишків Т.58).
- Після `prettier --write` інструмент `Write` відмовляє («файл змінено після читання») — такий файл у клоні далі правити не `Write`, а скриптом (порада вище в цьому розділі); `Write` лишати для нових файлів і документів проєкту (спостереження сесії після мержу Т.54).
- Історія правок опису PR із сесії недоступна (GraphQL закрито) — первісний опис PR виконавця зберігати файлом одразу після відкриття PR, якщо з ним треба буде порівнювати (спостереження сесії після мержу Т.54).
- `prettier` розгортає масив аргументів, довший за ширину рядка, на рядок кожен — у кроці біля ліміту 500 виносити сталі частини в константу; `git grep` з діапазоном кирилиці залежить від локалі — текст бази брати цілим (`git grep -hI -e ''`) і розбирати в Node (спостереження сесії після мержу Т.54).
- Годинник контейнера може показувати UTC з позначкою «Europe» — звіряти з часом повідомлення власника, а не з назвою часового поясу (спостереження сесії після мержу Т.57).
- Твердження «файл після дати X не мінявся» з мілкого клону перевіряти межею історії (`git log --reverse | head -1`): клон на 60 комітів закінчувався після Т.18, і «після 11.11» аудитор слушно назвав непідтвердженим (спостереження сесії після мержу Т.57).
