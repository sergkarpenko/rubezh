# Довідник агента: правила ядра, симуляції, аналіз балансу

Читати разом із [`common.md`](common.md) — там же про те, що таке довідник, для кого він і як оновлюється (ADR-0096). Уроки цього типу кроків дописувати сюди в PR кроку. Числа балансу і факти кроків Т.18–Т.29 — у звітах `docs/reports/t18-…` – `t29-…`.

Шляхи на кшталт `<тека>` — будь-яка робоча тека поза клоном; у прикладах `<клон>` — корінь клону репозиторію.

## Порядок кроку

- **Крок «probe + рішення + зміна» одним заходом (Т.29, 90 хв до зеленого PR):** базові прогони probe → прогноз у файл → 160 сідів на всі варіанти → 480 на основні → питання власнику з числами → «до» `sim-p11.8` і код → «після» → `--verify` → повні тести → коміт → PR.
- **Крок «зміна правила + симуляції»:** «до» — `git worktree add --detach <тека>/before HEAD` + символьне посилання на `node_modules`, два процеси з тек `b1`/`b2` (`--root <тека>/before`; у кожній теці `mkdir dist`); «після» — з тек `a1`/`a2`. Повні тести й коміт — коли симуляції скінчились.
- Прогноз записувати у файл до першого вимірювання і звіряти у звіті.
- Перед тунінгом — один кандидат «у зворотний бік». Зміна правила, що бере участь у кожному бою: 480 сідів і парний тест.
- Число, що рахує партії, які дожили до кінця, перевіряти ботом, який нічого не робить. **Частка виграних партій бота — не вимірювач балансу** (Т.20).
- Кожне несподіване число перевіряти здоровим глуздом до висновків. Варіант, що міняє спільний стан процесу, перевіряти в порядку прогону.
- **Політика без науки не змінилась — перевіряти `cmp` двох CSV** (байт-у-байт).
- **Зменшення порога в каталозі (Т.28):** перевірити код на стані зі старого сейва, де накопичене вже перевищує новий поріг.
- Після зміни циклу `simulateParty` оновити `trace-party.ts` і `probe-t23.ts` і прогнати `--verify`. `grep -c` по журналу `--verify` — шукати `^розбіжність`.
- **Нова поведінка бота за опцією (Т.76):** опція без значення — бот байт-у-байт як був; доказ — `cmp` CSV `sim-p11.8.ts --seeds 40` з `main` (окремий `git worktree`) і з гілки, плюс тест «порожня політика — той самий лог». Бот, що став поводитись «обережніше», не означає кращу партію: міряти рахунок і гроші, а не загиблих.

## Фонові прогони

- **Не чіпати файли ядра, поки стартує фоновий прогін (Т.29).** Поломку правила робити до запуску фонових прогонів або в копії.
- `probe-t23.ts` пише CSV лише наприкінці: обірваний прогін не лишає нічого (Т.27).
- Pre-commit хук ганяє повні тести — не комітити під час симуляцій.
- **Час probe на «легкому» (два процеси, два ядра):** клітинка 160 сідів ≈ 45 с, 480 сідів ≈ 2,5 хв. На «нормі» клітинка 480 ≈ 5 хв і більше.
- **Час `sim-p11.8` (480 сідів, усі пресети):** ≈ 13 хв на політику; поруч із двома процесами probe — ≈ 17 хв. `trace-party --verify` + `probe-t23 --verify` на одному пресеті разом — ≈ 10–12 хв.

## Команди

- Симуляції `sim-p11.8.ts`: `cd <тека-1> && node <клон>/scripts/run-ts.mjs <клон>/scripts/sim-p11.8.ts -- --seeds 480 --policies default` (або `science`). Готовність — за файлом `dist/p11.8-parties.csv` у теці запуску. Розділ «Числа балансу» — з Т.21: доба «без повного загону» — наприкінці доби боєготових менше трьох; ростер = живі разом із лікарнею.
- **Probe політик:** `node scripts/run-ts.mjs scripts/probe-t23.ts -- --variants <список через кому> --presets норма --seeds 480 --out /tmp/x.csv > /tmp/x.log`. Частини варіанта через «+»: `none`, `sciN`, `afterN`, `resN`, `rh`, `rh2`, `p:armor.optics`, `fire`, `nofire`, `done:armor`, `gift`, `g:armor`, `c:armor=30`, `pc:`, `pp:`, `keep`, `eqN`. `trace-party.ts` пресет — `--preset`, `probe-t23.ts` — `--presets`.
- **Probe каталогу:** ціни предметів і очки протоколів — частинами варіанта (`c:armor=30`, `pc:armor=48`, `pp:armor=14`; значення «норми», пресет множить сам).
- **Probe констант-`const` через змінні середовища (Т.29):** копія `cp -r src scripts package.json tsconfig*.json vite.config.ts <тека>/probeNN` + символьне посилання на `node_modules`; `sed` робить з константи `Number(process.env.X ?? <чинне>)`; звірка копії — базовий варіант без змінних дає той самий CSV. Черга: файл рядків `ім'я|змінні|варіант` і власний скрипт-обгортка одного прогону (у репозиторії його немає), запущений як `xargs -P 2 -I{} <обгортка> "{}" <сіди> <тека>`.
- Скрипти `scripts/*.ts` запускає `node scripts/run-ts.mjs <скрипт.ts> [аргументи]` (Т.103: `runnerImport` з `vite`, без залежностей); `npx -y vite-node` щоразу завантажував пакет. Прогін з іншої теки пише `dist/` у теку запуску.
- **Probe політики евакуації бота (Т.76):** `node scripts/run-ts.mjs scripts/sim-t76.ts -- --variants none,w50,last1 --seeds 120 --out /tmp/t76/a.csv`, зведення — `--summary a.csv,b.csv`. Клітинка «варіант × пресет» на 120 сідів — ≈ 1 хв (два процеси на двох ядрах). Варіант з евакуацією міняє кількість місій — порівнювати рахунок попарно за сідом з `none`.

## Перевірка тестів

- **Поломка правила для перевірки тестів:** `cp` файла ядра в `/tmp`, `sed` рядка, прицільні тести, `cp` назад, `git diff --stat`.
- Прицільний мутаційний прогін: `rm -rf /tmp/rubezh-stryker && npx stryker run --mutate "src/core/<файл>.ts:<від>-<до>" --reporters clear-text` — під хвилину; не разом із симуляціями.
- Перелік не виявлених мутантів: той самий прогін із `--reporters json,clear-text` (кілька файлів — через кому в `--mutate`; два файли на 436 мутантів — 2 хв 45 с) і розбір `dist/mutation/mutation.json` у Node: `files[<шлях>].mutants` зі `status` `Survived` або `NoCoverage` (`Timeout` — виявлений), `location.start.line`, `mutatorName`, `replacement`. Теку `dist/` після розбору видалити: вона не комітиться, але з нею `node scripts/agents-docs-check.mjs` дає хибну розбіжність на шляху `dist/…` у цьому довіднику. У Т.57 числа прицільного прогону по `intercept-bot.ts` і `map.ts` збіглися з рядками цих файлів у повному прогоні на раннері. У Т.136 — так само для `render-core.ts` (807 мутантів за 1 хв 29 с), але `intercept-bot.ts` і `map.ts` розійшлись на один мутант «тайм-аут ↔ вижив»: прицільний прогін відтворює число файла з точністю до плавання тайм-аутів.
- Прочитати повний прогін за розкладом: таблиця — з журналу джоби (`gh api repos/sergkarpenko/rubezh/actions/jobs/<id>/logs`, рядок `% Mutation score` і 19 рядків за ним (`grep -A19`); id джоби — `gh api …/actions/runs/<run>/jobs`); артефакт `mutation-report` з хмарної сесії не завантажується (сховище артефактів поза проксі) — перелік мутантів брати прицільним прогоном; шість файлів ботів, ШІ, мапи й сейву — ≈ 10 хв на двох процесах. Новий код від старого — `git blame` рядків мутантів відносно коміту попереднього прогону.
- Property-тести (`fast-check` 4.10, ADR-0085; поза мутаційним прогоном): нова дія ядра — нова команда в генераторі; нове правило про стан — твердження у `broken`; правило про перехід — `expect` у команді. Правило шару відображення, яке property-тест повторює вручну (`tick` ↔ `partyTick`), міняти в обох місцях.
- **Property-тест з іншим сідом:** `sed` рядка `const RUN = { seed: 20261111, numRuns: 100 }` у копію, `vitest run src/party.property.test.ts --testTimeout 600000`, файл відновити.
- Довгі тести повних партій — з явним тайм-аутом (`30_000`).
- Тести із зафіксованими значеннями: сід 49 (2 техноманти, броня, 7 виготовлено, 41 екіпірування, зарплата 140, 45 місій, 39 виграно); спіраль зарплат — сід 54; `save-compat` — гроші 3 795.
