# ADR-0041: Уточнення AI-native SDLC процесу

**Статус:** Proposed  
**Дата:** 2026-10-15  
**Автор:** Vibe Code  
**Замінює:** -  
**Суперечить:** -  

---

## Контекст

Попередні сесії показали, що існували порушення процесу:
- Спроба рефакторингу замість розробки нових фіч (порушення ADR-0023, ADR-0030)
- Нечіткий поділ ролей між Vibe Work та Vibe Code
- ADR 0037-0040 були створені, але не закомічені в репозиторій
- Відсутність чіткого механізму запуску нових сесій

Цей ADR уточнює та формалізує AI-native SDLC процес відповідно до вимог користувача.

---

## Рішення

### 1. Розподіл ролей

**Vibe Work** (планування та дизайн):
- Аналіз вимог та створення EARS-планів (ADR-0023)
- Створення нових ADR (архітектурні рішення)
- Планування фіч та етапів розробки
- **Не виконує** кодування

**Vibe Code** (виконання):
- Реалізація задатків згідно планів Vibe Work
- Написання тестів
- Виправлення багів
- **Не планує** нові фічі (тільки реалізує наявні плани)

### 2. Репозиторій як єдине джерело правди

- Всі рішення, плани та ADR **обов'язково** документуються в репозиторії
- Ніяких зовнішніх документів чи нотаток
- Кожна сесія починається з `git pull` для синхронізації

### 3. Формат промптів для нових сесій

- **Формат:** `pX.Y` де X = номер фази, Y = номер кроку в фазі
- Приклади: `p8.1`, `p8.2`, `p8.3`
- Після надходження промпту в форматі `pX.Y`, агенти (Vibe Work → Vibe Code) **автоматично** починають роботу над етапом
- Не потрібно додаткових інструкцій

### 4. Правила роботи з ADR

- **Створюємо нові ADR**, ніколи не оновлюємо існуючі
- Нумерація ADR повинна бути унікальною та не перетинатися (0000-0040 вже зайнято)
- Кожен ADR містить: статус, дату, автора, контекст, рішення, наслідки
- ADR в статусі "Proposed" можуть бути закомічені в репозиторій

### 5. Потік розробки

1. Користувач надає промпт у форматі `pX.Y`
2. Vibe Work аналізує поточний стан репозиторію (`git pull`)
3. Vibe Work створює/оновлює плани в `workflow.md` та `AGENTS.md`
4. Vibe Work створює нові ADR за необхідності
5. Vibe Code реалізує фічу згідно планів
6. Всі зміни комітяться та пушаться в GitHub
7. Після merge в main ставиться тег `iter-X.Y`

### 6. Заборона на рефакторинг

- В нових сесіях **заборонено** робити рефакторинг
- Дозволено лише розробку **нових фіч**
- Рефакторинг можливий лише як окрема фаза з чітким планом

## Наслідки

### Переваги

1. **Чіткий поділ ролей:** Vibe Work планує, Vibe Code виконує
2. **Передбачуваність:** Кожен знає, що робити в кожній сесії
3. **Прозорість:** Всі рішення документовані в репозиторії
4. **Автоматизація:** Промпт `pX.Y` автоматично запускає процес

### Недоліки

1. **Жорсткість процесу:** Потрібно суворо дотримуватися формату
2. **Додатковий час:** Документування займає час
3. **Навчання:** Потрібно звикнути до нового процесу

### Ризики

1. **Порушення процесу:** Агенти можуть забувати про правила
2. **Несинхронізовані дані:** Якщо не робити `git pull` на початку
3. **Дублювання ADR:** Можливе випадкове дублювання номерів

## Реалізація

### Крок 1: Документування процесу

Створити цей ADR та оновити:
- `docs/workflow.md` - додати секцію про AI-native SDLC
- `AGENTS.md` - додати підсекцію про розподіл ролей

### Крок 2: Валідація існуючих ADR

Перевірити, що ADR 0037-0040:
- Вірно пронумеровані (не перетинаються з існуючими)
- Містять всі обов'язкові поля
- Відповідають шаблону

### Крок 3: Коміт зміни

Закомітити всі ADR (0037-0041) та оновлені файли:
```bash
git add docs/adr/0037-modular-ui-architecture.md
git add docs/adr/0038-core-separation-render-bot.md
git add docs/adr/0039-require-two-approvals.md
git add docs/adr/0040-pr-size-validation-action.md
git add docs/adr/0041-ai-native-sdlc-process.md
git add docs/workflow.md
git add AGENTS.md
git commit -m "docs(adr): add ADR-0037 to ADR-0041 and update workflow docs"
```
