# ADR-0039: Вимога двох схвалень для merge

**Статус:** accepted  
**Дата:** 2026-10-15  
**Автор:** Vibe Code  
**Заміняє:** ADR-0028  
**Суперечить:** -  

---

## Контекст

Поточна конфігурація (ADR-0028) дозволяє merge PR після одного схвалення (`"схвалює"`). Це призводить до:

1. **Підвищеного ризику помилок:** Одне схвалення може бути недостатнім для виявлення всіх проблем
2. **Нерівномірного навантаження:** Один рев'юер може бути перевантажений
3. **Зниження якості коду:** Менше очей = менше виявлених проблем

Згідно з кращими практиками (Google, Microsoft, Netflix):
- Мінімум **2 схвалення** для злиття коду
- Для критичних змін (архітектура, безпека) — 3+ схвалення

---

## Рішення

Оновити вимоги до merge PR:

### Нове правило
**Мінімум 2 схвалення** потрібно для merge PR до `main`.

### Винятки
1. **Документація:** PR, що містять тільки зміни в `docs/` або `README.md` — 1 схвалення
2. **Dependabot:** Автоматичні оновлення залежностей — 1 схвалення
3. **Гарячі виправлення:** Критичні баги, що блокуютьроботу — 1 схвалення (з подальшим рев'ю)

### Реалізація

#### 1. Оновлення GitHub Branch Protection

Влаштувати в GitHub → Settings → Branches → Branch protection rules для `main`:

```yaml
# Вимоги для main
- Require status checks to pass before merging: ✅
- Include administrators: ✅
- Require pull request reviews before merging: ✅
- Require approvals: 2 ✅ (замість 1)
- Dismiss stale pull request approvals when new commits are pushed: ✅
- Require review from Code Owners: ❌ (не обов'язково)
```

#### 2. Оновлення workflow

Оновити `docs/workflow.md`:
- Додати вимогу про 2 схвалення в розділ "Мердж (merge-комітом)"
- Додати винятки для документації та Dependabot

#### 3. Оновлення AGENTS.md

Оновити таблицю в розділі "Мережеві дії":
```markdown
| Дія | Вимоги |
|-----|--------|
| Merge PR до main | 2 схвалення (1 для docs/Dependabot) |
```

## Наслідки

### Переваги

1. **Вища якість коду:** Два рев'юери виявлять більше помилок
2. **Краще розподілення навантаження:** Навантаження розподіляється між декількома рев'юерами
3. **Зменшення ризиків:** Меньше шансів, що критичні помилки потраплять в main
4. **Краще навчання:** Молодші розробники вчаться у досвідчених колег

### Недоліки

1. **Сповільнення процесу:** Потрібно чекати двох схвалень
2. **Блокування:** Якщо один рев'юер недоступний, PR може застрягти
3. **Додатковий тиск:** Рев'юери можуть відчувати тиск через збільшене навантаження

### Ризики

1. **Затримка релізів:** Довше очікування merge
2. **Конфлікти:** Більше часу між схваленнями = більший ризик конфліктів
3. **Втома рев'юерів:** Збільшене навантаження може призвести до зниження якості рев'ю

## Альтернативи

### Альтернатива 1: Гнучкі правила

Встановити різну кількість схвалень залежно від типу PR:
- **Feat/Refactor:** 2 схвалення
- **Fix:** 1 схвалення (якщо не критичний)
- **Docs/Chore:** 1 схвалення

**Плюси:** Гнучкість, швидке просування дрібних змін
**Мінуси:** Складніше керування, можливість зловживань

### Альтернатива 2: Code Owners

Встановити вимогу схвалення від Code Owner для певних файлів:
- `src/core/*` — вимагає схвалення від архітектора
- `*.ts` — вимагає схвалення від тимового ліда

**Плюси:** Експерти перевіряють свій код
**Мінуси:** Складніше налаштування, може блокувати PR

### Альтернатива 3: 3 схвалення для всіх PR

**Плюси:** Ще вища якість
**Мінуси:** Занадто довго, нереалістично для невеликих команд
