# 0145. Сценарій e2e телефона пальцем — окремий контекст з `hasTouch` і `isMobile`

- Статус: accepted (мерж PR власником = «схвалюю» — конвенція ADR-0052)
- Дата: 2026-11-25
- Доповнює: ADR-0080 (сценарій приймання, `e2e/acceptance.scenario.ts`), ADR-0082 (чек `e2e` обов'язковий), ADR-0119 (смуга загону), ADR-0140 (кореневі конфіги Playwright), ADR-0018 (workflow без змін)
- Автор: Claude Code (рішення власника 25.11.2026 на фініші Т.178 кнопкою — «Схвалюю; тач у e2e (52) (Рекомендовано)»; кандидат процесу 52)

## Контекст

- Звірка на `main` = `a740921`: у `playwright.e2e.config.ts` один проєкт `chromium` без `hasTouch` і `isMobile`; сценарії телефона (Т.120: 390 × 844, 320 × 568, 844 × 390, 568 × 320; меню на ворогові на 390 × 844, Т.131) міняють лише розмір вікна через `setViewportSize`. Єдиний тап по канві на телефоні — гейт Т.143 на 844 × 390 — іде допоміжною `tap()` сценарію, тобто `canvas.click` мишею. Сторінка в цих гейтах бачить мишу з наведенням: `(hover: hover)`, `(pointer: fine)`, `navigator.maxTouchPoints` = 0.
- Канва бою слухає `click`, `mousemove`, `mouseleave` (`src/main.ts`); на телефоні ці події — сумісні події миші, які браузер шле після дотику. Поломку, що зачіпає лише дотик (наприклад, `preventDefault` на `touchend` гасить сумісний `click`), мишачі гейти не бачать.
- `index.html` має сім блоків `@media (hover: hover)` — на тачі стилі наведення вимкнено; e2e цього стану сторінки не відкривав.

## Рішення

1. Сценарій телефона пальцем — окремий тест у `e2e/acceptance.scenario.ts` у блоці `test.describe` з `test.use({ hasTouch: true, isMobile: true, viewport: { width: 844, height: 390 } })`: власний контекст браузера з емуляцією дотику на горизонтальному телефоні. Тапи — `locator.tap()` (події дотику), а не `click`.
2. Перевірки тесту: сторінка бачить телефон (`(hover: none)`, `(pointer: coarse)`, `maxTouchPoints` > 0, ширина 844); партія, тіки й запуск місії — тапами; тап пальцем по бійцю вибирає його (картка смуги загону = рядок дзеркала); перший тап по клітинці — лише прев'ю «Шлях: N AP» (сумісний `mousemove` перед кліком не робить перший тап ходом), другий — хід, AP бійця — як у дзеркалі; тап по картці смуги загону вибирає іншого бійця; помилок сторінки немає.
3. Гейт Т.143 (тап мишею на 844 × 390) і решта сценаріїв лишаються як є; `playwright.e2e.config.ts`, workflow і код гри без змін.

## Наслідки

- Перевірка (Т.179): тест зелений (≈ 6 с); збірка з поломкою «`touchend` → `preventDefault` на канві» (`E2E_URL` на 4175) — тест червоний на виборі бійця пальцем, сценарій ADR-0030 з гейтом Т.143 мишею на тій самій збірці — зелений.
- e2e — 7 сценаріїв замість 6, у CI — та сама джоба `e2e`, той самий проєкт `chromium` (контекст тесту бере `use` з блоку).
- Інші розміри телефона пальцем (390 × 844, 320 × 568), меню на ворогові і зведені режими пальцем — за потреби, тим самим блоком.
- Клас PR — за `scripts/pr-class.sh` (сценарій e2e і документи; рішення про спосіб — сесії, крок обрав власник).
- Відхилено: другий проєкт Playwright у конфігу (`hasTouch`, `isMobile`, вибір тестів міткою, `grepInvert` для `chromium`) — зміна кореневого конфіга і правило розподілу тестів між проєктами заради одного тесту, а `test.use` дає той самий контекст; `hasTouch` для всього сценарію ADR-0030 — змінює медіазапити (`hover: none`) і поведінку настільних гейтів (наведення, прев'ю шляху мишею), які мають лишатися мишачими; `page.touchscreen.tap` у чинному кроці Т.143 — потребує `hasTouch` у контексті, якого там немає (`setViewportSize` тач не вмикає); `dispatchEvent` подій дотику вручну — оминає сумісні події браузера, які і є предметом перевірки.
