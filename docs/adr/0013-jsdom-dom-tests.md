# 0013. DOM-тести UI-шару (main.ts) через jsdom

- Статус: accepted
- Дата: 2026-10-13

**Контекст.** П7 (юніт-тести `main.ts`) реалізовано лише для чистих функцій: node-середовище vitest без DOM не дозволяє тестувати UI-керування (обробники кнопок, журнал, стани панелей). Залежності додавати було неможливо (до ADR-0012). Розглянуті альтернативи: happy-dom (легший, але менш сумісний — ризиковано дляMouseEvent/innerHTML-флоу); Playwright/Cypress (реальний браузер — найточніше, але важка інфраструктура і окремий runner, не вписується у `npm test`; кандидат на Фазу 3); взагалі без DOM-тестів (UI-флоу лишається покритим лише візуальною валідацією людини).

**Рішення.** Ми використовуємо **jsdom** як devDependency: per-file середовище vitest через docblock `// @vitest-environment jsdom` (без змін у конфігурації збірки). Тест `src/main.ui.test.ts` інжектить у jsdom реальну розмітку `index.html` (читання файлу — без дублювання структури, дрейф розмітки ловиться тестом), підмінює `HTMLCanvasElement.getContext` no-op заглушкою (jsdom без нативного `canvas` не рендерить 2D — ядро малювання покривається візуальною валідацією) і перевіряє UI-флоу живими кліками: час → радар → місія → бій → результат.

**Наслідки.** UI-керування (`main.ts`) покривається автоматичними тестами разом із `npm test`; візуальний вигляд далі валідується людиною в прев'ю. jsdom — лише devDependency, у браузерний бандл не потрапляє (вага збірки не змінюється). Тести детерміновані (сіди геосцени). Обмеження: канва-малювання не перевіряється (заглушка); реальну графіку і взаємодію зрізу залишаємо людині/майбутньому Playwright.
