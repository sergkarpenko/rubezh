# 0098. Аудитор Mistral отримує контекст: опис PR через API, довідники, записи кроків, ADR і результати чеків

- Статус: accepted (мерж PR власником = «схвалюю» — конвенція ADR-0018/0052)
- Дата: 2026-11-15
- Частково Supersedes: ADR-0095 (п. 1 — перелік подій workflow: додано `edited`; п. 3 — що бачить аудитор; п. 5 — зміст коментаря: код опису, рядок-мітка, рядок про контекст, і коментар тепер оновлюється також без пушу — міткою; решта пунктів чинна)
- Доповнює: ADR-0097 (два аудитори PR — постійно; роль аудиторів без змін); ADR-0018 (зміна workflow-файлу — з ADR)
- Автор: Claude Code (рішення власника 2026-11-15, текстом у чаті після Т.40: «Т.41 — доопрацювання аудитора Mistral (кандидат 34)»; задача Т.41)

## Контекст

За ADR-0095 аудитор Mistral бачить `AGENTS.md` з бази PR, назву й опис PR і диф. На кроках Т.37–Т.40 цього бракувало (записи кроків у `docs/workflow.md`, звіти `docs/reports/t37-mistral-audit.md` і `t40-session-docs-revision.md`):

- **Опис PR із події пушу.** Джоба читала опис, яким він був у момент пушу. Сесія править опис через API окремо від пушу, тож аудитор звіряв диф зі старим описом (Т.37).
- **Немає тексту, на який посилається PR.** Записів кроків, ADR і довідників `docs/agents/` аудитор не бачив і відновлював факти про минулі кроки з контексту дифа (Т.40).
- **Немає результатів чеків.** Аудитор не знав, чи пройшли тести, e2e і перевірка розміру на коміті, який читає.

Окремо: опис PR, змінений після прогону, лишав у PR коментар аудитора без жодного знаку, що він стосується попереднього опису.

## Рішення

1. **Опис PR — через API в момент прогону.** Скрипт читає назву й опис запитом `GET /repos/{repo}/pulls/{N}` на початку роботи. Якщо API не відповів — бере опис із події і пише про це в коментарі.
2. **Контекст із бази PR** (базу PR змінити не може; змінене самим PR видно в дифі):
   - довідники `docs/agents/*.md` — разом до 60 000 знаків;
   - записи кроків із `docs/workflow.md`, згаданих у назві, описі або доданих рядках дифа (`Т.N`, літера «Т» кирилична чи латинська), — цілком, до 5 записів у порядку першої згадки, кожен до 12 000 знаків;
   - звіти цих кроків (`docs/reports/tNN-*.md`) — до 2, кожен до 12 000 знаків; звіт кроку самого PR — новий файл, він у дифі;
   - згадані ADR (`ADR-NNNN`) — до 6, кожен до 10 000 знаків;
   - порядок згадок: спершу з назви й опису PR, далі з доданих рядків документів (`docs/`, `*.md`), далі з доданих рядків коду; у дифі частіші згадки — першими. Так у межі не потрапляють номери з тестових даних коду поперед тих, про які йдеться в PR;
   - обрізане за межею названо в коментарі аудитора;
   - перелік згаданого, чого в базі немає: «запису кроку немає», «ADR доданий цим PR», «ADR немає ні в базі, ні в дифі».
3. **Результати чеків коміту.** Перед запитом до моделі скрипт опитує `check-runs` коміту раз на 20 секунд, доки кожен з обов'язкових чеків `main` — `test`, `e2e`, `pr-size`, `codecov/patch` — з'явиться і завершиться, але не довше 5 хвилин (`codecov/patch` з'являється пізніше за решту, а пропущена джоба теж має стан «завершена», тому число чеків не годиться за умову); далі передає, що є (незавершений чек — зі станом). Збій API чеків аудиту не зупиняє. Workflow отримує дозвіл `checks: read`.
4. **Мітка «опис змінено після прогону».** Коментар аудитора несе прихований код опису (перші 12 знаків SHA-256 від назви й опису). Перед записом коментаря скрипт читає опис ще раз і, якщо код інший, одразу ставить рядок-мітку. Workflow реагує і на подію `edited`: така джоба моделі не викликає, а порівнює код у наявному коментарі з поточним описом і ставить або знімає мітку. Правка опису має власну групу `concurrency` і не скасовує аудит, що йде. Дві джоби можуть писати коментар одночасно, тому: джоба `edited` перед записом читає коментар ще раз і, якщо його вже переписано, починає з нового; джоба аудиту після запису коментаря звіряє опис ще раз і ставить мітку, якщо він змінився. Новий аудит — лише з наступним пушем.
5. **Без змін:** модель і глибина міркування, один коментар на PR, «Аудиту не було» і зелений чек при збої, чек не обов'язковий, роль аудитора (ADR-0097), секрет.

## Наслідки

- Ввід моделі зростає на розмір контексту; числа прогону наживо — у звіті `docs/reports/t41-mistral-audit-context.md`.
- Коментар аудитора з'являється пізніше на час очікування чеків (до 5 хвилин).
- На кожну правку опису PR запускається коротка джоба (самоперевірка скрипта і одне-два звернення до API GitHub); токенів Mistral вона не витрачає.
- Записи кроків, ADR і довідники беруться з бази: запис кроку самого PR і нові ADR аудитор бачить лише в дифі — про це йому каже розділ «згадано, але в базі немає».
- Звернення скрипта до API GitHub мають тайм-аут 30 секунд. Найгірший час джоби (очікування чеків і три спроби виклику моделі) — ≈ 27 хв при ліміті джоби 30 хв.
- Назви чеків приходять із workflow коміту PR; моделі вони подаються як дані в розділі з одноразовим кодом, а в коментарі екрануються.

- Навмисні поломки нового коду — `docs/reports/t41/mutations.py`.
- Прогін наживо — на PR цього кроку (скрипт і workflow із гілки PR).
