# 0132. Чек `check` workflow `iter-tag` — обов'язковий чек гілки `main`

- Статус: accepted (мерж PR власником = «схвалюю» — конвенція ADR-0052)
- Дата: 2026-11-24
- Частково Supersedes: ADR-0093 (п. 4 — «Чек не обов'язковий»)
- Доповнює: ADR-0131 і ADR-0082 (обов'язкові чеки `main`), ADR-0028 (захист гілки `main`), ADR-0094 (умови мержу класу `auto`), ADR-0018 (зміна workflow — з ADR)
- Автор: Claude Code (рішення власника 24.11.2026 на фініші Т.155 кнопкою — «Схвалюю; далі check (27)»; кандидат процесу 27)

## Контекст

- ADR-0093 (Т.34) додав workflow `iter-tag`: джоба `check` на кожну зміну відкритого PR у `main` (відкриття, пуш, зміна опису, повторне відкриття) проганяє самоперевірку `scripts/iter-tag.sh` і показує назву майбутнього тегу; недопустима чи вже зайнята назва — червоний чек. Чек лишився необов'язковим: червоний `check` мерж не зупиняв, і тег після такого мержу просто не ставився.
- Обов'язкові чеки `main` до цього ADR (`gh api …/branches/main/protection/required_status_checks`, 24.11.2026): `test`, `codecov/patch`, `pr-size`, `e2e`, `shuffle` (ADR-0131).
- Перевірка до рішення (Т.156): джоба йде на кожному відкритому PR без фільтра шляхів — і з рядком `Iter-Tag:`, і без нього (тоді `--preview` пише в підсумок «Рядка Iter-Tag … немає» і виходить з кодом 0), і на PR Dependabot (#366 — `check` success). Останні 100 прогонів `iter-tag` на подіях `pull_request` — усі success; на #464–#468 — по два зелені записи `check` (пуш і `edited`) і один `skipped` (подія `closed` після мержу). Джоба з тією самою назвою `check` є у workflow `tag-version`, але той іде лише на пуш тегів `v*` і на PR не з'являється.

## Рішення

1. Чек `check` (джоба `check` workflow `iter-tag`, застосунок GitHub Actions) — обов'язковий чек гілки `main` поруч із `test`, `codecov/patch`, `pr-size`, `e2e`, `shuffle`. Джерело чека в правилі — GitHub Actions, а не «будь-який застосунок»: назва `check` загальна, і джерело відсікає однойменні чеки інших застосунків. Однойменна джоба `check` workflow `tag-version` — того самого застосунку, але на голові PR не з'являється: вона йде на пуш тегів `v*`, а ті стоять на merge-комітах (ADR-0054). Налаштування — у захисті гілки (`Settings → Branches`, правило `main`, «Require status checks to pass»): змінює власник або сесія в його браузері з його підтвердженням (ADR-0131 п. 1; «Save changes» вимагає sudo mode — Passkey власника).
2. Червоний `check` блокує мерж будь-якого класу. Причини червоного (ADR-0093 п. 4, `from_body` у `scripts/iter-tag.sh`): недопустима чи зайнята назва, кілька рядків `Iter-Tag:` з різними назвами — виправити опис PR (`PATCH`) і дочекатись нового прогону з подією `edited`; старий прогін не перезапускати — «Re-run» бере опис зі старої події і лишиться червоним. Помилка запиту про тег — «Re-run» джоби.
3. Зміна опису PR перезапускає `check` (подія `edited`), як і `pr-size`: мерж одразу після `PATCH` опису — чекати, поки обидва завершаться.
4. Workflow `iter-tag` і `scripts/iter-tag.sh` — без змін.

## Відхилені варіанти

- **Лишити необов'язковим:** червоний `check` означає, що після мержу тег не стане (або назва зайнята); мерж без тегу виправляли потім ручним запуском `iter-tag` — зайвий крок, що тримався на увазі агента.
- **Перевірка назви тегу кроком у джобі `pr-size`:** змінює зміст наявного обов'язкового чека і дублює логіку `iter-tag.sh` у другому місці; окремий чек дає ту саму силу без цього.
- **Фільтр шляхів чи подій для `check`** (щоб не йшов на PR без тегу): обов'язковий чек, що не запустився, блокує PR назавжди; без фільтра він іде на кожному PR і на PR без рядка тегу зелений за секунди.
