# 0018. Зміна workflow-файлів — лише разом з ADR у тому ж коміті

- Статус: accepted
- Дата: 2026-10-13

**Контекст.** Guard `scripts/pre-commit.sh` (ADR-0014) відхиляв будь-який коміт зі змінами `.github/workflows/` — AGENTS.md категорично забороняв ці файли. Але процес вже передбачав авторизовані власником зміни CI: П12 (крок покриття) і П3.1 (прибрано `continue-on-error` з Codecov-кроку) довелося комітити з `--no-verify` і ручними перевірками — guard блокував саме те, що власник явно доручив, а `--no-verify` вимикав усі решта перевірок (тести, exact-байти, lint) радіусом не пропорційно до зміни. Розглянуті альтернативи: залишити категоричну заборону (кожна авторизована зміна CI — знову `--no-verify`, привчає обходити hook як норму); зняти заборону повністю (CI/CD — найбільший радіус ураження: деплой Pages виконується з `main`, тиха помилка ламає прев'ю одразу).

**Рішення.** Ми використовуємо той самий патерн, що й для залежностей (ADR-0012): зміна `.github/workflows/` можлива лише разом з новим файлом у `docs/adr/` у тому ж коміті — ADR фіксує що, чому і наслідки. Технічний рубіж — правило 1c у `scripts/pre-commit.sh`: workflow-файл у staged без файлу з `docs/adr/` у staged означає відмову коміту. `--no-verify` для таких змін більше не потрібен: усі перевірки hook'а (тести, exact-байти, lint через lint-staged) виконуються й на комітах з workflow-файлами.

**Наслідки.** ADR у коміті — необхідна, але не достатня умова: він не гарантує авторизації власника, тож відповідальність за перевірку, що ADR відповідає вказівці власника сесії, лишається на рев'ю (власник стежить за ADR у комітах). Кожна зміна CI має слід рішення в історії. Категоричні заборони AGENTS.md (видалення тегів `iter-*`, зміна історії git) не зачіпаються — вони поза цим процесом. Зміна цього рішення — новий ADR із полем Supersedes.
