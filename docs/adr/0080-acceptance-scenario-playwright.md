# 0080. Сценарій приймання в браузері — smoke ADR-0030 у Playwright, звірка з дзеркалом ядра

- Статус: accepted (мерж PR власником = «схвалюю» — конвенція ADR-0023/0030/0052)
- Дата: 2026-11-10
- Доповнює: ADR-0030 (стандартний smoke-сценарій валідації), ADR-0063 (Playwright; домен-смок прев'ю), ADR-0003 (детермінізм), ADR-0002 (чисте ядро), ADR-0076 (гейти в CI), ADR-0018 (workflow-файли — з ADR), ADR-0012 (package.json: новий скрипт, залежностей не додано)
- Автор: Claude Code (запит власника 2026-11-10, задача Т.8 — початок етапу 2 «приймання без очей» за аналізом процесу)

## Контекст

Стандартний smoke-сценарій (ADR-0030, крок 7 циклу) проходить людина: вибрати юніта → рух → постріл → дозор → кінець ходу → результат бою; геосцена: +1 тік, +1 доба, сейв → лоад; консоль без помилок. Це єдина перевірка, що гра проходиться в браузері від старту до результату. Автоматика цього не бачить: юніт- і DOM-тести (vitest + jsdom, ADR-0013) не мають Canvas і справжнього вводу, а домен-смок прев'ю (ADR-0063) зупиняється на «канва видима».

Наслідок — кожен крок чекає на очі власника, а дефект зв'язування UI з ядром може жити довго (урок ітерації 5.3: кнопка «Кінець ходу» була зламана, CI зелений).

Перешкода для автоматизації: стан гри зі сторінки не прочитати. Бойовище — канва, партія і місія — модульні змінні `main.ts`. Сценарій не знає, де стоять юніти, яка клітинка вільна і чи видно ціль.

## Рішення

1. **Сценарій приймання** `e2e/acceptance.scenario.ts` (Playwright, наявна залежність ADR-0063) проходить кроки ADR-0030 справжніми кліками: стартовий екран → нова партія (сід 42, «норма») → тіки до приземлення зонда → місія → вибір юніта → рух тап-тап → дозор → кінець ходу → постріл тап-тап у видиму ціль → авто-бій до результату → геосцена: +1 тік, +1 доба → сейв → лоад; нуль помилок сторінки і консолі за весь прохід. Порядок бойових кроків підлаштовано: ціль стає видимою після підходу демонів, тож постріл іде після першого кінця ходу.
2. **Дзеркало ядра** `e2e/mirror.ts`: сценарій веде в Node другу партію з тим самим сідом і повторює на ній ті самі виклики ядра, що їх робить шар відображення на кожен клік (`advanceTime`, `createMission`, `moveUnit`, `setOverwatch`, `endTurn` + `aliensTurn`, `resolveAttack`, `DemoSteps`). За ADR-0003 стани збігаються, тож дзеркало каже сценарію, куди клікати, і що має показати сторінка: годинник, кількість зондів і місій, рядок HP/AP юніта, ціну шляху, шанс влучання, кількість дій демонів, HP цілі після пострілу, банер результату, картки ростеру (HP і вбивства), чип «Боєготові». Розбіжність сторінки з дзеркалом — дефект зв'язування UI з ядром або порушений детермінізм.
3. Сценарій **не містить координат і не залежить від мапи**: клітинки, цілі й очікувані числа обчислюються ядром. Зміна балансу, генератора мапи чи ШІ сценарій не ламає; ламає його зміна поведінки, яку він перевіряє, або текстів і `id` елементів, за якими він читає сторінку.
4. **Ціль прогону — збірка того самого коміту**: `playwright.e2e.config.ts` сам запускає `npm run build` і `vite preview`. Код сценарію, дзеркало і гра завжди з одного дерева файлів — транзитного вікна домен-смоку (урок П12.2: смок з main проти чужої гілки) тут немає. Ретраїв немає: сценарій детермінований, ретрай сховав би нестабільність.
5. **Окремо від домен-смоку прев'ю**: суфікс `*.scenario.ts` і свій конфіг. `npm run test:smoke` (ADR-0063) і `npm test` (vitest) сценарію не тягнуть; `preview-branch.yml` не змінюється.
6. **Скрипт** `npm run test:e2e` у `package.json` (залежності без змін). `tsconfig.e2e.json` — перевірка типів сценарію і дзеркала: Playwright, як і vitest, типів не перевіряє (урок П11.3).
7. **CI**: джоба `e2e` у `ci.yml` на кожен PR у `main`: `npm ci` → `tsc -p tsconfig.e2e.json` → `playwright install --with-deps chromium` → `npm run test:e2e`. Окрема джоба, щоб встановлення браузера (~1 хв) не гальмувало чек `test`.
8. Чек `e2e` **поки не обов'язковий**: захист гілки `main` цим PR не змінюється. Перевести його в required — рішення власника після кількох зелених прогонів на реальних PR.

## Наслідки

- Питання «чи проходиться гра від старту до результату без помилок» отримує відповідь у CI на кожен PR, без браузера людини. Локальний прогін — близько 15 секунд разом зі збіркою.
- Перевірено від супротивного на `07dbe97` — кожна навмисна поломка шару відображення дає червоний сценарій із назвою кроку і парою «очікувано/отримано»: UI ігнорує сід із діалогу; зайвий кидок `rng` під час пострілу; кнопка «Дозор» не викликає ядро; подвійний хід демонів на «Кінець ходу»; `console.error` після завантаження сейву.
- Крок 7 циклу (валідація власником) не скасовується. Сценарій знімає механічну частину — «чи проходиться»; візуальна коректність, плавність анімацій (ADR-0030 п.5) і iPad лишаються за власником. Скорочення ручної валідації — окреме рішення власника.
- Нова ціна змін UI: PR, що міняє тексти підказок бою, `id` елементів чи порядок викликів ядра в обробниках вводу, має оновити сценарій або дзеркало в тому ж PR. Тести і гра з одного коміту, тож це звичайний червоний чек, а не транзитне вікно.
- Дзеркало повторює лише частину тіку партії — геосцену і лікарню. Економіка, наука, цех і перехоплення сценарієм не звіряються: він їх не чіпає. Розширення (перехоплення, вербування, дослідження) потребуватиме повного тіку партії в ядрі замість копії порядку викликів з `main.ts` — окремий крок.
- `e2e/` лишається поза `npm run lint` і `format:check` (вони дивляться `src/`); формат файлів цього PR перевірено вручну. Механізація — окремим кроком.
- Трейс падіння Playwright пише в `dist/e2e-results/` (`dist/` уже в `.gitignore`). У CI він як артефакт не вивантажується — діагностика за журналом джоби (звіт із кроками) і локальним прогоном.
- Зміна методики (знімки екрана, інші браузери, бот через UI) — новим ADR.

## Альтернативи

- **Жорсткий скрипт кліків за координатами для сіда 42** — відкинуто: будь-яка зміна балансу, мапи чи ШІ вимагала б заново «дивитись очима» і переписувати координати — саме те, від чого йдемо.
- **Налагоджувальний гачок у грі** (`window.__rubezh` зі станом партії) — відкинуто для цього кроку: зміна продуктового коду заради тесту і нова поверхня в проді. Може знадобитись для «бота через UI»; рішення — окремим ADR.
- **Додати сценарій у чинний домен-смок** (`*.e2e.ts`, `npm run test:smoke`) — відкинуто: той виконується з main проти прев'ю чужої гілки; сценарій з дзеркалом вимагає, щоб код тесту і гра були з одного коміту.
- **Dev-сервер замість збірки** — відкинуто: приймаємо те, що деплоїться (прод-збірка Vite), а не dev-режим.
- **Звірка знімків екрана** — поза цим кроком: потребує еталонів і порогів, перевіряє інше (вигляд, а не поведінку).
