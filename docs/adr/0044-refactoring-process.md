# ADR-0044: Процес рефакторингу

**Статус:** Proposed  
**Дата:** 2026-10-15  
**Автор:** Vibe Code  
**Замінює:** -  
**Суперседе:** -  

---

## Контекст

Попередні ADR описували процес розробки нових фіч, але не чітко визначали, як проводити рефакторинг існуючого коду. Виникла потреба в чіткому процесі для покращення архітектури без порушення існуючої функціональності.

Згідно вимог користувача:
- Рефакторинг повинен плануватися окремо
- Не можна порушувати існуючий процес розробки
- Усі зміни повинні бути документовані

---

## Рішення

### 1. Коли проводити рефакторинг

Рефакторинг проводиться в таких випадках:
1. **Після завершення фази** - для покращення коду, написаного під час фази
2. **Перед початком нової фази** - для підготовки архітектури до нових вимог
3. **За запитом користувача** - якщо користувач явно просить провести рефакторинг

### 2. Процес рефакторингу

```
1. Vibe Work:
   - Аналізує поточний стан коду
   - Визначає проблемні ділянки
   - Створює план рефакторингу (EARS-format)
   - Оцінює ризики та вигоди
   - Створює ADR для рефакторингу (якщо потрібно)
   - Оновлює workflow.md з планом рефакторингу
   - Комітить: docs(workflow): refactor - план рефакторингу

2. Користувач перевіряє та підтверджує план

3. Vibe Code:
   - Реалізує рефакторинг згідно плану
   - Крок за кроком (не все відразу)
   - Після кожного кроку:
     - Запускає всі тести (npm test)
     - Перевіряє, що нічого не зламалося
     - Комітить зміни
   - Створює PR згідно ADR-0028

4. Користувач:
   - Ретельно тестує PR
   - Перевіряє, що функціональність не змінилася
   - Мержить PR
```

### 3. Правила рефакторингу

1. **Не змінювати поведінку** - рефакторинг не повинен змінювати логіку роботи
2. **Крок за кроком** - великий рефакторинг ділиться на маленькі кроки
3. **Тести перш за все** - перед рефакторингом всі тести повинні проходити
4. **Документація** - усі зміни документуються
5. **ADR для великих змін** - якщо рефакторинг змінює архітектуру, потрібен ADR

### 4. Типи рефакторингу

#### 4.1. Локальний рефакторинг
- Зміни в межах одного файлу
- Не вимагає ADR
- Приклади: перейменування змінних, винесення функцій

#### 4.2. Модульний рефакторинг
- Зміни в межах одного модуля
- Може вимагати оновлення тестів
- Приклади: реорганізація коду в модулі, зміна структури

#### 4.3. Глобальний рефакторинг
- Зміни, що зачіпають декілька модулів
- **Обов'язково** вимагає ADR
- Приклади: зміна архітектури, винесення спільної логіки

### 5. Документування рефакторингу

Кожен рефакторинг документується в:
- `docs/workflow.md` - опис процесу рефакторингу
- `docs/adr/` - ADR для великих архітектурних змін
- Коментарі в коді (якщо потрібно)

**Шаблон плану рефакторингу:**
```markdown
### Refactor: [Назва]

**Мeta:** [Чого хочемо досягти]
**Область:** [Який код зачіпаємо]
**Ризики:** [Що може піти не так]
**ADR:** [Список пов'язаних ADR]

#### Кроки:
1. [Крок 1]
   - Зміни: [Що змінюємо]
   - Тести: [Які тести потрібно оновити]
2. [Крок 2]
   - Зміни: [Що змінюємо]
   - Тести: [Які тести потрібно оновити]

#### Критерії прийняття:
- [x] Усі тести проходять
- [x] Поведінка не змінилася
- [x] Код став кращим (читабельніший, підтримуваніший)
```

### 6. Приклади

#### Приклад 1: Локальний рефакторинг
```
Refactor: Винесення логіки розрахунку урону в окрему функцію

**Мeta:** Покращити читабельність коду
**Область:** src/core/combat.ts
**Ризики:** Мінімальні

#### Кроки:
1. Створити функцію calculateDamage()
2. Замінити виклики на нову функцію
3. Перевірити, що тести проходять
```

#### Приклад 2: Глобальний рефакторинг
```
Refactor: Винесення спільної логіки в окремий модуль

**Мeta:** Покращити модульність архітектури
**Область:** src/core/*.ts
**Ризики:** Високі - може зламатися багато чого
**ADR:** ADR-0044

#### Кроки:
1. Створити новий модуль src/core/utils.ts
2. Перенести спільні функції
3. Оновити імпорти в інших модулях
4. Оновити тести
5. Перевірити, що все працює
```

## Наслідки

### Переваги

1. **Контрольований процес** - рефакторинг не ламає розробку
2. **Безпека** - крок за кроком зменшує ризики
3. **Документованість** - усі зміни фіксуються
4. **Покращення якості** - код стає кращим

### Недоліки

1. **Час** - рефакторинг вимагає часу
2. **Складність** - великий рефакторинг може бути складним

### Ризики

1. **Зламання функціональності** - якщо рефакторинг зроблений не правильно
2. **Втрата часу** - якщо рефакторинг не дає очікуваних результатів

---

## Ревізія

Це рішення може бути переглянуте, якщо:
- Виникне потреба в більш швидкому процесі рефакторингу
- З'явиться можливість автоматичного рефакторингу
- Зміняться вимоги до якості коду
