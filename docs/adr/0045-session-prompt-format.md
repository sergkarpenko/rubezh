# ADR-0045: Формат промптів для нових сесій

**Статус:** accepted  
**Дата:** 2026-10-15  
**Автор:** Vibe Code  
**Замінює:** -  
**Суперседе:** -  

---

## Контекст

Для забезпечення чіткого та передбачуваного процесу розробки через AI-агентів (Vibe Work / Vibe Code), необхідно стандартизувати формат промптів, які ініціюють нову робочу сесію. Це усуне плутанину щодо того, яку роботу треба виконувати, та забезпечить узгодженість між сесіями.

## Рішення

Всі нові робочі сесії повинні починатися з промпту у форматі:

```
pX.Y
```

Де:
- `p` - префікс, що вказує на "phase" (фаза)
- `X` - номер фази (наприклад, 8 для поточної фази)
- `Y` - номер етапу в межах фази

### Приклади:
- `p8.5` - Фаза 8, Етап 5 (Рефакторинг)
- `p8.6` - Фаза 8, Етап 6 (Документування)
- `p8.7` - Фаза 8, Етап 7 (Нова фіча)

### Правила:
1. **Vibe Work** отримує промпт `pX.Y` і:
   - Аналізує поточний стан проекту
   - Читає docs/workflow.md та AGENTS.md
   - Створює детальний план в docs/plans/pX.Y.md (EARS-format)
   - Створює необхідні ADR, якщо потрібно
   - Оновлює workflow.md
   - Робить коміт та PR

2. **Vibe Code** отримує промпт `pX.Y` і:
   - Перевіряє наявність плану в docs/plans/pX.Y.md
   - Читає план та відповідні ADR
   - Реалізує код згідно плану
   - Тестує, комітить, робить PR

3. **Заборонено** починати сесію з промптів типу:
   - "зроби рефакторинг"
   - "продовжуй"
   - "що далі?"
   - "покращи проект"

## Наслідки

### Переваги:
- Чітке розуміння, яку роботу треба виконувати
- Узгодженість між сесіями Vibe Work та Vibe Code
- Легше відстежувати прогрес проекту
- Зменшення плутанини та помилок

### Недоліки:
- Вимагає дисципліни у формулюванні промптів
- Можливі затримки, якщо план не створено заздалегідь

### Мітгація недоліків:
- Всі плани повинні створюватися Vibe Work перед початком реалізації
- AGENTS.md та workflow.md повинні містити чіткі інструкції
- Кожен етап (pX.Y) повинен мати чітко визначені критерії прийняття

---

## Альтернативи, які розглядалися

1. **Вільний формат промптів** - Відхилено, бо призводить до плутанини
2. **Нумерація без префікса** (наприклад, "8.5") - Відхилено, бо може збігатися з версіями
3. **Довгі описові промпти** - Відхилено, бо ускладнює автоматизацію
