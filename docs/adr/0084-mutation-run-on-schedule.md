# 0084. Мутаційний прогін ядра — за розкладом у GitHub Actions, без гейта

- Статус: accepted (мерж PR власником = «схвалюю» — конвенція ADR-0018/0052)
- Дата: 2026-11-11
- Доповнює: ADR-0083 (StrykerJS, склад прогону; п.7 «`.github/workflows/` не змінюється» і наслідок «прогін ручний» цим ADR змінено), ADR-0018 (workflow-файли — з ADR), ADR-0076 (гейти в CI)
- Автор: Claude Code (запит власника 2026-11-11, задача Т.13 — етап 2 «приймання без очей» за аналізом процесу)

## Контекст

ADR-0083 дав міру якості тестів ядра і лишив її ручною: `npm run test:mutation` запускає агент у сесії або власник, 35–45 хвилин на двох ядрах. Число оновлюється лише тоді, коли хтось про нього згадав. Кроки Т.11 і Т.12 підняли score трьох файлів бою і геосцени та двох файлів сейву і цеху прицільними прогонами, але повний прогін після них не запускався: загальне число після серії — оцінка (≈ 85 %), а не вимір.

Гейт на кожен PR ADR-0083 відклав: прогін задовгий, а поріг без кількох вимірів ставити нема з чого. Між «вручну, коли згадали» і «чек на кожен PR» є проміжний крок — регулярний вимір без наслідків для мержу.

## Рішення

1. **Workflow `.github/workflows/mutation.yml`** запускає `npm run test:mutation` — той самий конфіг і склад прогону, що в ADR-0083, без змін у `stryker.config.mjs` і `vitest.stryker.config.ts`.
2. **Три тригери:**
   - `schedule` — щопонеділка о 02:17 UTC;
   - `workflow_dispatch` — вручну, завжди виконує прогін;
   - `pull_request` у `main` — лише коли PR змінює сам механізм вимірювання: `mutation.yml`, `stryker.config.mjs`, `vitest.stryker.config.ts`, `scripts/mutation-summary.mjs`. PR зі змінами коду гри прогін не запускає.
3. **Прогін за розкладом пропускається, якщо міряти нічого нового.** Workflow бере коміт останнього успішного прогону на `main` і порівнює з `HEAD` за шляхами `src`, `package-lock.json`, `stryker.config.mjs`, `vitest.stryker.config.ts`, `vite.config.ts`, `scripts/mutation-summary.mjs`, `.github/workflows/mutation.yml`. Без відмінностей — запис у зведенні «прогін пропущено» і вихід за кілька секунд.
4. **Результат — у двох місцях.** Зведення прогону (`$GITHUB_STEP_SUMMARY`): загальний mutation score, таблиця за файлами від найнижчого, до 60 не виявлених мутантів із файлом і рядком. Його друкує `scripts/mutation-summary.mjs` зі звіту `dist/mutation/mutation.json`. Повний звіт (`index.html` + `mutation.json`) — артефакт `mutation-report`, зберігається 90 днів.
5. **Це вимірювання, а не гейт.** Порога немає (`thresholds.break: null` з ADR-0083 лишається); чек `mutation` не додається до обов'язкових чеків `main`; червоний прогін мерж не блокує.
6. **Червоний прогін означає поломку вимірювання, а не низьке число:** не зібрались залежності, впав початковий прогін тестів, вийшов тайм-аут джоби (90 хвилин) або у звіті немає жодного виявленого мутанта (`mutation-summary.mjs` завершується з кодом 1).
7. **Базова лінія після серії Т.11–Т.12** — перший повний прогін цього workflow; окремий ручний прогін не потрібен. Число фіксується в записі кроку Т.13 у `docs/workflow.md`.

## Наслідки

- Число оновлюється саме, коли змінився код чи тести. Сесія агента читає останній результат без 40 хвилин очікування: `gh api repos/sergkarpenko/rubezh/actions/workflows/mutation.yml/runs?branch=main&status=success&per_page=1` дає прогін, зведення — на його сторінці, `mutation.json` — в артефакті.
- Прогін на раннері GitHub має більше ядер, ніж хмарна сесія агента, тож тривалість інша; score від числа ядер не залежить (ADR-0083: відтворюється з точністю до десятих відсотка через мутантів із тайм-аутом).
- Падіння score ніхто не побачить, поки не відкриє зведення: сповіщень про зміну числа немає. Це свідома ціна кроку без порога.
- GitHub вимикає розклад у публічному репозиторії після 60 днів без активності. Після довгої перерви власник вмикає workflow знову в Actions або запускає його вручну.
- Зміна конфігу Stryker чи скрипта зведення перевіряється прогоном на самому PR — поломку видно до мержу, хоча чек і не обов'язковий. Такий PR чекає на прогін довше за звичайний, якщо автор хоче побачити результат.
- Артефакти живуть 90 днів: історія числа довша за три місяці лишається лише в записах кроків у `docs/workflow.md`.
- Поріг і чек на PR — окремим ADR після двох-трьох прогонів за розкладом: поріг за файлами правил, а не на все ядро (боти `ai-bot.ts`, `intercept-bot.ts` тягнуть загальне число вниз); чек на PR потребує інкрементального режиму Stryker.

## Альтернативи

- **Щоденний розклад** — відкинуто: робота над проєктом іде серіями сесій, між якими `main` не змінюється; з пропуском незмінного коду щоденний розклад дав би те саме число прогонів, але й щоденні порожні записи в Actions.
- **Запуск на кожен пуш у `main`** — відкинуто: серія з трьох PR за годину дала б три прогони по пів години, з яких потрібен останній. Розклад із пропуском міряє той самий стан раз.
- **Прогін без пропуску, щотижня безумовно** — відкинуто: два прогони одного коміту дають той самий результат (перевірено в Т.10), а 30 хвилин раннера на тиждень простою нічого не кажуть.
- **Stryker Dashboard** (зовнішній сервіс з історією score і бейджем) — не взято: потрібен токен у секретах і ще один зовнішній сервіс; для вимірювання раз на тиждень вистачає зведення і артефакту. Якщо знадобиться графік історії — окремим ADR.
- **Коміт числа в репозиторій** (файл з історією score, який оновлює сам workflow) — відкинуто: workflow отримав би право запису в `main` в обхід PR (ADR-0028).
- **Поріг одразу** — відкинуто: після Т.11–Т.12 є лише прицільні виміри п'яти файлів; поріг ставити після кількох повних прогонів (прецедент ADR-0083: спершу вимір, потім рішення).
