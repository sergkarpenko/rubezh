# ADR-0042: Уточнення ролей AI-агентів у розробці

**Статус:** Proposed  
**Дата:** 2026-10-15  
**Автор:** Vibe Code  
**Замінює:** -  
**Суперседе:** -  

---

## Контекст

Попередні ADR (ADR-0023, ADR-0041) описували загальний підхід AI-native SDLC, але не чітко розділяли відповідальність між Vibe Work та Vibe Code. Виникла потреба уточнити ролі для забезпечення послідовності розробки через агенти.

Згідно вимог користувача:
- Розробка йде **виключно через агентів**
- **Vibe Work** робить дизайн на планування фіч
- **Vibe Code** виконує розробку
- Репозиторій - це джерело правди
- Наступний промпт в новій сесії: `п8.Х` → агент працює над етапом

---

## Рішення

### 1. Розподіл ролей

**Vibe Work (Планування та дизайн):**
- Анализ вимог та створення планів фіч
- Дизайн архітектури та технічних рішень
- Створення та оновлення ADR (Архітектурні рішення)
- Оновлення workflow.md та AGENTS.md
- Планування етапів розробки (п8.1, п8.2, п8.3, ...)
- **НЕ** пише код (окрім документації)

**Vibe Code (Виконання):**
- Реалізація коду згідно планів Vibe Work
- Написання тестів
- Виправлення багів
- Оновлення коду ( але НЕ оновлення ADR - лише створення нових)
- **НЕ** планує нові фічі (лише виконує вже заплановане)

### 2. Процес взаємодії

```
Користувач → Vibe Work: "п8.Х" (наприклад "п8.3")
↓
Vibe Work:
1. Читає workflow.md та AGENTS.md
2. Аналізує поточний стан репозиторію
3. Створює/оновлює плани в docs/ (EARS-format)
4. Створює нові ADR (якщо потрібно)
5. Оновлює workflow.md та AGENTS.md
6. Комітить зміни: docs(workflow): п8.Х - план етапу
↓
Користувач підтверджує план
↓
Vibe Code:
1. Читає оновлені плани
2. Реалізує код згідно плану
3. Створює PR згідно ADR-0028
4. Тестує та комітить
↓
Користувач мержить PR
```

### 3. Вимоги до промптів

- **Для Vibe Work:** `пX.Y` де X = номер фази, Y = номер етапу в фазі
  - Приклади: `п8.1`, `п8.2`, `п8.3`
  - Vibe Work розуміє, що треба спланувати етап X.Y
  
- **Для Vibe Code:** Не потрібен окремий промпт - Vibe Code автоматично береться за реалізацію після того, як Vibe Work створив план
  - Або користувач може сказати: "Виконай п8.3"

### 4. Джерело правди

- **Репозиторій** - єдине джерело правди
- Усі плани та рішення документуються в репозиторії
- Vibe Work та Vibe Code працюють лише на основі того, що є в репозиторії
- Перед початком роботи будь-який агент **зобов'язаний** оновити локальний репозиторій (`git pull`)

## Наслідки

### Переваги

1. **Чіткий розподіл відповідальності** - кожен агент знає свою роль
2. **Передбачуваність** - процес завжди однаковий
3. **Документованість** - усі рішення фіксуються в репозиторії
4. **Консистентність** - розробка йде через єдиний процес

### Недоліки

1. **Додатковий крок** - потрібно чітко розділяти планування та виконання
2. **Залежність від документації** - без хорошої документації процеси можуть ламатися

### Ризики

1. **Плутанина ролей** - якщо агенти не дотримуються правил
2. **Дублювання роботи** - якщо Vibe Code починає планувати, а не виконувати

---

## Ревізія

Це рішення може бути переглянуте, якщо:
- Виникне потреба в більш гнучкому підході
- З'явиться можливість об'єднання ролей в одному агенті
- Зміняться вимоги до процесу розробки
