# 0113. Кроки `run:` у workflow — під `bash` з `pipefail`: `defaults.run.shell: bash` у кожному workflow

- Статус: accepted (мерж PR власником = «схвалюю» — конвенція ADR-0052)
- Дата: 2026-11-22
- Доповнює: ADR-0018 (зміна workflow — з ADR у точці коміту), ADR-0076 (гейти в джобі `test`), ADR-0099 (явний `pipefail` у кроці самоперевірки), ADR-0112 (та сама вада в `scripts/pr-size.sh`)
- Автор: Claude Code (рішення власника 22.11.2026 на фініші Т.113 кнопкою — «Т.114 = 42 (Recommended)»; кандидат 42)

## Контекст

- Крок `run:` без `shell:` на раннері Linux іде під `bash -e {0}` — без `pipefail`: код конвеєра — код останньої команди. З `shell: bash` — `bash --noprofile --norc -eo pipefail {0}`. Замір у Т.114: `bash -e -c 'false | true'` — код 0; `bash --noprofile --norc -eo pipefail -c 'false | true'` — код 1.
- Огляд на `0901aa1` (`grep` рядків з `|` у `.github/workflows/*.yml`): конвеєрів у кроках — два. `vibe-audit.yml`, самоперевірка — `set -o pipefail; node … --self-test | tee /dev/stderr | grep -q …` (явний `pipefail`, як ADR-0099). `preview-branch.yml`, slug гілки — `echo … | tr '/' '-'` усередині `$(…)`: код першої команди не важить. Жоден чинний крок ваду не має.
- Вада — на майбутнє: новий гейт-конвеєр (`команда | tee | grep`) без `set -o pipefail` тихо губить код виходу команди — так було в Т.42 (знайшов аудит) і, в іншій формі, у `pr-size.sh` до Т.113. Правило досі жило лише в довіднику `docs/agents/common.md`.
- Скрипти `scripts/*.sh`, які кличуть workflow, — `#!/bin/sh`, запускаються окремим процесом; оболонка кроку їх не змінює. `pr-size.sh` виправлено в Т.113, `pr-class.sh` і `iter-tag.sh` ваду не мають (конвеєри там — у присвоєннях з перевіркою порожнього результату, в умовах `if` з `printf` ліворуч або з `|| true` навмисно).

## Рішення

1. Кожен workflow `.github/workflows/*.yml` має на верхньому рівні блок `defaults: run: shell: bash` (перед `jobs:`, з коментарем-посиланням на цей ADR). Усі кроки `run:` ідуть під `bash --noprofile --norc -eo pipefail`.
2. У джобі `test` workflow `ci` — крок «Workflow — bash з pipefail» одразу після `npm ci`: `grep -L -x -F -e '    shell: bash'` по `.github/workflows/*.yml` і `*.yaml` (`nullglob`); файл без рядка — `::error file=…::` і код 1; помилка самого `grep` (код понад 1) — `::error` і код 2. Новий workflow без верхнього блоку червонить обов'язковий чек `test`.
3. Явні `set -o pipefail` і `shell: bash` у кроках `vibe-audit.yml` лишаються: вони не шкодять і читаються без знання цього ADR.

## Наслідки

- Перевірка Т.114: YAML усіх восьми workflow розбирається, `defaults` = `{run: {shell: bash}}`; крок перевірки на гілці — код 0, з `shell: sh` у `tag-version.yml` — `::error file=.github/workflows/tag-version.yml::…` і код 1; новий `z.yaml` без блоку — код 1; каталог `d.yml` (помилка `grep`) — код 2 (GNU grep 3.11). Поведінка чинних кроків не змінюється: конвеєр у `preview-branch.yml` — у підстановці, код останньої команди кроку (`echo >> "$GITHUB_OUTPUT"`) той самий. `--noprofile --norc` не важить: кроки не покладаються на профіль оболонки (PATH від `setup-node` — через `GITHUB_PATH`).
- Перевірка рядком, а не розбором YAML: без нової залежності (ADR-0012) і без скрипта з `--self-test`; ціна — блок має стояти саме на верхньому рівні з відступом у 4 пробіли (`defaults` джоби дав би 8 і не пройшов би — це навмисно: нова джоба в старому файлі бере верхній блок).
- Межі перевірки: вона ловить лише відсутність верхнього блоку. Перекриття оболонки нижче — `defaults.run.shell: sh` джоби чи `shell: sh` кроку — проходить і лишається на аудиті; файл із закінченнями рядків CRLF дає хибну помилку (`-x` не збігається через `\r`).
- Аудит PR #429: Opus — glob без `*.yaml` (GitHub Actions виконує й їх), `|| true` ковтав код 2 від `grep`, межі перевірки не описані, неточний опис конвеєрів `pr-class.sh` — виправлено; Vibe — той самий `*.yaml`.
- Відхилено: `set -o pipefail` у кожному кроці з конвеєром (правило знову тримається на пам'яті автора); `defaults` на рівні джоби (кожна нова джоба — нове місце забути); тест vitest, що розбирає workflow (у `src` немає типів Node — ADR-0107, а для `scripts/` тестового прогону немає); скрипт `scripts/workflow-shell-check.sh` з `--self-test` (більше коду, ніж перевірка, яку він обгортає).
