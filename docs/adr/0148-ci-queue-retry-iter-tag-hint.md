# 0148. Черга замість скасування для `pr-size` і `iter-tag`, повтор запитів GitHub у `vibe-audit`, попередження про `Iter-Tag` на PR кроку фази

- Статус: accepted (мерж PR власником = «схвалюю» — конвенція ADR-0052)
- Дата: 2026-11-25
- Доповнює: ADR-0077 (workflow `pr-size`), ADR-0093 і ADR-0132 (workflow `iter-tag`, обов'язковий `check`), ADR-0102 / ADR-0104 / ADR-0105 (`vibe-audit`), ADR-0018 (зміна workflow — з ADR), ADR-0146 п. 6 (кандидати процесу — технічним блоком між фазами)
- Автор: Claude Code (технічний блок між фазами Т.189; обсяг — рішення власника 25.11.2026 кнопкою «А. Документи + CI (Рекомендовано)»; кандидати процесу 149, 169, 170, 174)

## Контекст

- **174.** Workflow `pr-size` має `concurrency` з `cancel-in-progress: true`. `PATCH` опису PR (подія `edited`) чи пуш поверх іншого прогону скасовує попередній прогін; скасований чек `pr-size` блокує мерж через API (405 «Required status check "pr-size" is cancelled»), і сесія перезапускала його вручну — на кожному кроці Т.183–Т.188.
- **149.** Workflow `iter-tag` групи `concurrency` не має: прогони джоби `check` одного PR (`opened`, `edited`, `synchronize`) ідуть паралельно, і результат старішого може прийти пізніше за новіший. `check` — обов'язковий чек `main` (ADR-0132), тож скасування для нього так само шкідливе, як і для `pr-size`.
- **169.** `scripts/audit-vibe-cli.mjs` робить запити REST GitHub (`pulls/N`, пошук і запис коментаря) одним викликом `fetch`: 503 від GitHub на п16.4 (Т.186) дав коментар «збій скрипта» без аудиту, хоча Vibe був доступний.
- **170.** PR кроку фази без рядка `Iter-Tag:` (п16.5, Т.187 — рядок дописано після відкриття) чек `check` не помічав: попередження друкувалось лише тоді, коли в описі згадано «iter-tag» не з початку рядка. Назви PR кроків фази містять «пX.Y» (PR #498–#503).

## Рішення

1. `pr-size`: `cancel-in-progress: false` — прогони одного PR ідуть по черзі; група та сама (`pr-size-${{ github.ref }}`).
2. `iter-tag`: група `iter-tag-<номер PR>-check` для джоби `check` і `iter-tag-<номер PR>-tag` для мержу (подія `closed`), ручний запуск — група з `run_id` (без черги); `cancel-in-progress: false`.
3. `vibe-audit`: функція `github()` повторює запит на 5xx і збій мережі — три спроби з паузами 3 і 10 с (`GITHUB_RETRY_MS`); 4xx — одразу помилка. POST (новий коментар) не повторюється всередині `github()`: запис міг відбутися до збою відповіді. Натомість `upsertComment` повторює всю операцію (пошук свого коментаря → `PATCH` або `POST`) з тими самими паузами, тож уже записаний коментар буде знайдено й оновлено, а не продубльовано. Паузи — параметр `wait` (`audit`, `github`, `upsertComment`); самоперевірка підставляє паузу без очікування. Нові випадки самоперевірки: 503 → 502 → 200; 503 тричі; 404 без повтору; збій мережі; POST без повтору; `upsertComment` після 503 на POST; 422 без повтору; прохід аудиту з двома 503 на `pulls/N`.
4. `iter-tag --preview`: функція `step_hint` бере з `$PR_TITLE` перше «пX.Y» (перед «п» — не цифра, не латинська літера і не крапка) і друкує очікувану назву `iter-X.Y`; PR без рядка `Iter-Tag:` з такою назвою дає `::warning::Назва PR — крок фази, а рядка «Iter-Tag: iter-X.Y» в описі немає — тег не буде поставлено (ADR-0093)`. Чек лишається зеленим: легка зміна і PR технічної лінії тегу не потребують, а PR серії несе тег лише на останньому (урок П8.5). Шаблон — альтернатива, а не набір у дужках: «п» — два байти UTF-8 (кандидат 165, Т.189). Назва PR — у змінній середовища `PR_TITLE` (недовірений текст, як `PR_BODY`). Нові випадки самоперевірки: сім для `step_hint` і три для `preview` (попередження, без попередження для іншої назви і для PR з рядком).

## Наслідки

- Скасування в черзі лишається: GitHub тримає в групі один прогін, що йде, і один, що чекає; третій скасовує той, що чекав (`cancelled` без старту). Таке буває, коли пуш, `PATCH` опису і мітка приходять поспіль за ≈ 10 с — тоді скасовану копію, як і раніше, перезапускає сесія (`…/actions/runs/<id>/rerun`, `docs/agents/common.md`).
- Черга подовжує чек на час попереднього прогону (`pr-size` ≈ 10–20 с, `check` ≈ 10 с).
- `vibe-audit` на тривалому збої GitHub чекає до ≈ 13 с на запит і до ≈ 40 с на запис коментаря, далі — як раніше: коментар «збій скрипта» або рядок у журналі джоби, чек зелений (чек не обов'язковий, ADR-0104).
- Попередження `check` видно в анотаціях прогону і в підсумку (`GITHUB_STEP_SUMMARY` — «Рядка Iter-Tag в описі PR немає»); сесія перевіряє його на першому пуші разом із чеками.
- Перевірка самоперевірок — навмисні поломки копій скриптів: одна спроба замість трьох, повтор на 4xx, повтор POST, `upsertComment` без повтору, збій мережі без повтору (`audit-vibe-cli.mjs`); `head -n 0`, межа без латинських літер, вимкнене попередження, «пX» без «.Y» (`iter-tag.sh`) — кожну ловить щонайменше один випадок; `iter-tag.sh --self-test` зелений за `LC_ALL=POSIX` і `C.UTF-8`.
- Відхилено: прибрати `concurrency` з `pr-size` зовсім — паралельні прогони після зміни мітки `size-deviation` могли б завершитись не в тому порядку, і чек показав би стан без мітки; червоний `check` замість попередження — заблокував би легкі зміни й PR серії; повтор POST коментаря всередині `github()` — дубль коментаря, якщо збій прийшов після запису.
