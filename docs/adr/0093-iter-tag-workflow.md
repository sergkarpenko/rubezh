# 0093. Тег кроку `iter-X.Y` ставить workflow після мержу PR — без дій власника

- Статус: accepted (мерж PR власником = «схвалюю» — конвенція ADR-0018/0052)
- Дата: 2026-11-14
- Доповнює: ADR-0018 (workflow-файли — з ADR), ADR-0028 (тег на merge-коміті), ADR-0052 (апрув власника в сесії), ADR-0057 (механічні PR — рядок тегу); змінює правило AGENTS.md «теги `iter-X.Y` — не в сесії агента» і крок 4 завершення сесії
- Автор: Claude Code (рішення власника 2026-11-14: «власник — вузьке місце», кандидат 21 «тег без власника»; задача Т.34)

## Контекст

Хмарна сесія агента пушить гілки, відкриває і мержить PR, але тег створити не може: її проксі відхиляє і пуш тегу, і створення ref через API (урок Т.5/Т.6). У Т.34 це перевірено знову: `POST /git/refs` — 403 «Write access to this GitHub API path is not permitted through this proxy», `git push origin <sha>:refs/tags/…` — 403.

Тому з Т.5 кожен крок закривався так: власник дає сесії доступ до теки локального клону, сесія ставить там тег, власник пушить його, після чого сесія відкриває і мержить другий PR — рядок тегу з sha merge-коміту (ADR-0057). За журналом кроків Т.15–Т.33 це дві дії власника і 2–12 хвилин очікування на кожен крок, плюс один механічний PR з повним колом чеків.

Валідація людиною, після якої за правилами ставиться тег, для кроків технічної лінії вже збігається з мержем: власник за потреби дивиться прев'ю гілки і пише «схвалюю» (ADR-0052), сесія мержить, тег ставиться на цей самий merge-коміт.

## Рішення

1. **Workflow `.github/workflows/iter-tag.yml`** ставить тег кроку на merge-коміт PR одразу після мержу в `main` (подія `pull_request: closed`, `merged == true`).
2. **Назву тегу задає опис PR** — рядок, що починається з `Iter-Tag:`, наприклад `Iter-Tag: iter-T.34`. PR без такого рядка workflow не чіпає: Dependabot, виправлення після кроку, перші PR серії. У серії рядок несе лише останній змістовний PR (якорення тегу — урок П8.5).
3. **Розбір і перевірка назви — `scripts/iter-tag.sh`**: назва має відповідати `iter-` + літери й цифри, частини через крапку (`iter-T.34`, `iter-15.2`, `iter-8.4a`, `iter-P`); два рядки з різними назвами або недопустима назва — помилка. Опис PR — недовірений текст: у кроки workflow він потрапляє лише змінною середовища, у команду йде тільки перевірена назва. Скрипт має самоперевірку на виписаних парах (`--self-test`).
4. **Джоба `check` на кожну зміну PR** (відкриття, пуш, зміна опису): самоперевірка скрипта і назва майбутнього тегу в підсумку прогону. Недопустима назва або назва, яку вже має наявний тег, — червоний чек до мержу. Чек не обов'язковий.
5. **Наявний тег workflow не пересуває.** Тег уже стоїть на тому самому коміті — прогін зелений без змін; на іншому — червоний.
6. **Запасний шлях — ручний запуск** (`workflow_dispatch`, входи `tag` і `sha`): повний sha на 40 знаків, коміт має бути в історії `main`. Для випадку, коли подія мержу не спрацювала, і для тегу на коміт, змержений раніше. Запускає сесія агента (запуск workflow їй дозволено) або власник.
7. **Права.** Workflow загалом — `contents: read`; лише джоба `tag` має `contents: write`. Код скрипта вона бере з `main` після мержу, не з гілки PR. Теги релізів `vN.N.N` (ADR-0054/0055) і `phaseN-complete` цей workflow не ставить.
8. **Рядок тегу — у PR кроку, без sha.** Запис кроку в `docs/workflow.md` містить «Тег `iter-X.Y` — на merge-коміті PR #N (workflow `iter-tag`)»; sha merge-коміту видно з PR і з тегу. Окремий PR рядка тегу більше не потрібен.
9. **Правило AGENTS.md** «теги `iter-X.Y` — після валідації людини, не в сесії агента» читається так: тег ставить workflow після мержу; мерж змістовного PR — лише після «схвалюю» власника (ADR-0052), тож тег без валідації людини не з'являється.

## Наслідки

- На крок у власника лишаються відповіді на питання і «схвалюю». Доступ до теки, пуш тегу і другий PR зникають.
- Сесія перевіряє тег після мержу без клону: `git ls-remote --tags https://github.com/sergkarpenko/rubezh.git iter-X.Y`.
- Тег з'являється одразу після мержу. Якщо власник хоче подивитись змінене на основному сайті до тегу, він каже про це до «схвалюю» — тоді PR іде без рядка `Iter-Tag`, а тег ставиться ручним запуском.
- Помилку в назві після мержу сесія не виправить: видалити чи пересунути тег вона не може, це лишається дією власника. Від цього захищає джоба `check` — назву видно до мержу.
- Тег, створений вбудованим токеном workflow, інших workflow не запускає. Для `iter-*` їх і немає (`tag-version` слухає лише `v*`).
- PR із форку отримує токен лише на читання: джоба `tag` на ньому буде червоною, тег не з'явиться. Розробка йде гілками самого репозиторію, для форку лишається ручний запуск.
- Локальний клон власника тегів не отримує, поки власник не зробить `git fetch --tags`; для процесу це не потрібно.
- Перше живе спрацювання — мерж PR самого кроку Т.34 (`Iter-Tag: iter-T.34`). До нього перевірено: самоперевірку скрипта, кроки workflow на заглушці `gh` (13 випадків, `docs/reports/t34-iter-tag.md`), джобу `check` на PR.

## Альтернативи

- **Тег із сесії через REST** — перевірено першим, відхиляє проксі сесії (див. «Контекст»).
- **Назва тегу з назви гілки або заголовка PR** — відкинуто: гілки називаються довільно (`fix/…`, `docs/…`), а в серії PR тег несе лише останній; явний рядок в описі не вгадує.
- **Мітка PR замість рядка** — відкинуто: мітку на кожен крок треба спершу створити в репозиторії; рядок в описі сесія пише сама.
- **Workflow сам дописує рядок тегу в `docs/workflow.md`** — відкинуто: запис у `main` в обхід PR (ADR-0028; те саме заперечення, що в ADR-0084).
- **Тег на пуш у `main` за текстом merge-коміту** — відкинуто: текст merge-коміту GitHub складає з номера PR і назви гілки, назви кроку в ньому немає.
- **Лише ручний запуск** — лишено запасним шляхом: основним він додав би сесії дію і очікування на кожен крок.
