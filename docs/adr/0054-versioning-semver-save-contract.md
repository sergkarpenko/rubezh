# 0054. Версіонування релізів — semver із сейв-контрактом

- Статус: accepted (методику затвердив власник у сесії 2026-10-16: «затверджую, дрібниця бонус — подобається»; мерж PR = формальна фіксація, конвенція ADR-0030)
- Дата: 2026-10-16
- Доповнює: ADR-0023 (merge = «схвалюю»), ADR-0028 (доставка гілкою + PR), ADR-0050 (схвалення одним власником), ADR-0052 (апрув у сесії; теги на merge-комітах), ADR-0043 (нумерація пX.Y)
- Автор: Vibe Code (методику запропоновано в сесії П9.5, затверджено власником)

## Контекст

MVP вийшов як v0.1.0 (тег на merge-коміті, GitHub Release, Pages). Питання власника (2026-10-16): адаптувати semver під проєкт, піднімати номери автоматично — згода власника потрібна один раз на методику, далі виконують агенти; формалізувати й назви етапів.

Особливості проєкту: гра деплоїться одним артефактом на Pages (без бекенду, без публічного API); «споживач» версії — гравець із сейвом у localStorage; реліз = тег + GitHub Release на merge-коміті (ADR-0052). Для гри сейв — це і є публічний контракт: головне питання гравця до версії — «чи відкриється мій сейв».

## Рішення

1. **Схема — semver із сейв-контрактом** `MAJOR.MINOR.PATCH`:
   - **MAJOR** — несумісність сейв-формату або правил кампанії (навіть до 1.0; відхід від букви semver «0.x може все» — свідомий, зафіксовано тут);
   - **MINOR** — нові фічі та зміни балансу/правил, сейв-сумісні (гравець відчуває зміни);
   - **PATCH** — багфікси шару відображення і рефакторинг без зміни поведінки (байт-у-байт логи, ADR-0003);
   - **1.0.0** — фриз сейв-формату і заява стабільності; окреме рішення власника.
2. **Реліз-крок** — кожна фаза завершується явним реліз-кроком `Реліз vN.N.N` (останній крок фази в нумерації пX.Y, ADR-0043): агент у реліз-PR піднімає `version` у package.json, пише нотатки Release; merge-коміт реліз-PR = якір тегу (урок П8.5); тег `vN.N.N` + GitHub Release — після валідації власника, виконання механічне (патерн ADR-0052).
3. **Згода власника — один раз на цю методику** (цей ADR); далі агенти піднімають номери без окремого апруву на кожен bump. Публікація Release лишається за валідацією власника (ADR-0023) — «автоматично» означає «агент виконує механічно за затвердженою методикою».
4. **Мапінг ліній кроків на тип релізу**:
   - фіча-фаза (`пX.Y`) → MINOR;
   - тунінг балансу/правил → MINOR;
   - рефакторинг (`пR.Y`, байт-у-байт) → PATCH або без релізу;
   - багфікси шару відображення (`fix/*`) → PATCH (збираються в PATCH-реліз між фазами);
   - технічні задачі (`Т.Y`) → без релізу;
   - зміна сейв-формату → MAJOR.
5. **Версія видима гравцеві**: екран «Як грати» показує «Версія N.N.N»; число читається з package.json на збірці (vite define), без дублювання в текстах (урок П9.1). Реалізація — перший пост-MVP крок.
6. **CI-гейт звірки «тег ↔ version у package.json»** — відкладено як кандидат на майбутнє Покращення за окремим рішенням власника (прецедент Т.1: спершу чесна методика, потім автоматизація гейту).

## Наслідки

- Версія чесно відповідає на питання гравця про сейв; релізи перестають бути ad hoc («який merge стає релізом» визначає план фази, а не пам'ять).
- Реліз-крок додає один docs-PR (плюс bump package.json) на фазу — прийнятна ціна за передбачуваність.
- CI-автоматизація підйому версії (release-please-стайл) відкинута: merge-коміти розмивають conventional-історію, а авто-публікація Release суперечить валідації власником (ADR-0023).
- Зміна методики — лише через новий ADR із полем Supersedes.

## Альтернативи

- Класичний pre-1.0 semver (0.x без обіцянок) — відкинуто: версія нічого не говорить гравцеві про сейв.
- Календарна схема (2026.10 / MVP.N) — відкинуто: не semver, погано масштабується.
- Повна CI-автоматизація (Workflow сам рахує версію з conventional-комітів і публікує Release) — відкинуто: нові залежності (ADR-0012), новий workflow (ADR-0018), публікація без валідації власника.
