# ADR-0043: Схема нумерації задач (пX.Y)

**Статус:** Proposed  
**Дата:** 2026-10-15  
**Автор:** Vibe Code  
**Замінює:** -  
**Суперседе:** -  

---

## Контекст

Попередні ADR (ADR-0023, ADR-0030) описували формат планування, але не чітко визначали схему нумерації задач для AI-агентів. Виникла потреба в уніфікованій системі нумерації, яка б дозволяла чітко ідентифікувати етапи розробки.

Згідно вимог користувача:
- Наступний промпт в новій сесії повинен бути `п8.Х`
- Агент уже працює над етапом
- ADR не оновлюємо, а створюємо новий

---

## Рішення

### 1. Формат нумерації

**Формат:** `пX.Y` де:
- `п` - префікс, що означає "phase" (фаза/етап)
- `X` - номер фази (мажорна версія)
- `Y` - номер етапу в фазі (мінорна версія)

**Приклади:**
- `п8.1` - етап 1 фази 8
- `п8.2` - етап 2 фази 8
- `п8.3` - етап 3 фази 8
- `п9.1` - етап 1 фази 9

### 2. Правила нумерації

1. **Фази (X):**
   - Фаза = великий блок робіт (наприклад, розробка нової фічі)
   - Нумерація фаз починається з 1 і збільшується послідовно
   - Кожна фаза має чітку мету (наприклад: "Розробка кампанії", "Додавання UFO")

2. **Етапи (Y):**
   - Етап = частина фази, яка може бути реалізована за одну сесію
   - Нумерація етапів в межах фази починається з 1
   - Кожен етап має конкретну задачу (наприклад: "UI кампанії", "Логіка перемоги")

3. **Послідовність:**
   - Етапи в фазі виконуються послідовно: п8.1 → п8.2 → п8.3
   - Не можна переходити до п8.3, не завершивши п8.2
   - Кожен етап залежить від попереднього

### 3. Життєвий цикл етапу

```
1. Користувач дає промпт: "п8.3"
2. Vibe Work:
   - Читає workflow.md, AGENTS.md
   - Аналізує поточний стан репозиторію
   - Перевіряє, чи завершено п8.2
   - Створює план для п8.3 в docs/ (EARS-format)
   - Створює нові ADR (якщо потрібно)
   - Оновлює workflow.md з планом п8.3
   - Комітить: docs(workflow): п8.3 - план етапу
3. Користувач перевіряє та підтверджує план
4. Vibe Code:
   - Читає план п8.3
   - Реалізує код згідно плану
   - Створює PR згідно ADR-0028
   - Тестує, комітить, пушить
5. Користувач мержить PR
6. Етап п8.3 вважається завершеним
```

### 4. Документування етапів

Кожен етап **обов'язково** документується в:
- `docs/workflow.md` - загальний опис етапу
- `docs/adr/` - архітектурні рішення для етапу (якщо потрібно)
- `AGENTS.md` - оновлення правил (якщо потрібно)

**Шаблон документації етапу:**
```markdown
### п8.3: [Назва етапу]

**Мeta:** [Короткий опис мети]
**Залежності:** п8.1, п8.2
**ADR:** [Список пов'язаних ADR]
**Результат:** [Що буде зроблено]

#### План:
1. [Крок 1]
2. [Крок 2]
3. [Крок 3]

#### Критерії прийняття:
- [x] Критерій 1
- [x] Критерій 2
```

### 5. Вимоги до ADR

- **ADR не оновлюємо** - лише створюємо нові
- Кожен новий ADR має унікальний номер
- Нумерація ADR не перетинається з нумерацією етапів
- ADR пов'язані з етапами через згадки в документації

## Наслідки

### Переваги

1. **Чітка ідентифікація** - кожен етап має унікальний ідентифікатор
2. **Послідовність** - чітка залежність між етапами
3. **Документованість** - усі етапи фіксуються в репозиторії
4. **Передбачуваність** - зрозуміло, який етап йде далі

### Недоліки

1. **Жорсткість** - важко змінити послідовність етапів
2. **Додаткова документація** - потрібно документувати кожен етап

### Ризики

1. **Плутанина нумерації** - якщо етапи нумеруються не послідовно
2. **Залежності** - якщо етап залежить від не завершеного попереднього

## Ревізія

Це рішення може бути переглянуте, якщо:
- Виникне потреба в більш гнучкій системі нумерації
- Зміняться вимоги до процесу розробки
- З'явиться можливість автоматичної нумерації
