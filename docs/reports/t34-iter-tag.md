# Т.34. Тег кроку без дій власника

Дата: 2026-11-14. Рішення — ADR-0093. Код гри не змінювався.

## Що було

Кожен крок технічної лінії з Т.5 закривався так:

1. власник пише «схвалюю», сесія мержить PR;
2. власник дає сесії доступ до теки локального клону;
3. сесія ставить там тег `iter-T.N`, власник пушить його;
4. сесія відкриває другий PR — рядок тегу з sha merge-коміту — і мержить його після чеків (ADR-0057).

За журналом кроків Т.15–Т.33 кроки 2 і 3 — це дві дії власника і 2–12 хвилин очікування на кожен крок; крок 4 — ще одне коло чеків.

## Перевірка: чи може тег поставити сама сесія

Ні. Обидва шляхи відхиляє проксі хмарної сесії (перевірено 2026-11-14 на пробній назві `probe-t34`, тег не створено):

| Шлях | Відповідь |
| --- | --- |
| `POST repos/sergkarpenko/rubezh/git/refs` (`ref=refs/tags/probe-t34`) | 403 «Write access to this GitHub API path is not permitted through this proxy» |
| `git push origin <sha>:refs/tags/probe-t34` | 403, «the remote end hung up unexpectedly» |

Урок Т.5/Т.6 чинний, тому потрібен workflow.

## Що зроблено

- `.github/workflows/iter-tag.yml` — лише виклики скрипта:
  - джоба `check` — на відкриття PR, пуш і зміну опису відкритого PR: самоперевірка скрипта і назва майбутнього тегу в підсумку прогону; недопустима або зайнята назва чи помилка запиту про тег — червоний чек; згадка `Iter-Tag` без правильного рядка — попередження;
  - джоба `tag` — після мержу PR у `main` або вручну (`workflow_dispatch`, входи `tag` і `sha`): ставить тег на merge-коміт через `POST /git/refs`; лише вона має `contents: write`.
- `scripts/iter-tag.sh` — уся логіка: назва тегу з рядка `Iter-Tag:` опису PR, перевірка назви і sha, режими `--preview`, `--plan`, `--put`, самоперевірка `--self-test`.
- ADR-0093; правила в `AGENTS.md` (мережеві дії, крок 4 завершення сесії, рядок таблиці ADR) і в `docs/workflow.md` (правило 8, розділ «Теги ітерацій», позначка на уроці Т.5/Т.6, запис кроку).

Як це виглядає для кроку: в описі PR — рядок `Iter-Tag: iter-T.N`; у записі кроку в `docs/workflow.md` — «Тег `iter-T.N` — ставить workflow `iter-tag` на merge-коміт PR #N». Після «схвалюю» сесія мержить PR і перевіряє тег командою `git ls-remote --tags`. Другого PR немає.

## Перевірки до мержу

### Самоперевірка скрипта (`sh scripts/iter-tag.sh --self-test`)

47 випадків, усі зелені в `dash` (це `sh` на раннері) і в `bash`. Її запускає джоба `check` на кожному PR.

| Група | Випадків | Що перевіряє |
| --- | --- | --- |
| назва з опису PR | 18 | рядка немає; CRLF; пробіли; той самий рядок двічі; порожній рядок поруч зі справжнім; рядок не з початку, з відступом, з іншим регістром ключа (не рахуються); дві різні назви, `v0.5.0`, зайве слово, `;id`, `/`, зворотні лапки (помилка) |
| назва і sha | 12 | `xiter-T.34`, `iter-`, `ITER-T.34`, кирилична «Т», `.lock`, дві крапки, другий рядок у назві; sha короткий, великими літерами, з другим рядком |
| джоба `check` (`--preview`) на заглушці `gh` | 5 | без рядка; нова назва; назва зайнята; недопустима назва; помилка API не читається як «назва вільна» |
| джоба `tag`, план (`--plan`) на заглушці | 7 | мерж без рядка; мерж з рядком; вручну; короткий sha; погана і порожня назва; коміт не в `main` |
| джоба `tag`, запис (`--put`) на заглушці | 5 | тегу немає — одне створення; легкий і анотований тег на тому самому коміті — без створення; тег на іншому коміті і помилка API — помилка без створення |

Заглушка `gh` — функція `stub_gh` у самому скрипті: відповідає за наявний тег (легкий, анотований, 404, інша помилка) і за порівняння з `main`, рахує створення.

### Навмисні поломки скрипта

19 поломок по одній (копія скрипта, заміна одного місця, самоперевірка): 18 дають червону самоперевірку — регулярний вираз без `^`, `+` → `*`, `grep -i`, без перевірки `.lock`, без перевірки другого рядка, дозволений відступ, порожні значення, будь-яка помилка API як 404, анотований тег без розіменування, sha без довжини і без набору знаків, `compare` без перевірки, зайнятий тег не зупиняє `--preview`, `--put` пересуває тег, не створює, створює повторно, ручний запуск бере назву з опису, `--plan` не пише вихід. Одна вижила і нічого не міняє: якщо дозволити кілька різних назв, їх відхиляє перевірка «назва — один рядок».

### На живому репозиторії (лише читання)

- `compare/d9ab9b7d…e57c...main` → `ahead`; `compare/6bbff273…21a7...main` → `identical`;
- `git/ref/tags/iter-T.3` → 404 (пошук точний, не за початком назви);
- `--preview` з `Iter-Tag: iter-T.33` → помилка «уже існує (коміт `d9ab9b7d…`)»; з `Iter-Tag: iter-T.34` → «буде поставлено»;
- `--put` для анотованого `iter-13.1` і його коміту `263651bf…` → «уже стоїть, без змін», запису немає (серед тегів `iter-*` дев'ять анотованих);
- джоба `check` на PR #327 — зелена.

## Аудит (експеримент Т.34–Т.36)

Аудитор — субагент Claude Opus без контексту сесії: диф, звіт, `AGENTS.md`, `docs/workflow.md`, опис PR. ≈ 3,5 хв, ≈ 115 тис. токенів. Десять знахідок, усі підтверджено; виправлено в цьому ж PR.

## Межі

- Джоба `tag` до мержу цього PR наживо не запускалась: перше живе спрацювання — мерж самого PR Т.34. Не перевірено наживо: чи подія `closed` запускає workflow, доданий цим самим PR; чи вистачає джобі права `contents: write` за налаштувань репозиторію; чи немає правила захисту тегів. На ці випадки є ручний запуск, а якщо не спрацює і він — тег ставиться по-старому, у теці власника.
- Самоперевірка на заглушці `gh` перевіряє логіку скрипта, а не вирази `if:` джоб, підстановку `${{ … }}` і справжні відповіді API на запис.
- Помилку в назві після мержу сесія не виправить: видалити чи пересунути тег може лише власник. Захист — чек `check` до мержу; він не обов'язковий.
- `scripts/` поза `tsc`, lint і тестами (урок Т.25): самоперевірку скрипта запускає лише джоба `check`, і вона не обов'язкова.
- Тег з'являється одразу після мержу, до перегляду основного сайту власником.
