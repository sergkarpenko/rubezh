## Звірка скіла і контексту проєкту `rubezh` у Mistral

Що бачить сесія в Chrome власника (`chat.mistral.ai`, розділ Code, 17.11.2026):

- **Інструкція проєкту** `rubezh` (вкладка Context): один рядок англійською — гобі-проєкт, стратегія, AI-native SDLC. Вказівок немає, з планом не розходиться. Підключений репозиторій — `sergkarpenko/rubezh`.
- **Скіл `rubezh-session`** (Skills, «Created by me»): увімкнений; у сесії Code його видно в меню поля повідомлення («+» → Skills → Personal). Опис: завантажувати на початку кожної Work-сесії про «Рубіж»; там само — «Кодові сесії … веде Vibe Code (VS Code) … — він цей скіл і тему знань не бачить». Чи підтягує Vibe Code скіл сам, за описом, сторінки не кажуть.
- **Сесія виконавця Т.61** від першого повідомлення: за репліками агента перші дії — `git` і читання плану; рядка про завантаження скіла не видно (кроки інструментів у вікні згорнуті — межа (а)).

Розбіжності тексту скіла з шаблоном, `docs/agents/common.md` і `AGENTS.md`:

| № | Скіл (переказ) | Чинне | Наслідок, якщо виконавець скіл завантажить |
| --- | --- | --- | --- |
| 1 | Vibe Code працює у VS Code і скіла не бачить | Vibe Code Web — у тому ж акаунті, скіл був увімкнений і стояв у меню сесії Code | припущення скіла про власну невидимість хибне |
| 2 | Початок сесії: прочитати тему знань «Рубіж», звірити з репозиторієм, узяти перший пункт «Наступні кроки» теми | Vibe Code не планує (`AGENTS.md`, ADR-0042); рішення власника 15.11: «Vibe: планування не давати»; крок і план дає сесія Claude | самостійний вибір кроку замість плану; тема знань з кроками Т.* не синхронізована |
| 3 | Тег `iter-X.Y` ставить власник після валідації | тег ставить workflow `iter-tag` за рядком `Iter-Tag:` в описі PR (ADR-0093) | хибне твердження про тег у документах кроку |
| 4 | Синхронізація теми знань після фази — дописати тему | план про тему знань нічого не каже | зайва робота поза репозиторієм |
| 5 | Зміни ядра: тести → коміт → CI зелений → валідація людиною | мерж — за класом PR (ADR-0094) і після аудиту (ADR-0097) | «CI зелений» як підсумок — близько до вади Т.61 (чеки CI записано як аудит) |

Вказівок пушити після PR чи писати про аудит у скілі немає. Інструкцію проєкту сесія не змінювала. Про скіл — питання власникові кнопками (після відкриття PR, поки йшов аудит): «вимкнути / переписати під процес Т.* / лишити як є». Відповідь власника (17.11.2026): «Вимкнути (Рекомендовано)». Сесія вимкнула перемикач «Enable skill» скіла `rubezh-session` у Chrome власника; після перезавантаження сторінки Skills він вимкнений. Текст скіла не змінено — увімкнути назад можна тим самим перемикачем.

## Перевірка

- `parsePlan` зі `scripts/vibe-plan-check.mjs` на новому шаблоні і на шаблоні з `main` (`d066deb`): назва PR, рядок тегу, відповіді власника, шлях і розділи звіту, терміни, заголовки й `afterAudit` (`false`) — ті самі; змінились лише слова, цитати, вказівки поза блоками і місця для заповнення (8 → 17: чотири місця виконавця замість одного місця-переліку і, за знахідкою Mistral, сім названих місць планувальника в блоках замість голого `<…>`).
- Шаблон із заповненими `<ім'я>`, `t<NN>` і `<N>` (у тимчасовому робочому дереві з комітом) — `vibe-plan-blocks.mjs` вирізає 5 блоків; блок `pr-body` з незаповненими місцями виконавця — `vibe-plan-check.mjs --title … --body-file …` показує всі три місця виконавця цього блоку як «незаповнене місце плану», після заповнення — жодного з них (лишаються лише місця планувальника шаблону); четверте місце, `<скільки червоних із скількох>`, — у блоці `record`: його скрипт показує в доданих рядках запису кроку (перевірка аудитора).
- Той самий план із дописаним розділом `## Після аудиту: порції (…)` — скрипт переходить у стан «після» і показує «Аудит ще не проведено» в описі PR; сам шаблон лишається в стані «до» (назва розділу в ньому — у тексті пункту, не заголовком).
- `rm -rf dist && node scripts/agents-docs-check.mjs` — розбіжностей немає.
- Коду гри, тестів і `.github/` PR не чіпає: чекліст коду не потрібен, обов'язкові чеки — у CI.

## Межі

- (а) Чи завантажує Vibe Code скіл `rubezh-session` сам, не встановлено: у вікні сесії Т.61 кроки інструментів згорнуті, старі повідомлення вантажаться прокруткою; на початку сесії видимого завантаження немає.
- (б) Шаблон перевірено розбором скриптів, а не живим кроком Vibe: чи виконавець утримається від пушу після PR і чи вставить таблицю файлом — покаже перший крок за новим шаблоном.
- (в) Місце з назвою кирилицею, заповнене вигаданим текстом, скрипт від правильного не відрізнить — як і раніше (межа (в) звіту Т.62); це закриває звірка дифа з прототипом планувальника.
- (г) Перелік кандидатів сесії Claude (документ проєкту claude.ai) оновлюється поза репозиторієм.

## Аудит

Mistral Large (джоба `mistral-audit`): на коміті `e561e80` — «Знахідок немає»; на коміті виправлень `8674391` — знайдено 1, підтверджено 1 (нижче, 10).

Підтверджені — що зроблено (комітом після аудиту):

1. Новий пункт «після PR нічого не пушити» суперечив старому «знахідка звірки — один коміт» — коміт за знахідкою звірки тепер без пушу, пуш — із першою порцією знахідок.
2. «Показує всі чотири» місця виконавця в блоці `pr-body` — їх там три, четверте — у блоці `record` — розділ «Перевірка» виправлено.
3. Про скіл сказано більше, ніж побачено («став видимим виконавцеві»), цитата «Vibe Code скіла не бачить» — не дослівна, дата «13.10» — припущення — запис кроку і довідник переписано: «стояв у меню сесії», без цитати і дати.
4. «Знахідки 1 і 5 аудиту в записі Т.61» — запис Т.61 знахідок не нумерує, вони в розділі «Аудит» звіту Т.61 — виправлено в шаблоні, звіті й довіднику (там рядок з Т.62).
5. Блоки `record` і `pr-body` давали «<число рядків> рядків» з неузгодженим відмінком — форма «рядків у підрахунку — <число рядків>».
6. Причина нової теки для блоків `-v2` («не затерти опис PR») хибна — опис лежить у `/tmp/pr-body.md` — названо справжню, додано `/tmp/pr-body-v2.md` і `gh pr edit`.
7. Неясно, як видавати порції, — усі одним комітом у план, далі «роби порцію K» повідомленням.
8. Місце в зворотних лапках скрипт теж не бачить, а `grep` ловив лише `<…>` — місця виконавця поза зворотними лапками, `grep -nP` і для `<...>`.
9. «≈ 10 с» проти «≈ 11 с», застаріле «виконавець може запушити ще один коміт», «сценарій прожене CI» проти «про чеки CI не писати» — узгоджено; разом із цим — кома у вступі шаблону і місце рядка «Виконано» в записі Т.62 (перед «Звіт», як у Т.59–Т.61).
10. (Mistral, `8674391`) Новий пункт забороняє голе `<…>` у блоках, а блоки `limits`, `record` і `pr-body` самого шаблону його ще мали (місця планувальника) — третім комітом вони названі (`<мета кроку>`, `<що змінено і чому>` тощо); у вирізаних блоках заповненого шаблону `grep -nP` — порожньо.
