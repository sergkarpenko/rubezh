# Шаблон плану кроку для Mistral Vibe Code

Шаблон для агента, що планує крок, який виконає інший агент (Mistral Vibe Code). Зібраний із планів і записів Т.39 і Т.51 та довідника `docs/agents/common.md` (розділ «Крок, який виконує інший агент»); уточнений за кроками Т.53 і Т.55 (Т.56) і за Т.58 та залишками Т.58 (Т.60). Це не правило: правила — `AGENTS.md`, `docs/workflow.md` і ADR.

**Як користуватись.** Скопіювати файл у `docs/plans/tNN-<суть>.md`, прибрати цей вступ і розділи «Перед тим як віддати план» та «Після PR», заповнити все в кутових дужках `<…>` і прибрати підказки курсивом. Розділи плану не викидати: якщо розділ не потрібен — лишити заголовок і написати «немає». План — перший коміт гілки кроку.

**Готові блоки (Т.60).** Усе, що виконавець додає дослівно — рядки коду з коментарями, тест, готовий текст документів, опис PR, — у плані лише блоками: рядок-позначка `<!-- блок: ім'я -->` і огорожа одразу після неї (` ```ts ` для коду, ` ```text ` для тексту; якщо всередині є огорожа — зовнішня з чотирьох зворотних лапок). Блоки вирізає один скрипт — і для виконавця, і для прототипу планувальника: `node scripts/vibe-plan-blocks.mjs <план> /tmp/blocks` пише кожен блок у `/tmp/blocks/<ім'я>.txt` (вміст огорожі без кінцевого переносу рядка) і відмовляє (код 1), якщо позначку написано з помилкою чи без огорожі, ім'я повторюється або має щось, крім латинських літер, цифр, `.`, `_` і `-`. Старих файлів у теці скрипт не видаляє — брати нову або порожню теку. Вказівки виконавцеві — поза блоками: усе всередині блоку він переносить дослівно, усе поза ним — ні.

## Обмеження

- **Розмір:** оцінка — <число> рядків коду і <число> рядків тестів, <один PR | серія з K PR>. <Якщо власник схвалив плановане перевищення 500: «відхилення записано тут, один PR, мітку `size-deviation` ставить виконавець (ADR-0061, ADR-0077)».> Інакше: якщо виходить понад <поріг> рядків — написати про це в сесії до того, як продовжувати; без запису про відхилення в цьому плані мітку `size-deviation` не ставити.
- **Не чіпати:** <файли і теки>.
- У доданих рядках (код, коментарі, тести, документи) немає трансліту — лише кирилиця.
- Тести не послаблювати, щоб пройшли.
- Історію не переписувати (без amend, rebase, force-push).
- **Працювати короткими кроками:** одна правка — одна перевірка — коміт. Великий документ писати частинами, а не обмірковувати цілком.

## Чекліст перед PR

`npx tsc --noEmit`, `npx tsc --noEmit -p tsconfig.core.json`, `npx tsc --noEmit -p tsconfig.e2e.json`, `npm run lint`, `npm run format:check`, `npm test`, `npm run docs`, `npm run test:e2e`.

Крок не зачіпає сценарій e2e (`e2e/` і те, що він клікає):> на e2e в пісочниці — **не більше 10 хвилин** (підготовка браузера — у розділі «Лише для Mistral Vibe Code» довідника); не піднявся або падає так само на чистому `origin/main` — написати про це у звіті й в описі PR і йти далі: сценарій прожене CI. <Крок зачіпає сценарій e2e: e2e обов'язковий (`AGENTS.md`); планувальник пише тут, як виконавець його проганяє і що робити, якщо пісочниця не дає.>

## PR

- **Документи кроку закомітити до відкриття PR** (звіт, запис кроку, рядки довідника): перед `gh pr create` команда `git log --oneline origin/main..HEAD` показує коміт із ними.
- PR у `main`, **не чернеткою**. Назва — **дослівно, скопіювати**: `<тип>(<область>): Т.<N> — <назва>`.
- Опис PR — **увесь, дослівно** блоком `pr-body`: скопіювати `/tmp/blocks/pr-body.txt` у `/tmp/pr-body.md` і заповнити місця `<…>` там (повторний запуск вирізача перезаписує `/tmp/blocks`): <перелік місць — результати чекліста, число рядків, числа звірки>. Перед відкриттям PR `grep -n '<[^!]' /tmp/pr-body.md` нічого не знаходить. Рядок `Iter-Tag` — з початку рядка, без відступу. Розділів понад ці не додавати; розділ «Аудит» до аудиту каже «Аудит ще не проведено», після аудиту його текст дає планувальник.

<!-- блок: pr-body -->
```text
### Що змінено і чому

<…>

### Критерії приймання

<…>

### Відповідь власника (<дата>)

Питання: «<питання дослівно>». Відповідь: «<відповідь дослівно>».

### Перевірка

<результати чекліста; число рядків; числа звірки скриптом — місця для виконавця>

### Аудит

Аудит ще не проведено.

Згадка: <Т.NN, PR #NNN>; план — `docs/plans/t<NN>-<суть>.md`.

Iter-Tag: iter-T.<N>
```

- Перед відкриттям PR, коли документи кроку вже закомічено, запустити звірку з планом разом із готовими назвою й описом: `node scripts/vibe-plan-check.mjs --plan docs/plans/t<NN>-<суть>.md --title "<назва з плану>" --body-file /tmp/pr-body.md` — числа цього запуску вже в описі, з яким відкривається PR; після відкриття — ще раз із `--pr <номер>` (звіряє назву й опис PR). Кожну знахідку виправити або назвати в описі PR з причиною. **Якщо числа запуску з `--pr` інші — дописати їх в опис PR** (`gh pr edit <номер> --body-file <файл>`), **а не новим комітом**: коміт одразу після відкриття PR скасовує перший прогін чеків, а аудитор, запущений на PR, читає вже не останній коміт (Т.55). Джоба `mistral-audit` читає опис на початку прогону, тож після такої правки рядок «Опис PR змінено після цього прогону» в першому коментарі очікуваний. Якщо знахідка вимагає правки файла — один коміт і повідомлення про нього в сесії.
- Після відкриття PR — коротко відповісти в сесії: номер PR, що з чекліста не вдалося, скільки часу зайняв крок і перелік «пункт плану — зроблено / ні» з доказом `grep` на кожен рядок «зроблено». **Не мержити.**

## Після PR (для планувальника; у план не йде)

- **Підказка для запуску сесії виконавця:** «Перемкнись на гілку `<гілка>`, прочитай `docs/plans/t<NN>-<суть>.md` і виконай план. Готові блоки вирізай `node scripts/vibe-plan-blocks.mjs`, руками не набирай. Коміть у цю гілку, відкрий PR у `main`, не мерж. Працюй короткими кроками.»
- **Старт:** за 5 хв немає жодного виклику інструмента — перезавантажити сторінку, одна нова сесія, завислі зупинити, одне питання власникові, хто пише код (Т.43, Т.44).
- **Аудиторові для мержу** дати копію репозиторію і попросити запустити тести й гру (Т.39). Запускати через ≈ 5 хв після появи PR, коли `git diff --stat` гілки вже показує документи кроку: виконавець може запушити ще один коміт одразу після відкриття PR (Т.53; у Т.55 — через ≈ 2,5 хв за часом прогонів CI); інакше — дати аудиторові команду оновити копію перед читанням.
- **Звірка з прототипом:** `git diff origin/main...<гілка PR> -- . ':(exclude)docs/plans/'` проти збереженого `/tmp/proto.diff` — рядки `^[-+]` (залишки Т.58: збіг побайтний). Очікувані розбіжності — лише місця `<…>`, які заповнив виконавець; решта — перша порція знахідок.
- **Правку плану чи власних рядків** планувальник комітить у ту саму гілку перед порцією знахідок; перший пункт повідомлення виконавцеві — «спершу `git pull`» (Т.55).
- **Знахідки аудиту — порціями по три-чотири**, документи (звіт, запис кроку, довідник) з числами — окремою порцією наприкінці, з числами аудиторів і переліком «підтверджені / відхилені» готовим текстом розділу «Аудит» — блоком (`<!-- блок: … -->` у повідомленні або комітом у план), вказівки поза ним (Т.53, Т.55: ≈ 8–10 хв, один пуш). Порція документів — теж по 3–4 пункти (Т.58: порцію з дев'яти пунктів виконано наполовину без слова про пропущене). Кожна порція закінчується проханням дати перелік «пункт — зроблено / ні» з доказом `grep`; наступну порцію давати після коміту попередньої. У Т.51 десять знахідок одним повідомленням виправлялись довше, ніж робився сам крок. Ціна порцій: кожен пуш — прогін чеків і джоби `mistral-audit`; щоб не множити прогони, просити комітити кожну порцію, а пушити раз, після останньої.
- **«Thinking» без дій понад 20 хв:** зупинити хід і написати «продовжуй короткими кроками»; хто доробляє, якщо не допомогло, — питання власникові.
- **Перевірка виправлень** — власними прогонами чекліста і навмисних поломок, а не за звітом виконавця; назву PR, цитати власника, розділи звіту і терміни звіряє `node scripts/vibe-plan-check.mjs --plan <план> --pr <номер>` (Т.54; що скрипт бачить і чого ні — у звіті `docs/reports/t54-vibe-plan-check.md`).
