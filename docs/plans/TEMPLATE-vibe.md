# Шаблон плану кроку для Mistral Vibe Code

Шаблон для агента, що планує крок, який виконає інший агент (Mistral Vibe Code). Зібраний із планів і записів Т.39 і Т.51 та довідника `docs/agents/common.md` (розділ «Крок, який виконує інший агент»). Це не правило: правила — `AGENTS.md`, `docs/workflow.md` і ADR.

**Як користуватись.** Скопіювати файл у `docs/plans/tNN-<суть>.md`, прибрати цей вступ і розділи «Перед тим як віддати план» та «Після PR», заповнити все в кутових дужках `<…>` і прибрати підказки курсивом. Розділи плану не викидати: якщо розділ не потрібен — лишити заголовок і написати «немає». План — перший коміт гілки кроку.

## Перед тим як віддати план (для планувальника; у план не йде)

- [ ] Кожне твердження про наявний код і UI перевірено по коду, у плані названо `main` = `<sha>`, на якому перевірено (Т.39: план спирався на панель, якої в UI немає).
- [ ] Умова в коді записана дослівно — виразом, який можна вставити (Т.51: код вийшов правильним із першого разу).
- [ ] Сценарій наскрізного тесту відтворено на ядрі: сід, пресет, номери тіків, запасні сіди.
- [ ] Тексти UI — повними рядками, як у грі: зі знаком категорії і номером об'єкта; звірені з кодом побайтно.
- [ ] Розмір оцінено і приміряно до ліміту 500 рядків; понад 350 — поділено на PR або записано відхилення за ADR-0061 з рішенням власника (Т.39: «один PR до 500» виявився нездійсненним).
- [ ] Відповіді власника вписані дослівно, з датою; чого власник не казав — у плані позначено «рішення планувальника».
- [ ] Назва PR і рядок `Iter-Tag` вписані готовими рядками.

## Обмеження

- **Розмір:** оцінка — <число> рядків коду і <число> рядків тестів, <один PR | серія з K PR>. Якщо виходить понад <поріг> рядків — зупинитись і написати про це в сесії; мітку `size-deviation` не ставити (ADR-0061).
- **Не чіпати:** <файли і теки>.
- У доданих рядках (код, коментарі, тести, документи) немає трансліту — лише кирилиця.
- Тести не послаблювати, щоб пройшли.
- Історію не переписувати (без amend, rebase, force-push).
- **Працювати короткими кроками:** одна правка — одна перевірка — коміт. Великий документ писати частинами, а не обмірковувати цілком.

## Чекліст перед PR

`npx tsc --noEmit`, `npx tsc --noEmit -p tsconfig.core.json`, `npx tsc --noEmit -p tsconfig.e2e.json`, `npm run lint`, `npm run format:check`, `npm test`, `npm run docs`, `npm run test:e2e`.

На e2e в пісочниці — **не більше 10 хвилин** (підготовка браузера — у розділі «Лише для Mistral Vibe Code» довідника). Не піднявся або падає так само на чистому `origin/main` — написати про це у звіті й в описі PR і йти далі: сценарій прожене CI.

## PR

- Гілка — ця сама: `<тип>/t<NN>-<суть>` (план уже в ній першим комітом). Комітити в неї, Conventional Commits українською.
- PR у `main`, **не чернеткою**. Назва — **дослівно, скопіювати**: `<тип>(<область>): Т.<N> — <назва>`.
- Опис PR: що змінилось і чому; відповідь власника дослівно (з розділу вище); згадка «<Т.NN, PR #NNN>» і цього плану; результати чекліста; число рядків; і окремим рядком з початку рядка, без відступу:

```
Iter-Tag: iter-T.<N>
```

- Після відкриття PR — коротко відповісти в сесії: номер PR, що з чекліста не вдалося, скільки часу зайняв крок. **Не мержити.**

## Після PR (для планувальника; у план не йде)

- **Підказка для запуску сесії виконавця:** «Перемкнись на гілку `<гілка>`, прочитай `docs/plans/t<NN>-<суть>.md` і виконай план. Коміть у цю гілку, відкрий PR у `main`, не мерж. Працюй короткими кроками.»
- **Старт:** за 5 хв немає жодного виклику інструмента — перезавантажити сторінку, одна нова сесія, завислі зупинити, одне питання власникові, хто пише код (Т.43, Т.44).
- **Знахідки аудиту — порціями по три-чотири**, документи (звіт, запис кроку, довідник) — окремою порцією наприкінці; наступну порцію давати після пушу попередньої. У Т.51 десять знахідок одним повідомленням виправлялись довше, ніж робився сам крок.
- **«Thinking» без дій понад 20 хв:** зупинити хід і написати «продовжуй короткими кроками»; хто доробляє, якщо не допомогло, — питання власникові.
- **Перевірка виправлень** — власними прогонами чекліста і навмисних поломок, а не за звітом виконавця; назву PR, цитати власника і терміни звірити `grep` з планом.
