# Робочий процес «Рубіжу» (AI-native SDLC)

Конвенції розробки для власника і ШІ-агентів (Vibe Work / Vibe Code). Джерело правди коду, рішень, статусу і плану — цей репозиторій (ADR-0023); тема знань «Рубіж» у Vibe Work — дзеркало, яке синхронізує окрема Work-сесія (агент Vibe Code доступу до знань не має). Сесії розробки — з 2026-10-13 у Vibe Code (VS Code, локальний клон).

Структура (ADR-0074): цей файл — активний процес і статус (конвенції, теги активної фази, уроки, рішення, активна фаза); завершені фази, позафазні лінії та історичні рядки тегів — в архіві `docs/workflow-archive/` (індекс — розділ «Архів фаз» наприкінці файлу).

## AI-Native SDLC Process (2026-10-15)

This project uses an AI-native Software Development Lifecycle (SDLC) with two specialized agents:

- **Vibe Work**: Responsible for planning, design, and creating EARS-plans (ADR-0042)
- **Vibe Code**: Responsible for implementation, testing, and delivery (ADR-0042)

### Task Numbering (ADR-0043)
All work is organized in phases using the `пX.Y` format:
- `п`: Prefix indicating "phase"
- `X`: Phase number (e.g., 8 for current phase)
- `Y`: Step number within the phase

Example: `п8.5` = Phase 8, Step 5 (Bot-player simulations of the full campaign loop). Refactoring on owner request (ADR-0044) is a separate line `пR.Y`, outside the phase numbering (ADR-0049).

### Process Flow (ADR-0041)
1. Vibe Work receives prompt `пX.Y`
2. Vibe Work creates EARS-plan in `docs/plans/`
3. Vibe Work creates ADR if needed in `docs/adr/`
4. Vibe Code pulls changes, reads plan, implements
5. Vibe Code creates PR per ADR-0028
6. PR is reviewed and merged into main

### Refactoring Process (ADR-0044)
Refactoring is conducted in stages:
- **Local**: Single module improvements
- **Modular**: Multi-module reorganization
- **Global**: Architecture-wide changes

See `docs/plans/refactoring.md` and `docs/workflow-archive/linia-pr.md` (архів, ADR-0074) for details.


## Принципи

1. Одна сесія ≈ один вузький крок: одна ітерація або її частина (свідоме рішення власника — не розганяти довгий контекст).
2. Кожна ітерація: ШІ готує → локальна перевірка (сценарії-перевірки + `npm test`) → людина валідує → фіксація (коміт + тег + оновлення цього файлу).
3. Чисте ядро `src/core/` без DOM/Canvas; відображення — окремий шар (`src/main.ts`, ADR 0010).
4. Вимоги фіксуються у блоці «Рішення власника» в плані фази (вільний формат; EARS для умовної поведінки); архітектура — лише в ADR; фіча з архітектурою починається з проєкту ADR від агента на затвердження до коду (ADR-0023).
5. Кожна фаза завершується ретроспективою — окремий останній крок плану фази: уроки + процесні пропозиції; зміни процесу — через ADR (ADR-0030).

## Цикл зміни ядра

0. Нова фіча (ADR-0023): вимоги фіксує власник у блоці «Рішення власника» плану фази (EARS для умовної поведінки); агент готує проєкт ADR з відкритими питаннями і подає на затвердження — код лише після «схвалюю». Рядок плану кроку — мета + 1–3 критерії приймання; звіт — окремим підпунктом «Виконано:» під рядком.
1. Початок сесії: прочитати цей файл (активну фазу, «Наступні кроки», уроки) і `AGENTS.md`; взяти пункт з «Наступних кроків» (або вказаний власником); завершені фази — в архіві `docs/workflow-archive/` (ADR-0074), читати лише за потреби. Тему знань «Рубіж» (Vibe Work) агент Vibe Code не бачить — процес самодостатній у репо.
2. Перевірка логіки: сценарії-перевірки до коміту локальними запусками (до 2026-10-13 — пісочниця Work). Інваріанти: детермінізм (один сід + дії = той самий лог), `geo.rng` не витягається, перма-смерть наскрізна.
3. Тести: сценарії-перевірки перенести у vitest (`*.test.ts`), звірити тести з реалізацією до пушу.
4. Гілка + коміт (ADR-0028): робота одразу в тематичній гілці від актуального `origin/main` (`<тип>/<крок>-<суть>`, напр. `fix/p6.6-...`), не в локальному main. Коміт — Conventional Commits, повідомлення українською: `feat(core):`, `fix(core):`, `fix(test):`, `docs:`, `docs(adr):`, `chore(ci):`.
5. PR → CI → мерж власником (ADR-0028): пуш гілки, PR у main (опис: що, чому, критерії приймання за ADR-0023, результат локальної перевірки). Обов'язкові зелені чеки `test` (ci.yml: типи `tsc --noEmit` з тестами, ESLint, Prettier — ADR-0076; тести, покриття, збірка, docs) і `codecov/patch` (ADR-0034: patch-покриття дифа ≥ 95%) — червоний CI = стоп, фіксити до продовження. Чек `e2e` (ADR-0080) — сценарій приймання в браузері: гра проходиться від старту до результату бою, сторінка збігається з дзеркалом ядра; обов'язковий чек `main` (ADR-0082), червоний `e2e` — той самий стоп. Мерж (merge-комітом) робить лише власник = «схвалюю» (ADR-0023); після мержу — `git checkout main && git pull --ff-only`; віддалену головну гілку PR GitHub видаляє автоматично (налаштування репо «Automatically delete head branches», ADR-0056), локальну гілку й віддалені посилання чистимо `git branch -d` / `git fetch --prune`. Малі багфікси шару відображення без архітектурних наслідків (без ADR): план-рядок у workflow.md і фікс — в одному PR, без окремого план-PR (ADR-0030). Оновлюється прев'ю: https://sergkarpenko.github.io/rubezh/
6. Exact-байти: стосувалось пушів через пісочницю Work (екранування могло пошкодити вміст). У сесіях Vibe Code файли редагуються локально — крок не потрібен; правило лишається для Work-пушів.
7. Валідація людиною: сторінка з жорстким оновленням (Ctrl+Shift+R); помилки з консолі — скріншотом, фіксити наступною сесією. Обов'язковий мінімум — стандартний smoke-сценарій (ADR-0030): вибрати юніта → рух (тап-тап) → постріл у видиму ціль → дозор → рух → кінець ходу (хід прибульців) → до результату бою; геосцена: +1 тік, +1 доба, сейв → лоад; консоль без помилок. Механічну частину сценарію проходить автоматика — `npm run test:e2e` (ADR-0080, джоба `e2e` у CI); за власником лишаються вигляд, плавність анімацій і цільові пристрої.
8. Тег `iter-X.Y` на merge-коміті ітерації в main (після валідації людиною; мержі — merge-комітами, тож тег завжди на коміті з GitHub-мержу, ADR-0028).
9. Кінець сесії: оновити цей файл — чекбокси кроку, звіт «Виконано:», статуси, уроки (у тому ж коміті або одразу після). Тему знань «Рубіж» синхронізує окрема Work-сесія після завершення фази або на запит власника.

## Теги ітерацій

- Формат: `iter-X.Y` — **X: номер фази**, Y: крок фази (наприклад `iter-5.2` — Фаза 5, крок П5.2); нечислові кроки — `iter-P` (прев'ю), `iter-D` (документація).
- Перенумерація (2026-10-14, рішення власника — «теги за номером фази»): дофазний перенос (ітерації 0–5.3) — тепер `Фаза 0`, теги `iter-0.x`; тег `iter-6.1` (Dependabot-бамп `52ba70b`, не крок жодної фази) вилучено.

## Уроки (фіксуємо, щоб не повторювати)

- **Авто-ціль Codecov не є гейтом (урок П7.5):** `codecov/patch` з auto-target (99.29%) — лише інформаційний, поки не required check — PR #48 змерджено з patch 95.23% і непокритими гілками П7.4 у save.ts. Рішення — ADR-0034: `codecov.yml` з фіксованим target 95% + `codecov/patch` у required checks (дія власника в Settings → Branches). Гейт має жити в механізмі репозиторія, а не в увазі агента: сесія агента скінчена, CI — ні.

- Критичний UI-флоу без автоматичних тестів: кнопка «Кінець ходу» була зламана з ітерації 5.3 (endPlayerTurn викликав aliensTurn у хід гравця) — не спрацювала ані у CI (UI не покривався), ані у візуальній валідації людини. Правило: критичний флоу покривати DOM-тестами (jsdom, ADR-0013), людина валідує вигляд, а не логіку.
- Локальне середовище: з 2026-10-13 встановлено Node.js (Homebrew) — `npm test` запускати локально перед пушем (підтверджено: 96/96). Правило: якщо локально бракує інструмента (node, npm тощо) — одразу повідомити власника, не мовчки обходити.
- Тести до першого ранта CI не запускалися — CI упав на 3 багах тестів. Правило: звіряти тестові файли з реалізацією до пушу; CI — останній рубіж, а не перший.
- Template literals у файлах, що пишуться через пісочницю, екрануються з помилками (Syntax error у тесті детермінізму). Правило: у таких файлах — конкатенація рядків.
- TDZ на рівні модуля (виклик `newParty` до оголошення `let`) убив весь main.ts: сторінка «напівжива», помилка лише в консолі. Правило: виклики — після оголошень; при порожній сторінці дивитися консоль.
- Автопрогравання ШІ на таймерах (setTimeout у useEffect) у React-віджеті зависало; синхронний цикл в обробнику кнопки — надійніше (5.1.4).
- Гарячі клавіші розпізнавати за `ev.code` (фізична клавіша), не за `ev.key`: в українській розкладці KeyE дає «у», KeyO — «щ», і керування за ev.key ламалося б; і фільтрувати поля вводу (input/textarea/contentEditable), інакше набір сіду перехоплює клавіші (П6.4).
- Тач-патерн «тап — прев'ю, повторний тап у ту саму клітинку — хід» реалізується одним обробником `click` — окремі touch-обробники не потрібні, мишка і iPad отримують той самий патерн (П6.4, підтверджено валідацією на iPad Pro).
- Тестові клітинки бойовища підбирати під детермінований сід емпірично: A* (4 напрямки) обходить клітинки, зайняті своїми юнітами, — шлях до сусідньої клітинки висадки коштує 6 AP, а не 2 (П6.4).
- Канва без повного очищення накопичує артефакти у пікселях, які кадр не перезаписує: `renderBattle` заливав клітинки `fillRect` із проміжком 1px, маркер дозору виступав у цей проміжок — і лишався на канві назавжди (оранжеві штрихи, П6.6). Правило: кожен кадр канви починати з `clearRect` на весь buffer (патерн `renderGeo`), маркери тримати в межах клітинки юніта.
- Документи процесу розійшлися з механізмом репозиторія (ретроспектива 2026-10-14): AGENTS.md/workflow.md/ADR-0025 описували прямий пуш у main, а налаштування GitHub уже вимагали PR + approval — кожна нова сесія ламалась об захист і імпровізувала гілку (PR #11, feat/p6.3–p6.4, PR #16–#18). Правило: зміна налаштувань репозиторія (захист гілок, чеки) фіксується ADR-ом і правкою AGENTS.md/workflow.md у тому ж PR; доставка змін — лише гілка + PR, мерж власником (ADR-0028).
- Нескінченний анімаційний цикл («живий» пульс радара) суперечить правилу «idle → 0 перерисовок» (ADR-0029, батарея iPad). Рішення П6.9: пульс — подієвий, ставиться в чергу на тік часу і гасне; серія тіків («доба» = 48 тіків одним викликом) дає один пульс (coalesce за busy), а геосцена використовує другий інстанс того самого `AnimEngine` зі своєю перемальовкою `renderGeo` — патерн рушія не дублюється.
- Піксельний знак, накладений на пікселі спрайта, без темного канту губиться: золота «блискавка» дозору на світлому шоломі солдата / червоній мантії прибульця була майже непомітна навіть на 8×8 (дві ітерації П6.12a/b). Правило: контраст знака з тлом важливіший за форму — накладені знаки малювати з темним кантом і розміщувати там, де тло клітинки, а не спрайта (кутові зони; кути матриць спрайтів прозорі) — силует не перекривається.
- jsdom у vitest НАДПОВІДАЄ requestAnimationFrame — припущення П6.8 «rAF може бути відсутній у тестовому середовищі» хибне для DOM-тестів (hasRaf=true), і покрокове демо П6.16 чекало на дренаж черги анімацій недетермінованими кадрами: тести повзли до таймаутів, а мільйони кадрів журналу малювання валили кучу (OOM). Правило: у DOM-тестах, де послідовність залежить від анімацій/таймерів, стабити rAF відсутнім до імпорту main.ts (`vi.stubGlobal`) — гейт hasRaf у коді сам прибере чергу (патерн П6.8), темп крокуватимуть лише фейк-таймери; rAF-гілку покривати юніт-тестами рушія на фейковому планувальнику (render.test.ts).
- Покроковий механізм (відтворення, реплей) поруч з миттєвим — обов'язковий тест еквівалентності: та сама місія через DemoSteps і через autoBattle — лог байт-у-байт, результат і півходи збігаються (П6.16). Ловить розгортку циклів (ліміти guard, порядок умов while) швидше за візуальну перевірку; спершу міряти обсяг (скільки дій) — «689 ітерацій» одразу викривало проблему темпу, поки я не перевірив фактичні числа подій боїв.
- Рядок тегу у списку тегів workflow.md додавати в тій самій сесії, що ставить тег: iter-6.11 стояв з часів PR #30, а рядок був утрачений — розсинхрон помітили лише при закритті фази 6c.
- Статус, що залежить від мержу, фіксується в тому ж PR; таблиця фаз оновлюється тим самим PR, що закриває фазу (урок П8.1, 2026-10-15): ADR-0033 змерджено власником у PR #44, але конвенція «статус фактично стає accepted» не призначала нікому фіксації — шапка й реєстр лишалися `proposed` кілька фаз, поки PR #57 не синхронізував; Фаза 7 була завершена на П7.7, але її рядок у таблиці завис у «У РОБОТІ». Рішення: нові ADR подаються одразу `accepted` (уточнення ADR-0030), рядок фази рухає той самий PR, що відкриває/закриває фазу, а перед завершенням кожної сесії перевіряється інваріант узгодженості (чек-лист у AGENTS.md, розділ «Workflow AI-Agent», крок 6).
- Пакет процесних ADR від нестабільної сесії (2026-10-15): 13 ADR за день без звірки з фактичним станом — ADR-0039 вимагає 2 схвалень у репо з одним власником (заявляло «Заміняє: ADR-0028»), ADR-0045 носив колізію «п8.5 = рефакторинг» у власних прикладах і забороняв власнику вільні промпти, плани посилались на неіснуючі функції (calculateDamage) і вже зроблену архітектуру; «система нагород» — фіча без рішення власника (ADR-0023). Суперовано ADR-0050/0051 (пR.1), борг фіксації П8.3/П8.4 виявлено при синхронізації. Правило: ADR звіряти з фактичним станом (сутності існують, немає конфлікту з чинними ADR, рішення застосовне до реальної конфігурації репо) до мержу; пакет із понад ~3 ADR — розрізати на окремі PR, щоб власник валідував кожне рішення, а не гору.
- Гейт codecov/patch фактично авто-ціль, а не 95% з codecov.yml (пR.3, 2026-10-15): на PR #83 чек провалився з «97.77% of diff hit (target 99.38%)» при `target: 95%` у codecov.yml — фіксована ціль не застосувалась, порівняння йде з покриттям тих самих рядків у базі (~покриття репо). Правило: у рефакторинг-PR закривати 100% нових рядків тестами (3 непокриті рядки render-core.ts і 4 ai-bot.ts догнали гейт), і за рішенням власника — тести в рефакторинг-PR їдуть РАЗОМ із кодом в одному PR (патерн пR.2 «код і тести — окремі PR» для лінії пR скасовано: код-PR без тестів шнизить patch і гейтить серію). Синхронізація codecov.yml ↔ ADR-0034 — задача Т.1 (вище). За тією ж ретроспективою пR.3 (підтримано власником 2026-10-15): серії наступних глобальних етапів різати на 2–3 більші PR з тестами разом, а не 5–6 дрібних — менше координаційних точок мержу при тій самій рев'юваності.
- Причина авто-цілі codecov/patch (Т.1, 2026-10-15, ADR-0053): codecov.yml не проходив валідацію Codecov — поле `only_pull_requests` невідоме схемі, а невалідний конфіг Codecov мовчки відкидає цілком (без попередження на PR — єдиний симптом: «плаваюча» ціль чека). Правило: кожну зміну codecov.yml валідувати перед комітом — `curl --data-binary @codecov.yml https://codecov.io/validate` (має повернути `Valid!`); валідне поле для «статус лише для PR» — `only_pulls`, не `only_pull_requests`.
- Якорення тегу кроку (ретроспектива П8.5, 2026-10-15): прецеденти розходились — iter-8.4a ставився на feature-merge (`b81e210`), пR.3 — на останній контентний merge серії (`a2c993e`), конвенція ніде не була записана. - Прогноз дифа кроку — на етапі планування, а не посеред виконання (ретроспектива П11.2, 2026-10-17): крок П11.2 за критеріями (модуль + тести + сейв-інтеграція + partyTick) фізично не влазив у ліміт ADR-0036 (500 рядків, диф склав 701), і єдине звернення до власника посеред виконання було саме про це — рішення за хвилину (ADR-0052), але виконавець уже витратив цикл на пошуки штучного шву «ядро/інтеграція» і стиснення тестів. Корисний побічний ефект ліміту: стиснення тестового файла 414 → 352 рядки без втрати покриття (консолідація describe-блоків). Правило (ADR-0061, варіант «c» — рішення власника 2026-10-17): Work-сесія при плануванні оцінює прогноз дифа кроку (модуль + тести за критеріями); крок з прогнозом понад ліміт — одразу планується як серія PR (прецедент пR.3) або містить у плані явний запис «прогноз ~N рядків; відхилення від ADR-0036 схвалено планом», щоб виконавча сесія не зупинялась посеред кроку.
- Мовчазні правила моделі — фіксувати в ADR або перевіряти probe (ретроспектива П11.2, 2026-10-17): у research.ts порядок контуру доби «зарплата → звільнення неплачених → наукові точки від тих, хто залишився» детермінований і логічний, але це рішення прийнято в коментарі коду, а не в ADR-0058; на «складному» воно може дати спіраль «мало грошей → звільнення → менше точок → довші проєкти». Правило: у П11.8 probe-грід перевіряє спіраль зарплата/продуктивність на трьох пресетах; якщо спіраль є — зміна моделі (поріг невиплати) лише через новий ADR, не тихою правкою.
- «Добовий контур» зростає дубляжем лічильників (ретроспектива П11.2, 2026-10-17): межу доби патерном `geoDay(geo) − 1` + власний last*-лічильник незалежно тримають economy (lastAllowanceDay), research (lastSalaryDay), campaign (campaignTick) — працює і ізольовано, але кожен новий добовий споживач = ще один лічильник і ще один виклик у partyTick. Правило: патерн не рефакторити до появи третього-четвертого однотипного споживача (цех П11.3 — черга у тіках, не добовий); при появі — кандидат на спільний «добовий контур» (список підписок на завершену добу) лінією пR (ADR-0044).
- Vitest не перевіряє типи — типова помилка живе до typedoc у CI (ретроспектива П11.3, 2026-10-17): опечатка «гаркатний модуль» замість «гарматний» (ProjectId у research.ts) у ключах `Record<ItemId, number>` пройшла всі локальні тести (runtime-об'єкт із «зайвим» ключем консистентно використовувався і в тестах) і впала лише в `npm run docs` на CI (TS2353) — три фікс-коміти у трьох гілках серії без force-push. Правило: локальний чекліст перед пушем = `npm test` + `npm run docs` (typedoc — фактичний type-check репозиторія); рядкові ключі домену (ProjectId, ItemId) копіювати з файлу-джерела правди, не з пам'яті.
- Серія складених гілок + однакові фікс-коміти на кожній — конфлікт на останньому PR (ретроспектива П11.3, 2026-10-17): фікс опечатки комітився незалежно на кожну гілку серії #146–#148; фікс змінив «хвіст» union-типу WorkshopEvent (крапка з комою опинилась у різних місцях) — GitHub відмовив у мержі #148 (merge conflicts). Правило: перед мержем наступного PR складеної серії вливати `origin/main` у його гілку і чекати свіжого CI (прецедент #148); у фікс-комітах не чіпати рядки, які наступна гілка серії змінює.
- Механізм планованих відхилень ADR-0061 працює як задумано (ретроспектива П11.3, 2026-10-17): серія 3 PR (372/330/177 рядків) з незалежно зеленими тестами пройшла без жодного питання посеред кроку; складені гілки не вимагали чекання власника між PR — усі три мержі одним апрувом у кінці. Підтверджений патерн для наступних «великих» кроків (П11.4–П11.6 — кандидати на таку саму оцінку прогнозу дифа).
- Серія складених гілок: CI на наступних PR серії приходить лише після перенацілювання на main (ci.yml — `pull_request: branches [main]`); GitHub перенацілює автоматично, коли мерж видаляє base-гілку (ADR-0056) — мержі серії суворо послідовні: мерж → перенацілення → влиття origin/main → свіжий CI → наступний мерж (ретроспектива П11.4, 2026-10-17). Нуль конфліктів і фікс-комітів проти серії П11.3. Правило: план серії за ADR-0061 закладає послідовність мержів, паралельного CI на складених гілках нема — не мержити без свіжого CI після перенацілення.
- Чекліст «npm test + npm run docs перед комітом» (урок П11.3) дав нуль фікс-комітів у серії П11.4 — проти трьох у П11.3: усі помилки (три тестові сценарії, два файли prettier) спіймано локально до коміту (ретроспектива П11.4, 2026-10-17). Правило: до git add додати `prettier --check` на змінені файли (verify-exact-bytes.sh перевіряє байти, prettier-формат — до коміту).
- Витратники бою — стан бою `GameState.items`, а не поля Unit (П11.4, прецедент для майбутніх витратників): ядро бою не знає про ростер/склад, Unit і сейв-формат не зачіпаються (критерій «нові поля опційні» виконується тривіально — items живе лише в стані бою, сейв у бою недоступний, ADR-0026), «по одній на місцію» — прапорець у копії стану бою; місток екіпірування ↔ бій — пара deployConsumables/settleConsumables за патерном removeLostEquipment (загиблих опрацьовує перма-смерть, уцілілих — розрахунок).
- Механіка shell у workflow не покривається локальним чеклістом — «перший живий ран» і ловить її (ретроспектива П11.5, 2026-10-17): `cp -r` не створює проміжні каталоги (`dist/preview/` у білді main не існує) — упав саме перший живий запуск прев'ю, жоден локальний чек (npm test, docs, prettier, exact-байти, YAML-лінт) цю сім'ю помилок не бачить. Правило: для кроків shell у workflows, які недетерміновано відтворюються лише в Actions, план кроку закладає живий прогін одразу після мержу (прецедент: валідація П11.5 тимчасовою тест-гілкою) — «мерж = зелений CI» для CI-коду сам не є валідацією.
- Робота через прев'ю гілки — основний режим для візуальних кроків (рішення власника, ретроспектива П11.5, 2026-10-17): візуальні зміни (арт, UI — починаючи з П11.6) деплояться прев'ю гілки (ADR-0060), власник валідує у браузері ДО мержу — мерджиться лише те, що власник уже бачив живим; main лишається максимально стабільним, а «постфактум-валідація» мержем зникає як клас. Автосмок прев'ю і кореня (ADR-0062 HTTP + ADR-0063 DOM/Playwright, рішення власника у тій самій сесії) тримає наявність і живість сторінки раном, візуальну коректність — лише власник (смок свідомо без скріншот-порівнянь).
- Ретраї в смоках — необхідність, не перестрахування (ретроспектива П11.5, 2026-10-17): перший живий смок-ран дав HTTP 404 на першій спробі одразу після deploy-pages (CDN-розповзання), 200 — лише на другій: смок/health-check після деплою Pages без ретраїв дав би хибний червоний ран. Правило: будь-який смок проти свіжого Pages-деплою — з ретрай-циклом (прецедент: 5×10с у preview-branch.yml).
- Глоби інструментів тестування перетинаються — e2e-спеки з суфіксом `*.e2e.ts` (ретроспектива П11.5, 2026-10-17): глоб vitest (`**/*.{test,spec}.ts`) підбирав Playwright-спеку смоку, і юніт-ран падав на імпорті стенду — обидва ранери задовольняють `*.spec.ts`, конфлікт невидимий до першого живого прогону. Правило: файли, що належать іншому ранеру, — за суфіксом поза глобом основного (`*.e2e.ts` + явний `testMatch` у конфігу Playwright, ADR-0063); при додаванні нового інструменту тестування перевіряти взаємодію глобів юніт-ранера першим же прогоном `npm test`.
- Семантичні CSS-класи DOM — частина контракту з тестами, не «стилістика» (ретроспектива П11.6, 2026-10-17): кнопкам «Старт» каталогу досліджень дав клас `.mission` «заради жовтого акценту» — а DOM-тести чекають `button.mission` як кнопку запуску місії; цикл радара в main.ui.test.ts виходив одразу (клас вже був) і серія з 31 тесту падала каскадом. Правило: стилізаційний клас не заступає семантичний — новим кнопкам окремий клас (`.research`) з тим самим кольором у CSS; селектори тестів — рівень джерела правди поруч із розміткою.
- Ліміт ADR-0036 — на рівні PR (мережевий диф гілки), не коміту (ретроспектива П11.6, 2026-10-17): первинний коміт ч.3 серії вийшов 533 рядки — «прогноз до старту» вбереже від цього, але на місці знайшлось стиснення другим комітом (armItem замість дубльованих зведень, цикл кнопок витратників, консолідація describe) без amend: мережевий диф 500, ліміт на рівні PR витримано, історія прозора у гілці. Правило: перелимит уже закоміченого (до пуша) — підтиск наступним комітом, не rewrite історії; повторення — сигнал, що прогноз серії треба робити по-рядково до коміту.
- Режими вибору цілі витратників — гілки кліку планувати заздалегідь (ретроспектива П11.6, 2026-10-17): у зведеній аптечці клік по СОЮЗНИКУ — ціль лікування, а не вибір солдата (виняток із гілки вибору), у зведеній гранаті клік по юніту — перевибір (симетрія з пострілом); клік по власній клітинці в режимі пострілу/гранати — перевибір, тож «кидок собі під ноги» потребує порожньої сусідньої клітинки. Правило: такі ветвлення фіксувати в тестах скануванням валідних клітинок (порожня + LOS + дальність), а не фіксованими координатами — DOM-флоу тримає детермінізм без прив'язки до конкретної мапи.
- Гранулярність подій ядра — перевіряти джерелом перед підключенням відображення (ретроспектива П11.7, 2026-10-17): подія `move` виявилась «одна на клітинку шляху» (combat.ts moveUnit), а не «одна на хід»; хибна модель дала дві повернуті ітерації звуку руху (фіксована кількість кроків → «не те», відстань Чебишева події → завжди 1 → регресія до одного стуку). Правило: перед wiring відображення до подій ядра читати продюсера подій у src/core — не припускати гранулярність.
- Звуки одного дрену зливаються: серія — за однаковим currentTime батчу (ретроспектива П11.7, 2026-10-17): усі події одного дрену журналу граються з тим самим AudioContext.currentTime — постріли черги і кроки шляху без зсуву звучать одним імпульсом. Рішення: стакато-зсув лічильником серії (черга — цикл 0/0.09/0.18с; кроки — 0.14с, нова серія = новий дрен/новий currentTime, кап 16 на батч для демо-бою). Детермінізм не страждає: зсув — внутрішній стан аудіо-модуля (відображення), не стан гри; у тестах currentTime мока фіксований — серія відтворювана (ADR-0003).
- Аудіо-валідація через прев'ю — три ітерації фідбеку без жодного мержу (ретроспектива П11.7, 2026-10-17): «робота через прев'ю» (практика П11.5) поширена на аудіо: кожен фідбек власника — один коміт у гілці серії + dispatch прев'ю + смоки зелений, мерж лише після фінального апруву. Правило: сенсорні критерії (звук, а пізніше — анімація/баланс) не мають «визнаних» значень — планувати в циклі кроку місце на 2–3 ітерації прев'ю-фідбеку, серію PR на це не розтягувати (правки — коміти в гілці останнього PR серії).
- «Порожні перемоги»: перемога кампанії = вижити до 30-ї доби (ADR-0033), тому в probe-таблицях % перемог читати разом із рахунком і місіями (ретроспектива П11.8, 2026-10-18): кандидат «зарплата 25» на «складному» дав 71.7% перемог при найгіршому рахунку (1340) і 9 місіях проти 12 — дорога наука вимиває штат авто-звільненнями, партія бідніє і менше воює, але «перемагає». Правило: ручка, що піднімає % перемог падінням рахунку/активності, — не кандидат на тунінг; у probe-таблицях колонки «перемоги/банкрутства/рахунок/місії» стоять поруч завжди.
- Метрики витрат «за сумою spend-події» ламаються при збігах сум (ретроспектива П11.8, 2026-10-18): після синхронізації hirePrice з множником найм солдата і найм вченого списують однакові суми (100 × economyMultiplier) — розрізнення подій за amount у загальному журналі стало неможливим; hireSpent у party-bot тепер рахується за фактом (hiredTotal × hirePrice). Правило: нові витрати одразу міряти подією джерела (кількість × ціна з каталогу), не парсити суми загального журналу економіки.
- Probe-патч у копії репо звіряти з фактичним ефектом (ретроспектива П11.8, 2026-10-18): два «кандидати» першого grid-у (точки ×0.75/×1.25, тики цеху ×0.75) виявились непатченими — regex у харнесі не матчив формат рядка без коми, і прогони повернули таблиці, тотожні базлайну; збіг із базлайном це і викрив. Правило: «нульовий ефект» у probe — перший підозрюваний — баг патчу; кандидат із метриками, байт-у-байт рівними базлайну, перезапускати з перевіреним патчем (grep зміненого рядка) до трактування результату.
- Фаза 11 (9 кроків) — перша «велика» комбінована фаза за власним планом ADR-0058 (ретроспектива Фази 11, 2026-10-18): (1) серії складених PR (П11.3/П11.4/П11.6/П11.7/П11.8 — 2–3 PR за ADR-0061) разом з «прогнозом дифа на плануванні» (ретро П11.2) стали стандартом для кроків понад ліміт ADR-0036 — за всю фазу жодного питання власнику посеред виконання; мержі серій — суворо послідовно (retarget + влиття origin/main + свіжий CI, ретро П11.4). (2) «Валідація через прев'ю» (П11.5→П11.7→П11.9) довела до основного режиму: візуальні, сенсорні й релізні зміни власник бачить живими ДО мержу, фідбек — ітераціями комітів у гілці (звук — три ітерації без розтягування серії), «постфактум-валідація мержем» зникла як клас; реліз-крок П11.9 пройшов тим самим контуром (прев'ю → смоки → апрув → merge). (3) Probe-метод дозрів до «probe-таблиця кандидатів + одне пряме питання з варіантами» (П10.4 → П11.8), а правила читання метрик («порожні перемоги», «нульовий ефект = баг патчу») — рівень самої методики, не окремого тунінгу. (4) Реліз за ADR-0054 — другий за методикою, контур без сюрпризів (bump → прев'ю → апрув → merge-коміт → тег → гейт 7с → Release); реліз виявився природною точкою звірки «обіцяного» з «зробленим» — README відстав від фази на п'ять кроків (фічі Фази 11, найм за множником, клавіші M/G, кількість тестів), актуалізовано в реліз-PR за питанням власника. Правило: у реліз-кроці перевіряти README/сторінку «Як грати» на відповідність changelog фази.
- Прев'ю гілки — dispatch з ref main: branch policy середовища github-pages (ретроспектива П13.2, 2026-10-18): preview-branch, запущений workflow_dispatch з ref гілки, падає в deploy-джобі миттєво — нуль виконаних кроків, жодного рядка логів, deployment у середовищі github-pages зі статусом failure і порожнім description; причина — protection rule branch_policy середовища (allowlist: лише `main`), тож деплоїтися може лише ран із ref main, гілка передається входом `branch`. - Ассет-джерело під критерії приймання перевіряти чисельно ДО конвеєра (кандидат А «нічний супутник», 2026-10-22): перша генерація geo-map.jpg провалила ЖОРСТКІ перевірки виведення розкладу (острів приглушений, медіана клітинки бази (8,4) = океан; північний материк торкався обох країв X — швів не уникнути) — жодного порогу/вікна, що проходить (а)+(б): стоп-сесія за дорученням, поріг не силувався, комітів нема; друга генерація geo-map2.jpg пройшла з першого разу (океан плоско 13.0, суша 30+, темні краї) — увесь конвеєр без переробок. Правило: якщо розклад/поведінка ВИВОДИТЬСЯ з ассета, критерії приймання перевіряти скриптом на сирці до конвертації й коду (аспект кадру також міряти: 4:3 замість «16:9» з опису плану — cover змінює геометрію сітки; у другій ітерації поріг брався з фактичного розриву розподілу медіан 14.0→14.8, а не підбір під бажаний результат).

- Чисельна перевірка відображення пострілів (позафазна лінія «візуальні порівняння», 2026-10-22): (1) «юніт не намальований» шаблон-матчингом НЕ доводиться — темний кадр смерті на темному терені дає хибні 0.60 покриття на ПОРОЖНІЙ клітинці; довід — рендер-еталон тієї ж сцени без юніта (піксель-внесок 0 = байт-у-байт), покриття шаблону — лише для позитивних тверджень «яка поза/ряд/фліп намальовані»; (2) детермінізм canvas-кадру міряти регіон-хешами спрайтів/ефектів, а не повнокадровим хешем: растеризація canvas-тексту (цифри HP, fillText) нестабільна між завантаженнями сторінки (антиаліасинг глифів) і забруднює весь хеш, тоді як спрайти/трасер/терен байт-у-байт збігаються; (3) знімки подієвих кадрів короткої тривалості (трасер 150мс) — керований анімаційний адаптер у харнесі (active/now задає драйвер) замість гонитви за rAF: production-шлях відображення той самий, кадр гарантовано в потрібній фазі; (4) захисні гілки рендера, які ядро не породжує (невидимий прямий стрілець: LOS симетричний, VISION_RANGE = дальність зброї), перевіряти скаффолдом кадру (стіна на лінії пострілу — лише для відображувального кадру), не ускладнюючи ядро під тести.
- Вікно кропу «нічного супутника» виводиться з точки власника, а не підбирається на око (геосцена «сюди», 2026-10-23): цільову точку вимірювати ваговим центроїдом яскравого ядра (BT.709, luma > порогу) і від нього рахувати вікно та клітинку; простір розв'язків обмежений фіксованою геометрією (клітинка бази (8,4) = центр сцени, аспект 16:9, сирець 1024×768) і жорсткими перевірками розкладу — при масштабі мельче дрібні острови (52×36 px) розчиняються у медіані клітинки 70×70 (океан-мода 13.0), класифікація падає і поріг силувати не можна — шукати іншу точку/масштаб; яскраве ядро мису узбережжя (96×64, піки 40–61) тримає медіану бази 35.6 і проходить усі перевірки з першого разу. Спрайт-якір радара — центр клітинки (звідки виходить промінь): «радар стоїть не там» фіксується вікном КАРТИНИ, а не зсувом спрайта (дві відхилені власником ітерації зсуву вежі).
- Сурогатний гейт має сліпу зону (Т.5, 2026-11-10): `npm run docs` вважався перевіркою типів (урок П11.3), але TypeDoc виключає `*.test.ts` — у main жили 20 помилок типів у тестах, зокрема застарілий тип результату бою після П15.2 і імпорт неіснуючого `UnitSpriteView`; ESLint і Prettier існували лише в pre-commit, який процес сам дозволяв обходити `--no-verify`; ADR-0040 був accepted без файлу workflow. Правило: гейт називаємо за тим, що він перевіряє фактично, і тримаємо в required-чеку (ADR-0076/0077); ADR, що описує механізм, вважається виконаним лише тоді, коли механізм є в репозиторії — «accepted» без реалізації фіксувати як відкритий крок плану.
- Серія складених PR і автовидалення гілок (Т.5, 2026-11-10): PR Т.5b і Т.5c з першої спроби не створилися — їх відкривали командою `gh pr create --base <гілка попереднього PR>` уже після мержу Т.5a, коли base-гілку видалив автоделіт (ADR-0056). Правило: або відкрити ВСІ PR серії до першого мержу (GitHub сам перенацілить наступний на `main`, урок П11.4), або відкривати по одному проти `main` після мержу попереднього; інструкція серії називає один із двох способів явно.
- Кількісні твердження — з лічильника, не з хвоста виводу (Т.5a, 2026-11-10): перша оцінка «13 помилок типів» узята з `tsc | tail -15`; фактично 20 (`grep -c 'error TS'`) — число встигло потрапити в аналітичний документ і виправлялось. Правило: число у звіті чи плані береться з `grep -c` / `wc -l` по повному виводу; обрізаний вивід — лише для читання прикладів.
- Відтворюваність згенерованих артефактів звіряти результатом, а не байтами файла (Т.6b, 2026-11-10): повторний прогін конвертерів на іншій версії Pillow дав PNG іншого розміру в байтах (47 923 проти 47 992), але піксель у піксель той самий атлас — exact-байти (`verify-exact-bytes.sh`) тут дали б хибне «розходження». Правило: для артефактів з кодеком (PNG, WebP) критерій відтворюваності — порівняння декодованих пікселів; байт у байт порівнюються лише детерміновані текстові виходи (знімки probe, звіти JSON). Скрипт, що дав артефакт, і звіт, що на нього посилається, комітяться разом з артефактом: «untracked-скрипт» у звіті (П15.3) робить звіт неперевірюваним для всіх, крім автора.
- Файл, що переходить з untracked у git, ламає `git pull` у клоні, де він лежить невідстежуваним (Т.6b, 2026-11-10): `scripts/probe-p15.3.ts` існував локально у власника — після мержу PR #266 pull відмовив би («untracked working tree files would be overwritten»). Правило: сесія, яка додає в git файли, що вже існують untracked на машині власника, тією ж сесією звіряє локальні копії з закоміченими (диф по кожному файлу) і синхронізує клон; копії з іншими шляхами (тут — `assets-src/*.py`) прибираються після звірки, щоб не лишалось двох джерел.
- Теги з хмарної сесії агента не ставляться (Т.5/Т.6, 2026-11-10): хмарна сесія Claude пушить гілки, відкриває і мержить PR, але пуш тегів і створення ref через API її проксі відхиляє — теги `iter-T.5`/`iter-T.6` створено в локальному клоні власника, пуш — дія власника. Правило: крок «тег» у плані сесії хмарного агента формулювати як «створити локально + команда пушу власнику», рядок тегу мержити після появи тегу на GitHub; кандидат на автоматизацію (окремий ADR): тег `iter-*` ставить workflow за подією мержу.
- Новий автоматичний гейт перевіряти від супротивного до мержу: зелений прохід не доводить, що гейт щось ловить (Т.8, 2026-11-10): перша версія сценарію приймання пройшла з першого запуску — і так само пройшла на грі з навмисно зайвим кидком `rng` перед пострілом, тобто з порушеним детермінізмом. Оракул був заслабкий: після пострілу звірявся лише рядок стрільця (HP/AP від результату пострілу не залежать), а банер «3 уцілілих» збігся випадково. Після цього додано звірку HP цілі, стану всього загону після кожного ходу демонів і карток ростеру після бою (HP і вбивства кожного) — та сама поломка дає червоний крок. Правило: до кожного нового гейта (тест, лінт-правило, чек CI) — список навмисних поломок, які він мусить зловити, і прогін кожної; поломка, що лишила гейт зеленим, — дефект гейта, а не «рідкісний випадок». Прецедент того самого прийому — Т.6a (ADR-0079).
- Інструмент, що копіює проєкт у теку всередині проєкту, засмічує `npm test` (Т.10, 2026-11-11): vitest 5 виключає з пошуку тестів лише `node_modules` і `.git` — після аварійного прогону Stryker пісочниця лишилась у `dist/`, і `npm test` виконував копії тестів із неї (зокрема з тайм-аутами). `.gitignore` від цього не рятує: vitest його не читає. Правило: тимчасові копії дерева — у системній тимчасовій теці, з прибиранням за будь-якого завершення (`tempDirName`, `cleanTempDir: 'always'`, ADR-0083); після аварії інструмента перевіряти `git status` і число тестів у `npm test`.
- Тест відмови без причини помилки може проходити не з тієї причини (Т.11, 2026-11-11): у «заборонених випадках» руху шлях до зайнятої клітинки починався з несуміжного кроку — `toThrow()` без тексту ловив «Крок не суміжний», і перевірку «Клітинка зайнята» можна було прибрати з ядра; у тесті friendly fire гинули один союзник і один ворог, тож `kills === 1` виконувалось і для правила, і для його протилежності. Покриття рядків обох місць — 100 %, знайшов мутаційний прогін. Правило: у тесті відмови перевіряти причину (`toThrow('…')`) і будувати сценарій так, щоб спрацювала лише потрібна перевірка; у тесті лічильника — щоб правильне і хибне правило давали різні числа. Нові тести правил ядра перевіряти прицільним прогоном по рядках (`npx stryker run --mutate 'src/core/combat.ts:286-296'`, близько хвилини) до пушу.
- Мутант, що вижив, ще не прогалина (Т.12, 2026-11-11): у звіті Т.10 «копії в серіалізації» рахувались прогалиною, але `serializeParty` одразу віддає знімок у `JSON.stringify`, тож прибрана копія нічого не змінює — мутант еквівалентний. Справжня прогалина стояла поруч: round-trip перевірявся лише на новій партії, де лікарня, бій винищувача і рахунок кампанії мають значення за замовчуванням, і втрату цих полів тести не бачили. Правило: перед тестом на мутанта спитати, яку поведінку він ламає; для round-trip сейву заповнювати поля значеннями, відмінними від стартових.
- Довгий чек із `cancel-in-progress` перезапускається кожним пушем у PR (Т.13, 2026-11-11): фільтр `paths` у тригері `pull_request` дивиться на весь диф PR, а не на останній коміт, тож пуш самих документів скасував 4-хвилинний мутаційний прогін і почав новий на 32 хвилини. У PR, що запускає `mutation`, документацію класти в той самий пуш, що й код, або пушити після завершення прогону.
- Рядок покритий, а правило не виконується (Т.14, 2026-11-11): перебір сідів бойовища в `missionMap` (до 50 спроб, доки зона висадки не з'єднана з демонами) у тестах ніколи не йшов далі першої спроби — генератор на 8 % перешкод незв'язної мапи 20×20 практично не дає, тож тест «бойовище зв'язне» проходив би й без перевірки зв'язності. Вісім мутантів циклу вижили за покриття рядків 99 %. Правило: захисний код, до якого справжні дані не доходять, перевіряти підстановкою залежності (`vi.mock` генератора з перемикачем — решта тестів файлу працює зі справжнім), а не чекати, що вхідні дані колись його зачеплять. І вдруге після Т.11: `toThrow()` без тексту в `missionSquad(r, 0)` і в запуску місії без цілі ловив іншу помилку, кроком пізніше, — у тесті відмови називати причину.
- Зелений property-тест ще нічого не означає (Т.15, 2026-11-11): перша версія генератора партії за 100 партій не завершила жодного протоколу, не виготовила жодного предмета і не провела жодного раунду повітряного бою — твердження про науку, цех і перехоплювач перевірялись на порожньому стані й були зелені. Випадкові команди самі до глибоких станів не доходять: потрібна вага команд, вибір придатного об'єкта, розгін і макрокоманди («чекати, доки завершиться протокол», «чекати зонд на радарі»). Правило: генератор міряти лічильниками (куди дійшов), а твердження — навмисними поломками ядра (що ловить); зміну генератора без обох вимірювань не мержити. Друге: у `catch` property-тесту відмовою вважати лише `Error` з ядра — `TypeError` зі зламаного коду інакше мовчки рахується «відхиленою командою». Третє: property-тести мутантів майже не додають (6 з 1 033 понад тести-приклади за +44 % часу прогону) — їхня користь у станах, яких ніхто не будував: обидві знахідки кроку — властивості правил, а не дефекти рядка.

## Рішення

- Архітектурні рішення — ADR у `docs/adr/` (шаблон — `0000-template.md`). Записи незмінні; зміна рішення — новий ADR із полем Supersedes.
- Статус ADR (ADR-0030, уточнено 2026-10-15): новий ADR подається одразу зі статусом `accepted` у шапці та реєстрі — до мержу це чернетка у гілці, після мержу — правда в main; окремий PR зміни статусу не потрібен (урок П8.1: конвенція «статус фактично стає accepted» без власника фіксації дала дрейф ADR-0033 — PR #44 змерджено, статус лишився proposed до PR #57).
- Термінологія: «сід» (англ. seed), не «сія»; ідентифікатори англійською, коментарі українською.
- Таблиця «Статус фаз» (правило 2026-10-15, урок П8.1): рядок фази оновлює той самий PR, що відкриває або закриває фазу — ПX.1 ставить «У РОБОТІ», завершальний крок фази (валідація/ретроспектива) ставить «ЗАВЕРШЕНО» + тег `phaseN-complete` у тій самій правці. Кейс: Фаза 7 закрита на П7.7 (тег є), але рядок лишався «У РОБОТІ» до PR #57.
- Ретроспектива кроку (ратифіковано власником 2026-10-16, ретроспектива П9.1): уроки кроку фіксуються в тому ж docs-PR, що закриває крок (рядок [x] + «Виконано» + уроки в «Уроки») — одна точка мержу замість двох (патерн пR.3: менше координаційних точок мержу); якщо уроків нема — досить запису «Виконано». ### Фаза 15 «Евакуація з місії» (У РОБОТІ)

**Рішення власника (2026-10-25, Work-сесія планування П15.1):**
1. Евакуація — із зони висадки загону (SQUAD_SPAWN) у будь-який момент бою.
2. НЛО при евакуації лишається приземленим (як при поразці), премія не нараховується.
3. Бій іде, доки всі живі солдати не евакуйовані або не загинуть; «залишити» когось на полі не можна; ті, хто не дійшов до точки, — втрачені назавжди (перма-смерть наскрізна).
4. Евакуюватись можна з будь-якою кількістю живих (результат «евакуйовано» при ≥1 врятованому; 0 врятованих = чинна поразка 5.0).
5. Кутовий випадок (2026-10-25): частина загону евакуйована, останній солдат на полі знищує всіх прибульців → це ПЕРЕМОГА з премією за чинною логікою; евакуйовані в цьому випадку — уцілілі. Перемога має пріоритет над «евакуйовано».

Кандидатні рішення агента (уточнюються probe/валідацією; ADR-0075):
- Дія «Евакуація» (кнопка тулбара + клавіша V): активний солдат у клітинці зони висадки, вартість 2 AP; солдат знімається з поля у список evacuated, подія evac_unit у лог бою.
- Евакуйований не є ціллю ШІ, пострілів, гранат і реакційного вогню; ШІ діє лише щодо неевакуйованих, при 0 видимих цілях — patrol (ADR-0022).
- Завершення бою: живих на полі 0 → ≥1 евакуйований = результат «евакуйовано» (НЛО лишається, без премії, подія mission_evacuated; врятовані проходять чинний контур уцілілих — лікарня при пораненні, предмети збережені); 0 евакуйованих — чинна поразка.
- Сейв-контракт: evacuated — стан бою (сейв у бою недоступний, ADR-0026); SAVE_VERSION не росте; сейви сумісні.

EARS-критерії приймання:
1. Коли активний солдат перебуває в клітинці зони висадки (SQUAD_SPAWN) і має ≥2 AP, то команда евакуації вдається: солдат знімається з поля, подія evac_unit у лог бою.
2. Якщо солдат поза зоною висадки або не має 2 AP, то команда евакуації відхиляється з українським повідомленням причини (ядро — throw; UI показує причину без винятку в консолі).
3. Якщо всі живі солдати евакуйовані або загинули і ≥1 евакуйований, то бій завершується результатом «евакуйовано»: НЛО лишається приземленим, премія не нараховується, подія mission_evacuated у журналі партії.
4. Якщо всі солдати загинули (0 евакуйованих), то бій завершується чинною «поразкою» — поведінка 5.0 без змін.
5. Якщо солдат евакуйований, то ШІ прибульців не бачить і не атакує його; при 0 видимих неевакуйованих — patrol до зони висадки (ADR-0022).
6. Якщо евакуйований поранений, то після бою він проходить чинний контур уцілілих (лікарня за ADR-0021, предмети збережені, перма-смерть не зачіпається).
7. Сейви сумісні: формат сейву не зростає, міграція не потрібна (ADR-0026); geo.rng не витягається, траєкторія геосцени без фічі і з нею — за умови однакових дій байт-у-байт.
8. Якщо загін евакуйований, то НЛО лишається приземленим до кінця вікна посадки (чинна логіка geo.ts); місію можна спробувати повторно новим загоном.
