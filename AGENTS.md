# Rules for AI Agents (Vibe Work / Vibe Code)

**Версія:** 2.0  
**Дата:** 2026-10-15  
**Мова:** Ukrainian (коментарі, помилки, коміти)  
**Контекст:** проект "Рубіж" — AI-native SDLC

**Оновлення:** Додано чіткий розподіл ролей Vibe Work та Vibe Code (ADR-0042, ADR-0043, ADR-0044, ADR-0045-0048)

---

## Принципи роботи

1. Одна сесія = один вузький крок (див. [docs/workflow.md](docs/workflow.md))
2. Читати перед дією: ADR, workflow, поточні стан коду
3. Тестувати перед комітом: `npm test` має проходити
4. Детермінізм: Один сід + послідовність дій = той самий результат
5. **Розробка йде виключно через агентів** - репозиторій є джерелом правди
6. **Vibe Work** робить дизайн на планування фіч, **Vibe Code** виконує (ADR-0042)

## Розподіл ролей (ADR-0042)

### Vibe Work (Планування та дизайн)

- **Відповідальність:** Анализ вимог, створення планів, дизайн архітектури
- **Дії:**
  - Створення та оновлення ADR (Архітектурні рішення)
  - Оновлення workflow.md та AGENTS.md
  - Планування етапів розробки (пX.Y)
  - Створення документації
- **НЕ робить:** Не пише код (окрім документації)

### Vibe Code (Виконання)

- **Відповідальність:** Реалізація коду згідно планів Vibe Work
- **Дії:**
  - Написання коду
  - Написання тестів
  - Виправлення багів
  - Оновлення коду
- **НЕ робить:** Не планує нові фічі (лише виконує вже заплановане)

### Категорічні заборони

- Пуш без PR у `main` (гілка захищена: PR + чека `test` — ADR-0025/0028)
- Мержити PR без явного апруву власника (конвенція мержу — ADR-0052: явний апрув у сесії чи коментарі PR дозволяє агенту виконати merge-коміт; апрув однієї серії не узагальнюється на нові PR)
- Видаляти гілочку Git (`iter-*`)
- Змінювати історію Git (rebase, amend, force-push без схвалення)
- Видаляти залежності без ADR (ADR-0012: ADR + явна авторизація власника, коміти `chore(deps):`)
- Використовувати `Math.random()` у ядрі (див. ADR-0003)
- Порушувати детермінізм (кожен сід + послідовність дій = той самий результат)

## Вимоги до коду

### 1. Коментарі та документація

- **Мова:** Ukrainian (коментарі, логіка, тести)
- **Формат комітів:** [Conventional Commits](https://www.conventionalcommits.org/) українською

  ```
  feat(core): додати функцію розрахунку
  fix(combat): виправити розрахунок точності
  docs(adr): додати ADR-0011 про економіку
  chore(ci): оновити workflow preview.yml
  ```

### 2. Нумерація задач (ADR-0043)

- **Формат:** `пX.Y` де X = номер фази, Y = номер етапу
- **Приклади:** `п8.1`, `п8.2`, `п8.3`
- **Рефакторинг за запитом власника (ADR-0044 п.1) — окрема лінія `пR.Y`** (ADR-0049): не входить у послідовність етапів фаз (прецедент нечислових тегів — `iter-P`, `iter-D`)
- **Правила:**
  - Етапи в фазі виконуються послідовно
  - Не можна переходити до п8.3, не завершивши п8.2
  - Кожен етап документується в workflow.md
- **ADR не оновлюємо** - лише створюємо нові з унікальними номерами

### 3. Тестування

- **Покриття:** мінімум 80% для ядра (`src/core/`)
- **Детермінізм:** Тести з фіксованим RNG

  ```typescript
  const alwaysHit: RNG = () => 0;
  const rng = mulberry32(42);
  ```

- **Перед комітом:** `npm test` має проходити

### 4. Шари архітектури

- **`src/core/`:** Чиста логіка (без DOM/Canvas) — див. ADR-0002
- **`src/main.ts`:** Цільовий UI (ванільний TS + Canvas 2D) — див. ADR-0010
- **`src/core/ai-bot.ts` + `src/core/intercept-bot.ts`:** Демо-бот і бот перехоплень (пR.3, ADR-0038; колишній `src/bot.ts` видалено — UI-інтеграція в `src/ui/*`)

## Workflow AI-Agent

### 1. Початок сесії

```bash
# Крок 0: ОНОВИТИ ЛОКАЛЬНИЙ РЕПОЗИТОРІЙ (ОБОВ'ЯЗКОВО!)
git pull origin main

# Крок 1: Ознайомитися з контекстом
cat docs/workflow.md
cat AGENTS.md
ls docs/adr/

# Крок 2: Перевірити поточний стан
git status
git log --oneline -5
git tag -l | sort -V | tail -5

# Крок 3: Вибрати завдання
# - Для Vibe Work: "п8.3" → спланувати етап
# - Для Vibe Code: виконати заплановане
```

### 2. Розробка

```bash
# Крок 1: Перевірити вхідні дані
# - Прочитати ADR, пов'язані з завданням
# - Перевірити поточний стан коду

# Крок 2: Планування (Vibe Work)
# - Створити план в docs/ (EARS-format)
# - Створити нові ADR (якщо потрібно)
# - Оновити workflow.md

# Крок 3: Реалізація (Vibe Code)
# - Реалізувати код згідно плану
# - Написати тести

# Крок 4: Тестування і перевірка типів
npm test
# typedoc = перевірка типів: vitest типи не перевіряє (урок П11.3) —
# без цього кроку типові помилки ловить лише CI
npm run docs

# Крок 5: Перевірка exact-байтів (якість коду)
# - Для зміни файлів
./scripts/verify-exact-bytes.sh
# - Автоматична перевірка
./scripts/verify-exact-bytes.sh --fix
```

### 3. Завершення сесії (ADR-0028: гілка + PR, merge в main)

```bash
# Крок 0: Тематична гілка — один раз на початку сесії, не в main
git checkout -b <тип>/<крок>-<суть> origin/main

# Крок 1: Зробити коміт (після npm test і npm run docs)
git add .
git commit -m "feat(core): додати функцію X"

# Крок 2: Пуш гілки + PR у main
git push origin <гілка>
# Опис PR: що змінилось, чому, критерії приймання (ADR-0023), результати npm test

# Крок 3: Дочекатися CI
# - Червоний CI = стоп, фіксити до пушу
# - Зелений CI = можливість merge (merge-комітом) = «схвалює» (ADR-0023); агент PR не робить
# - Після merge: git checkout main && git pull --ff-only, гілку видаляти
# - Перевірити https://sergkarpenko.github.io/rubezh/

# Крок 4: Додати тег (після валідації людини — не в сесії агента) — на merge-коміті в main
git tag iter-X.Y
git push origin iter-X.Y

# Крок 5: Оновити workflow.md
# - Статус ітерацій
# - Уроки
# - Рішення

# Крок 6: Запланувати наступні кроки в кінці сесії (workflow.md):
# - Останній зміни ADR: шапка файлу = рядок у таблиці AGENTS.md = accepted
# - Закрити фазу: рядок у таблиці = ЗАВЕРШЕНО + тег phaseN-complete
# - Відкрити фазу: рядок = У РОБОТІ; початок нової фази (phaseN) — [x] з записом «Наступний крок»
# - Закриті кроки фази — [x] з записом «ВИКОНАНО»
# Знайдений вільний рядок — вибрати для нової сесії
```

### Процес для Vibe Work (Планування)

```bash
# 1. Отримати промпт "п8.3" від користувача
# 2. Оновити локальний репозиторій
git pull origin main
# 3. Проаналізувати поточний стан
# 4. Створити план для п8.3 в docs/ (EARS-format)
# 5. Створити нові ADR (якщо потрібно)
# 6. Оновити workflow.md з планом
# 7. Комітити зміни
```

### Процес для Vibe Code (Виконання)

```bash
# 1. Отримати план від Vibe Work (або прочитати workflow.md)
# 2. Оновити локальний репозиторій
git pull origin main
# 3. Реалізувати код згідно плану
# 4. Створити PR згідно ADR-0028
# 5. Тестувати, комітити, пушити
```
