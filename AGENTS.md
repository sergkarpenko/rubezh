## Принципи роботи

1. Одна сесія = один вузький крок (див. [docs/workflow.md](docs/workflow.md))
2. Читати перед дією: ADR, workflow, поточні стан коду
3. Тестувати перед комітом: `npm test` має проходити
4. Детермінізм: Один сід + послідовність дій = той самий результат
5. **Розробка йде виключно через агентів** - репозиторій є джерелом правди
6. Крок веде сесія агента (Claude); Mistral — лише аудитор PR у джобі `vibe-audit` (ADR-0101, ADR-0104)

## Ролі (ADR-0100, ADR-0101, ADR-0104)

- **Сесія агента, що веде крок (Claude):** план кроку, ADR, дизайн-аналіз UX/UI і варіанти на вибір власника (колишня роль Vibe Work, рішення власника 2026-10-19), код і тести, документи, PR; питання власникові — до реалізації; мерж — після «схвалюю» (ADR-0052) або сам для PR класу `auto` (ADR-0094).
- **Аудитор для мержу (ADR-0094):** читач без контексту автора, інша модель (у сесії Claude — субагент Opus); його аудит — умова мержу класу `auto`.
- **Mistral Vibe CLI — джоба CI `vibe-audit` (ADR-0102, ADR-0104):** аудитор PR у копії репозиторію на голові PR; файлів не змінює; чек не обов'язковий, умову мержу не виконує.
- **Власник:** правила гри, тексти UI, вибір варіантів, «схвалюю» для PR класу `approve`, реліз-теги після валідації.
- **Історія:** ролі Vibe Work (планування) і Vibe Code (виконання) з ADR-0042 не діють — схему виконавця згорнуто (ADR-0100), режим Issues закрито (ADR-0101); джобу `mistral-audit` вимкнено (ADR-0104). Колишній текст розділів — у тегу `iter-T.86`.

### 1. Коментарі та документація

- **Мова:** Ukrainian (коментарі, логіка, тести)
- **Формат комітів:** [Conventional Commits](https://www.conventionalcommits.org/) українською

  ```
  feat(core): додати функцію розрахунку
  fix(combat): виправити розрахунок точності
  docs(adr): додати ADR-0011 про економіку
  chore(ci): оновити workflow preview.yml
  ```

### 2. Нумерація задач (ADR-0043)

- **Формат:** `пX.Y` де X = номер фази, Y = номер етапу
- **Приклади:** `п8.1`, `п8.2`, `п8.3`
- **Рефакторинг за запитом власника (ADR-0044 п.1) — окрема лінія `пR.Y`** (ADR-0049): не входить у послідовність етапів фаз (прецедент нечислових тегів — `iter-P`, `iter-D`)
- **Правила:**
  - Етапи в фазі виконуються послідовно
  - Не можна переходити до п8.3, не завершивши п8.2
  - Кожен етап документується в workflow.md
- **ADR не оновлюємо** - лише створюємо нові з унікальними номерами

### 3. Тестування

- **Покриття:** мінімум 80% для ядра (`src/core/`)
- **Детермінізм:** Тести з фіксованим RNG

  ```typescript
  const alwaysHit: RNG = () => 0;
  const rng = mulberry32(42);
  ```

- **Перед комітом:** `npm test` має проходити (коміт лише з документів і допоміжних скриптів хук пропускає без тестів, ADR-0146)
- **Мутаційне тестування (ADR-0083):** `npm run test:mutation` — вимірювання якості тестів ядра, не гейт і не крок сесії; повний прогін на раннері GitHub — ≈ 40–60 хвилин (крок `npm run test:mutation` workflow `mutation`: 16.11.2026 — 40 хв, 22.11 — 45 хв, 23.11 — 60 хв), під час прогону не запускати `npm test` (тайм-аути спотворять число). Базова лінія і розбір — `docs/reports/t10-mutation-baseline.md`. Повний прогін іде сам за розкладом у GitHub Actions (ADR-0084, workflow `mutation`: щопонеділка, якщо змінились код чи тести; вручну — Run workflow): останнє число — у зведенні останнього успішного прогону на `main`, звіт — артефакт `mutation-report`. У сесії запускати лише прицільний прогін по своїх файлах (`npx stryker run --mutate "src/core/<файл>.ts"`). Чек `mutation` не обов'язковий і мерж не блокує
- **Property-тести (ADR-0085):** `src/battle.property.test.ts` (бій) і `src/party.property.test.ts` (партія) — твердження про стан після кожної дії на згенерованих послідовностях (fast-check, фіксований сід; ідуть у `npm test`). Нова дія ядра, доступна гравцеві, — нова команда в генераторі; нове правило про стан — нове твердження у `broken`. Червоний property-тест друкує найкоротший контрприклад: перенести його звичайним тестом у файл тестів модуля разом із виправленням. Зміну генератора чи тверджень перед пушем прогнати з іншим сідом і більшим `numRuns`

### 4. Шари архітектури

- **`src/core/`:** Чиста логіка (без DOM/Canvas) — див. ADR-0002; перевіряється механічно (ADR-0079): `tsconfig.core.json` без lib.dom + ESLint-правила `src/core` (без `Math.random`, годинника, імпортів поза ядром)
- **`src/main.ts`:** Цільовий UI (ванільний TS + Canvas 2D) — див. ADR-0010
- **`src/core/ai-bot.ts` + `src/core/intercept-bot.ts`:** Демо-бот і бот перехоплень (пR.3, ADR-0038; колишній `src/bot.ts` видалено — UI-інтеграція в `src/ui/*`)

## Workflow AI-Agent

### 1. Початок сесії

```bash
# Крок 0: ОНОВИТИ ЛОКАЛЬНИЙ РЕПОЗИТОРІЙ (ОБОВ'ЯЗКОВО!)
git pull origin main

# Крок 1: Ознайомитися з контекстом
# docs/workflow.md великий (≈ 200 КБ) — не читати цілком: заголовки, далі активна фаза,
# «Наступні кроки» й уроки; завершені фази і записи старих кроків — в docs/workflow-archive/, за потреби (ADR-0074, ADR-0137)
grep -n '^## \|^### ' docs/workflow.md
cat AGENTS.md
ls docs/adr/
# Довідники агентів (ADR-0096) — практичний досвід кроків, не правила: спільний і свого типу кроку
# (ui.md — вигляд і UX, sim.md — ядро, симуляції, баланс)
cat docs/agents/common.md

# Крок 2: Перевірити поточний стан
git status
git log --oneline -5
git tag -l | sort -V | tail -5

# Крок 3: Вибрати завдання
# - Крок Т.N або етап пX.Y — за запитом власника («роби Т.N»); зміст — рішення власника наперед
```

### 2. Розробка

```bash

# - Прочитати ADR, пов'язані з завданням
# - Перевірити поточний стан коду

# Крок 2: Планування — сесія, що веде крок
# - Етап фази: план з EARS-критеріями (ADR-0023); нові ADR — якщо потрібно
# - Питання про правила гри, тексти UI, варіанти — власникові до реалізації
# - Запис кроку в workflow.md

# Крок 3: Реалізація — та сама сесія (ADR-0100)
# - Код і тести; аудит — після відкриття PR (див. крок 3 завершення сесії)

# Крок 4: Тестування і перевірка типів
npm test
# Повна перевірка типів, включно з тестами (ADR-0076): vitest типи не перевіряє
# (урок П11.3), typedoc тести виключає — той самий крок є гейтом у CI
npx tsc --noEmit
# Ядро без DOM (ADR-0002/0079): src/core компілюється без lib.dom
npx tsc --noEmit -p tsconfig.core.json
# Скрипти scripts/*.ts, кореневі playwright*.config.ts і e2e/smoke.e2e.ts з типами Node (ADR-0106, ADR-0140, ADR-0141)
npx tsc --noEmit -p tsconfig.scripts.json
# Лінт (src, scripts, e2e і playwright*.config.ts, ADR-0106, ADR-0111, ADR-0140), зокрема правила ядра (ADR-0079): Math.random/годинник/імпорти поза src/core
npm run lint
# typedoc = генерація довідки API (ADR-0016/0019)
npm run docs
# Сценарій приймання в браузері (ADR-0080): smoke-сценарій ADR-0030 проти збірки
# цього коміту, звірка сторінки з дзеркалом ядра; зміни UI і вводу — обов'язково.
# Без браузера Playwright: E2E_CHROME=/шлях/до/chrome npm run test:e2e
npm run test:e2e

# Крок 5: Перевірка exact-байтів (якість коду)
# - Для зміни файлів
./scripts/verify-exact-bytes.sh
# - Автоматична перевірка
./scripts/verify-exact-bytes.sh --fix
```

### 3. Завершення сесії (ADR-0028: гілка + PR, merge в main)

```bash
# Крок 0: Тематична гілка — один раз на початку сесії, не в main
git checkout -b <тип>/<крок>-<суть> origin/main

# Крок 1: Зробити коміт (після npm test і npm run docs)
git add .
git commit -m "feat(core): додати функцію X"

# Крок 2: Пуш гілки + PR у main
# Розмір дифа до пушу (ADR-0077; ліміт 500 рядків коду, ADR-0036/0061):
./scripts/pr-size.sh origin/main HEAD
# Клас PR (ADR-0094): auto — мерж без «схвалюю» після зелених чеків і аудиту;
# approve — лише після «схвалюю». Перед мержем без «схвалюю» — версія з main:
# git fetch --depth=50 origin main && git show origin/main:scripts/pr-class.sh > /tmp/pr-class.sh && sh /tmp/pr-class.sh origin/main HEAD
./scripts/pr-class.sh origin/main HEAD
git push origin <гілка>
# Опис PR: що змінилось, чому, критерії приймання (ADR-0023), результати npm test

# Крок 3: Дочекатися CI
# - Червоний CI = стоп, фіксити до пушу
# - Аудитор для мержу (ADR-0094) — запускає сесія одразу після відкриття PR
# - Чек `vibe-audit` (ADR-0102, ADR-0104) лишає в PR коментар «Аудит Vibe» (Mistral Vibe CLI): не обов'язковий;
#   знахідки обох аудиторів перевірити — підтверджені виправити, відхилені перелічити з причиною в описі PR
# - Зелений CI = можна мержити (merge-комітом): агент мержить після «схвалюю» власника (ADR-0052)
#   або сам — PR класу auto (ADR-0094) і механічний PR (ADR-0057)
# - Після merge: git checkout main && git pull --ff-only, гілку видаляти
# - Перевірити https://sergkarpenko.github.io/rubezh/

# Крок 4: Тег кроку — на merge-коміті в main, ставить workflow `iter-tag` (ADR-0093):
# в описі PR кроку (в серії — останнього змістовного PR) рядок «Iter-Tag: iter-X.Y»;
# чек `check` показує назву до мержу. Після мержу перевірити:
git ls-remote --tags https://github.com/sergkarpenko/rubezh.git iter-X.Y
# Тег не з'явився — запустити workflow `iter-tag` вручну (входи tag і sha merge-коміту)

# Крок 5: Оновити workflow.md
# - Статус ітерацій
# - Уроки
# - Рішення

# Крок 6: Запланувати наступні кроки в кінці сесії (workflow.md):
# - Останній зміни ADR: шапка файлу = рядок у таблиці AGENTS.md = accepted
# - Закрити фазу: рядок у таблиці = ЗАВЕРШЕНО + тег phaseN-complete
# - Відкрити фазу: рядок = У РОБОТІ; початок нової фази (phaseN) — [x] з записом «Наступний крок»
# - Закриті кроки фази — [x] з записом «ВИКОНАНО»
# Знайдений вільний рядок — вибрати для нової сесії
```

## Уроки (Lesson Learned)

Єдине місце уроків — розділ «Уроки» у [docs/workflow.md](docs/workflow.md) (ADR-0023: офіс у workflow.md; дублювання у двох файлах заборонено). Урок окремого кроку пишеться підпунктом «Урок» у записі цього кроку в тому ж файлі; у розділ «Уроки» — урок, що стає правилом для всіх агентів (така зміна — PR класу `approve`, ADR-0094). Агенти читають уроки з workflow.md під час планування. Ретроспективний PR завершеної фази може переносити уроки фази в архів-файл фази (`docs/workflow-archive/`, ADR-0074); уроки активного процесу лишаються у workflow.md. Робочі поради про спосіб виконання кроку (команди, пастки середовища) — у довідниках `docs/agents/` (ADR-0096): це не уроки-правила, і правило там не дублюється.
