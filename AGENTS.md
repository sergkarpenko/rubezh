## Принципи роботи

1. Одна сесія = один вузький крок (див. [docs/workflow.md](docs/workflow.md))
2. Читати перед дією: ADR, workflow, поточний стан коду
3. Тестувати перед комітом: `npm test` має проходити
4. Детермінізм: Один сід + послідовність дій = той самий результат

| `.gitignore` | Змінювати | Централізоване керування |
| `package.json` (без ADR) | Змінювати | Залежності — лише за процесом ADR-0012: ADR + явна авторизація власника |
| `tsconfig.json` | Змінювати | Конфігурація TypeScript |
| `vite.config.ts` | Змінювати | Конфігурація збірки |

### Категоричні заборони
- Пуш безпосередньо в `main` (гілка захищена: PR + чек `test` — ADR-0025/0028)
- Мержити PR (мерж = «схвалюю» власника — ADR-0023/0028)
- Видаляти теги Git (`iter-*`)
- Змінювати історію Git (rebase, amend, force-push без схвалення)
- Додавати залежності поза процесом ADR-0012 (ADR + явна авторизація власника, коміт `chore(deps):`)
- Використовувати `Math.random()` у ядрі (див. ADR-0003)
- Порушувати детермінізм (кожен сід має давати однаковий результат)

## Встановлення та налаштування

### Pre-commit hook

Хук встановлюється автоматично при `npm install` через Husky (ADR-0014): скрипт `prepare` задає `core.hooksPath = .husky/_`, а `.husky/pre-commit` викликає `scripts/pre-commit.sh`.

```bash
npm install
```

Hook перевіряє:
- Правила AGENTS.md (заборонені файли)
- Тести (`npm test`)
- Exact-байти (проти розходжень з git)

### Перевірка exact-байти

Для ручної перевірки:

```bash
./scripts/verify-exact-bytes.sh
# або з автоматичним виправленням (лише для текстових файлів)
./scripts/verify-exact-bytes.sh --fix
```

## Вимоги до коду

### 1. Коментарі та повідомлення

- **Мова:** Ukrainian (коментарі, тексти помилок, лог)
- **Формат комітів:** [Conventional Commits](https://www.conventionalcommits.org/) українською

  ```
  feat(core): додати підтримку заступи
  fix(combat): виправити розрахунок точності
  docs(adr): додати ADR-0011 про економіку
  chore(ci): оновити workflow preview.yml
  ```

### 2. Типізація

- **TypeScript:** Суворі типи, жодних `any`
- **ADR посилання:** Коментувати код з посиланнями на ADR

  ```typescript
  // ADR-0002: Чисте ядро без DOM — уся логіка тут
  export function calculateHitChance(unit: Unit, mode: ShotMode): number { ... }

  // ADR-0003: Детермінізм через ін'єктований RNG
  export function mulberry32(seed: number): RNG { ... }
  ```

### 3. Тестування

- **Покриття:** Мінімум 80% для ядра (`src/core/`)
- **Детермінізм:** Тести з фіксованим RNG

  ```typescript
  const alwaysHit: RNG = () => 0;
  const rng = mulberry32(42);
  ```

- **Перед комітом:** `npm test` має проходити

### 4. Шари архітектури

- **`src/core/`:** Чиста логіка (без DOM/Canvas) — див. ADR-0002
- **`src/main.ts`:** Цільове відображення (ванільний TS + Canvas 2D) — див. ADR-0010
- **`src/bot.ts`:** Демо-бот для превью

## Workflow AI-Agent

### 1. Початок сесії

```bash
# Крок 1: Ознайомитися з контекстом
cat docs/workflow.md
cat AGENTS.md
ls docs/adr/

# Крок 2: Перевірити поточний стан
git status
git log --oneline -5
git tag -l | sort -V | tail -5

# Крок 3: Вибрати завдання з "Наступних кроків" (workflow.md) або за вказівкою
```

### 2. Розробка

```bash
# Крок 1: Прочитати відповідні ADR
# Приклад: перед змінюванням бойового ядра
cat docs/adr/0002-pure-core-no-dom.md
cat docs/adr/0003-injected-rng-determinism.md
cat docs/adr/0004-distance-independent-accuracy.md
cat docs/adr/0005-overwatch-one-shot-penalty.md

# Крок 2: Зробити зміни у коді
# - Додати посилання на ADR у коментарі
# - Дотримуватися Conventional Commits

# Крок 3: Тестувати
npm test

# Крок 4: Перевірити exact-байти (якщо кодувати через пісочницю)
# Порівняти файли з локальним станом
```

### 3. Завершення сесії (ADR-0028: гілка + PR, мерж власником)

```bash
# Крок 0: Тематична гілка — одразу на початку роботи, НЕ в локальному main
git checkout -b <тип>/<крок>-<суть> origin/main

# Крок 1: Зробити коміт (після npm test)
git add .
git commit -m "feat(core): додати функцію X"

# Крок 2: Пуш гілки + PR у main
git push origin <гілка>
# Опис PR: що змінено, чому, критерії приймання (ADR-0023), результати npm test

# Крок 3: Дочекатися чека `test` у PR і мержу власником
# - Червоний CI = стоп, фіксити до продовження
# - Мерж (merge-комітом) робить власник = «схвалюю» (ADR-0023); агент PR не мержить
# - Після мержу: git checkout main && git pull --ff-only && git branch -d <гілка>
# - Перевірити https://sergkarpenko.github.io/rubezh/

# Крок 4: Додати тег (після валідації людиною) — на merge-коміт в main
git tag iter-X.Y
git push origin iter-X.Y

# Крок 5: Оновити workflow.md
# - Статус ітерацій
# - Уроки
# - Рішення
```

**Зміна рішення?** Створіть новий ADR з полем `Supersedes: ADR-NNNN`.

**Реєстр ADR не губити (правило 2026-10-14, після того, як ADR-0029/0030 не потрапили в таблицю):** новий ADR і його рядок у таблиці вище — в одному PR; рядок додається ще на поданні зі статусом із файлу ADR (`proposed`). Мерж PR = прийняття рішення (ADR-0030): окремий PR для зміни статусу не потрібен — статус фактично стає `accepted` (конвенція в шапці ADR), наступна правка таблиці синхронізує напис. Перевірка перед пушем: найбільший номер ADR у `docs/adr/` = останній рядок таблиці.

## Зв'язок з власником

**Коли звертатися до власнику:**

- Незрозуміле архітектурне рішення
- Потреба у новому ADR
- Зміна існуючого ADR
- Проблеми з CI/CD
- Валідація людиною (перед тегом)

**Як звертатися:**

- Чітко описати проблему
- Запропонувати рішення
- Посилатися на ADR чи workflow
